## 1. 通用前提：`.nct` 加密与 keystream 上限（**这条决定了很多方案可行不可行**）

* `.nct` = 明文按**字节位置** XOR `keystream_full.bin`。同一位置对任何文件都是同一个字节，
  与文件内容、文件名无关；XOR 对称，加密解密同一个函数。
* `re\nctwork\keystream_full.bin` 与 `keystream_big.bin` **都是 603,513 B，内容完全相同**，
  且不是周期序列（周期 16…65536 全部不成立），无法外推。
* ⇒ **任何超过 603,513 B 的 `.nct` 我们都写不出来**（缺密钥流字节）。
* `carupgrade.upgrades.nct` 的文件长度**恰好等于 603,513 B**，一个字节都加不进去。
  *这是工具链限制，不是引擎限制*——引擎自己会按位置生成密钥流，读多大的文件都行；
  我们只是没有 603,513 之后的密钥流。所以「克隆一个 upgrades 块」在数据上可行、
  在**加密上不可行**。
* 数据包里另有 3 个超限 `.nct`（`data\events.dat.nct` 14.4 MB、`jobs.bin.nct` 3.5 MB、
  `gtlt.bin.nct` 688 KB），都不属于本次五张表。

### 2.3 `appearances.link.nct`（12,685 B）— 别名车 → 基础车 的外观映射

**布局**

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0 | u32 | version = **1**（读错会报 `Error loading appearances.link.nct - expected version %d, found version %d.`，0x004513C4） |
| 4 | u32 | count = **82** |
| 8 | — | 条目区 |

每条 = `[token 别名车名]` + `u32 (恒为 1)` + `u32 (多为 0)` + `[token 基础车名]`，
即两个车名 token 之间固定夹 **8 B**。此后再接**可选 payload**。

* 全文件共 **272 个 token**：164 个车名（82×2）+ **108 个涂装贴图路径**，后者只出现在
  4 台 NASCAR 车上（例如 `2020_chevrolet_camaro_nascar_ext_fictional_181.ptc.pvr.z` 与其
  完整路径 `2019_chevrolet_camaro_nascar/livery/…ptc.pvr.z` 成对出现）。
  payload 的确切 schema **未定** → 见 §5「需人工确认」。
* 条目长度：最短 63 B（第 0 条 8..71，`2011_nissan_jrm_gtr_gt1 → 2011_nissan_sumo_gtr_gt1`），
  带 payload 的最长约 1.4 KB。

**LFA 在里面长什么样：没有。** `lexus` / `lfa` 在整文件里命中 **0**——
LFA 的外观数据直接放自己的 `.appearances.nct`，不需要 link 条目。**条目占用：0 B。**

**插入脚本规则：** 不需要。若要给新车做「别名 → LFA 外观」，可以克隆第 0 条再改两个名字；

## 3. 为什么这五张表「缺了不崩」，而那两张「缺了就崩」

| 查找方式 | 表 | 查不到的结果 |
|---|---|---|
| **按车 id 的升序定长数组 + 二分/下标**，返回值**直接解引用** | `suspensionbehaviour.suspensiondata.nct`（540×140 B，首 u32=id）、`cardamagethresholds.damage.nct`（540×116 B） | 越界/`nullptr` → 实测 `fault addr 0x28` 崩溃；日志 `Failed to match suspension data for car: %d. Does the whitelist need to be updated?` |
| **按字符串 key / 名字查**（哈希或线性），查不到有默认值 | `carupgrade`（desc 给的 key → 回退级别默认块）、`appearances.link`（别名缺省=用自身外观）、`carparts` / `carrepairs`（与车无关的字典） | 走默认值/空串，不崩 |
| **按车名找「每车一个文件」** | `liveries/<车名>.liveries.bin.nct`、`<车名>.*` 资源 | 文件缺失是常态（352/540），只丢涂装 |

所以判断新表要不要注册，**先看它有没有「车辆 id 字段 + 有序数组」**：
有 → 必须补记录（否则崩溃）；没有（纯名字/纯 key）→ 缺省有回退，不必补。

## 4. 工具 `analysis/newcar_tables.py`

```
python analysis/newcar_tables.py <表> <动作> [选项]
    表  : parts | repairs | link | upgrades | livery | all
   动作 : list | dump | insert | remove | selftest
选项  : --src 名  --new-name 名  --new-key key  --out-dir 目录  --dry-run
```

* 源包**只读**：所有产物写到 `analysis/out_tables/`（文件名与包内一致，可直接覆盖回去）。
* 加解密都用 `analysis/nct_dec.py` 的 keystream；超过 603,513 B 时 `save()` 会拒绝写盘并说明原因。
* `--selftest` = 「插入 → 删除 → 与原文件逐字节比较」。

**自测结果（2026-10-25，Build260716 真包）**

| 表 | 插入 → 删除 | 字节数变化 | 逐字节一致 |
|---|---|---|---|
| parts | 379 → 380 → 379 条 | 50,648 → 50,773 → 50,648 | ✅ |
| repairs | 33 → 34 → 33 条 | 5,531 → 5,720 → 5,531 | ✅ |
| link | 82 → 83 → 82 条 | 12,685 → 12,744 → 12,685 | ✅ |
| upgrades | 329 → 330 → 329 块（块数 1453 处同步 329→330→329） | 603,513 → 605,309 → 603,513 | ✅（仅内存态，超 keystream 无法落盘） |

## 5. 需人工确认 / 未定项

1. `carupgrade.upgrades.nct` 偏移 0 的 **u32 = 1005 含义未定**（不是块数 329，不是条数，
   全文唯一一处）。插入脚本不动它。若将来真要加块，得先确认它会不会被校验。
2. `carupgrade` 的 **数值槽位全 0**：本包所有 329 块的价格/PR 都是 0，
   推测数值在别的表/每车 spec 里。若实机升级界面显示异常，问题不在这张表。
3. `appearances.link.nct` 里 4 台 NASCAR 条目带的 **payload schema 未定**
   （108 个贴图路径 token）。克隆这些条目需人工确认；LFA 没有条目，不受影响。
4. `carrepairs.repairs.nct` 的 **19 个 u32 字段含义只到「猜测」**（费用/磨损/倍率/序号/分类）。
   插入克隆记录时是整体复制，不影响正确性，但不要手改数值。
5. `liveries` 文件内部是否含**绝对偏移**未被证明（708..996 的 288 B 参数区与
   `(u32, 0x799/0x79a)` 对表疑似索引）。当前做法只改第 1 个 token（+9 B），
   未做偏移修补；若实机涂装错乱，需回到这里确认。
6. **keystream 只有 603,513 B**：任何「让文件变大」的方案（含 upgrades 加块、
   `events.dat.nct` 等 3 个超限文件）在工具链上都是**死路**，除非另行导出更长的密钥流。
