## 1. 装好并确认能用

### 1.1 装

把 `rr3_blender_addon/` 整个目录拷进

```
%APPDATA%\Blender Foundation\Blender\4.5\scripts\addons\rr3_blender_addon\
```

然后 *Edit ▸ Preferences ▸ Add-ons*，搜 `Real Racing 3`，勾上。

### 1.2 三条自检

| 检查 | 期望 |
| --- | --- |
| 3D 视图按 `N`，看有没有 **RR3** 标签页 | 有，且分 Import / Export / Textures / Car / Reference 五组 |
| *File ▸ Import* 里有没有 `Real Racing 3` 子菜单 | 有，且**有 7 项**（含 `Driver (posed)`） |
| *File ▸ Export* 里有没有 `Real Racing 3` 子菜单 | 有，且**有 4 项** |

旧版（1.0）的 bug 就是这里只有 3 项和 1 项 —— 因为"导入模型 / 导入整车"
那几个类定义了却没注册进 `classes` 元组。2.0 已修。

### 1.3 脱离 Blender 的自检（可选）

底层 `rr3lib/` 是纯 Python，不需要 Blender：

```bash
python tools\test_car.py        # 端到端造车全流程，13 项，最后打印 CARTEST: PASS
python tools\sync_rr3lib.py --check   # 插件里那份 rr3lib 是否和根目录一致
```

## 2. 任务 A：把一台车导进 Blender 看模型

**用时**：1 分钟。**产出**：场景里一台完整的车（车身 + 四轮 + 方向盘 + 锚点 + 尾翼枢轴）。

1. *File ▸ Import ▸ Real Racing 3 ▸ Import RR3 Vehicle (wheels + aero)*
2. 文件浏览器里**进到车目录**，随便选一个文件（插件只取目录路径）。
   例：`...\.depot\vehicles\2012_lexus_lfa\`
3. 参数保持默认，点 *Import RR3 Vehicle*。

导入后你会看到：

| 对象 | 说明 |
| --- | --- |
| 一个集合，名字是车名 | 里面是全部对象 |
| 车身网格 | 名字形如 `LOD_A_BODY_mm_ext` |
| `WHEEL_FL` / `WHEEL_FR` / `WHEEL_BL` / `WHEEL_BR` | 轮子枢轴（ARROWS 显示），轮网格挂在下面 |
| `STEERING_WHEEL` | 方向盘枢轴 |
| `AERO_0_*` … | 每个会动的零件一个（CUBE 显示），只在有 `_wing.banim` 的车上有 |
| `ANCHOR_POINT_*` / `ANCHOR_HINGE_*` | 锚点空物体 |
| `<车名>_LOD<X>_damaged` / `_camera` / `_blur` | 三个子集合：撞毁件、车头视角壳与发光片、轮子的动态模糊替身。`_blur` 里的网格和轮子完全重合（就是轮子飞速转起来时引擎换上去的那两个），觉得挡事就把这个子集合关掉 |

> **法向：能编辑，且和游戏看起来一样。** 导入默认**不烘** `.m3g` 里的法向（`file_normals` 关），
> 而是 `shade smooth` 让 Blender 按几何实时算。原因很实际：烘进去的自定义法向是**冻结数据**，
> 你一动顶点它不跟着变，表面就会冒出和形状无关的锐利三角面——这就是"衰减编辑一拉就花"。
> 实测（Chiron 车身壳，拉 6 个相邻顶点 0.25 m）：烘法向 → 4 条边法向夹角 >10°、最坏 58.9°；
> 不烘 → 0 条、最坏 0.04°。两种做法观感差别很小（文件法向与几何法向夹角中位 0.6°、p90 5.5°），
> 因为 RR3 的硬边本来就是"同一位置两个顶点"，平滑跨不过去。
> 已经导入的旧模型不用重导：选中 → `N` 面板 → *Car ▸ Make normals editable*。
> 只做导出、不做编辑时，把 `file_normals` 勾上可获得最贴近游戏的硬边。

### 常见调整

| 症状 | 改什么 |
| --- | --- |
| 车陷进地面 / 浮空 | `height_adjust`，±0.3 米微调 |
| 轮子看起来都一样大 | 正常，`wheel_size` 保持 `engine` 即可（默认值）；细节见下 |
| 轮子太大 / 太小 | 先确认 `wheel_size` 是 `engine`；还要单独调就动 `wheel_scale`（0.2–4.0），它会乘在自动系数上 |
| 轮子位置不对 / 掉在车底 | 不该再出现：轮子枢轴现在直接取 `.points` 锚点。若仍错，先看锚点对不对 |
| 后轮胎比轮毂窄（Pagani Huayra） | 保持 `rear_tyre_width` 勾选（默认）；它会按后轮辋宽度比拉宽后轮胎 |
| 某个轮子看起来"平的"、不接光 | 现在默认不烘自定义法向，法向由几何实时算；若真的看着平，先确认模型的 `use_smooth` 开着（*Object ▸ Shade Smooth*），再确认用的是最新 zip |
| **衰减编辑（比例编辑）一拉，表面出现锐利三角面** | 2026-11-25 之前导入的模型带着**自定义拆边法向**（从 `.m3g` 烘进去的），顶点一动法向不跟着变。选中对象 → `N` 面板 → *Car ▸ Make normals editable*（`rr3.clear_custom_normals`）即可修好；重新导入默认就是可编辑的，见 §3.1 的说明 |
| 重新导入后某些硬边变圆了 | 反了：`file_normals` 勾上会烘回文件里的法向（硬边最准），但那样就不能放心编辑了。两者取舍见 §3.1 |
| 轮子飞速转起来时那个"糊成一圈的轮子"在哪 | 在 `<车名>_LOD<X>_blur` 子集合里，**正常显示**（不再默认隐藏了），和轮子重合着。觉得挡事就把这个子集合关掉；`blur_wheels` 不勾就完全不导 |
| 按距离合并顶点后棱变软了，再标锐边也标不回来 | 别用 Blender 自带的合并。用 `N` 面板 → Car ▸ **Weld, keep hard edges**：它按文件里的法向判断哪些是棱。已经合坏的模型只能靠重导（`rr3_normal` 属性在导入时才写） |
| 合并后贴花/徽标那块亮暗不对 | 预期内：贴花在文件里的法向和它自身几何差很远（染色靠面板法向），合并后只能按几何算。1.1% 的面角属于这种，见插件 README 的实测表 |
| 玻璃整块不透明 / 镂空贴图是实心的 | 现在导入会自己量贴图 alpha：有镂空的页（badges）接 alpha + DITHERED，有渐隐的页（wheel_blur）接 alpha + BLENDED，纯平的页不接。如果还是不对，确认 `textures` 勾着、用的是最新 zip |
| 拿 FBX 对位置时朝向反了 | `facing` 选 `-Y`（整车绕 Z 转 180°，车身/轮子/锚点一起转） |
| 拿到的 FBX 是镜像的 | 勾 `mirror_x`（整车在 X 上镜像） |
| 想让某个轴的动画角度归零 | `delta_axes` 勾上那个轴（X/Y/Z 各自独立，优先于 `rot_mode`） |
| 想要更精细的模型 | `lod` 改成 A（默认就是 A）；想快就用 D/E |
| 一次要全部 LOD | 勾 `all_lods`，每级一个子集合（`<车名>_LODA` … `_LODH`） |
| 少了刹车盘 / 卡钳 | 确认 `brakes` 是勾上的（默认）；注意只有 LOD A 和 B 有这两个网格 |
| 卡钳跟着轮子转过去了 | 不该再出现：卡钳四个各自建模在自己角落、不参与右轮半圈旋转。确认用的是最新 zip |
| LOD F 的轮子被拉大/移位了 | 不该再出现：LOD F 的轮子是预装配的整车网格，走独立路径放世界原点、不缩放 |
| 不要贴图（省内存） | 关掉 `textures` |
| 想要游戏自己的材质和贴图 | `materials` 选 **Game materials**（默认是 `simple` 假色） |
| 想换涂装 | `materials` 选 **Game materials** 导入，然后选中网格 *Car ▸ Switch paint scheme* 填预设号 |
| 贴图看不到 / 重启后变粉色 | 用 *Textures ▸ Load car textures* 重新加载；导入时的贴图已经打包进 .blend，粉色说明是旧版本 |
| 想要贴图文件本身 | *Textures ▸ Export textures*，把私有容器解成 PNG（见 §6.7） |
| 窗户/轮胎/刹车盘没贴图 | 它们的图在 `vehicles/common`，由 `default.liveries.bin.nct` 指定。确认 `materials = Game materials` 且用的是最新版本（取贴图按「涂装覆盖 → 车表 → default 表」三级回退） |
| 内饰（`_mm_cab`）跟着涂装变 | 正常，有些车的 cab 面板确实随涂装换贴图（Veyron GSV 有 `cab.png` / `cab_chrome.png` / `cab_orange.png`） |
| 车身有两个版本叠在一起、像穿模 | 那是完好件和撞毁件重合。确认 `separate_damage` 勾着（默认），损伤件会进 `<车名>_LOD<X>_damaged` 子集合 |
| 某个零件的贴图明显是别的零件的 | 材质名撞了。确认用的是最新版本（撞名会自动加 tag 后缀，如 `<车>_car_flat_cab`） |
| 材质太亮/太暗，跟游戏不一样 | 正常：Roughness/Metallic 是从游戏的双镜面叶瓣**换算**的，不是原值。见 `docs/游戏材质与涂装.md` §5 |
| 整车像镀铬、看不见车身颜色 | 旧版本 bug：`Specular Tint` 把游戏的 0–255 字节直接写进了 Blender 的 0..1 颜色槽，高光被放大 255 倍。现已除以 255，重新导入即可 |
| 贴图上下颠倒了 / 文字是反的 | 贴图需要**垂直翻转**：游戏把图存成 bottom-up，MonkeyTool 是"翻图、不翻 UV"。`texport.FLIP_V = True` 已默认开启，重新导入即可 |
| 轮胎也在跟着换涂装 | 不该再出现：只有涂装表覆盖到的部件才有多预设，轮胎/轮毂/刹车盘只给 1 套 |
| 有些零件没贴图 | 那些 tag（`chassis`/`dash`/`*_glow`）在涂装表里本来就没槽，只有材质参数 |
| 想导入驾驶员 | *File ▸ Import ▸ Real Racing 3 Driver*（`import_scene.rr3_driver`），见 §6.8 |
| LOD G 的轮子看起来是 F 级的 | 正常：`_shared.m3g` 只到 F 级，游戏在 G 级复用那套预装配轮子 |
| LOD H 没有轮子 | 正常：H 级是最低质量，游戏本来就不给轮子 |
| 车身里多出一层重复的车壳、和引擎盖打架 | 那是 `BONNETCAM` 车头视角壳。确认 `separate_camera` 勾着（默认），它会在 `<车名>_LOD<X>_camera` 里 |
| 只想看内饰 / 车头视角壳 | *LOD* 选 `int_a` / `int_b` / `shared`，它们会整份导入 |
| 尾翼看起来"绕原点转"而不是"绕铰链转" | 勾上 `hinge_pivot` |
| 尾翼角度一开始就是展开的 | `rot_mode` 保持 `DELTA`（把首帧归零）；想保留引擎原值选 `ABS` |

> **装配顺序**：整车导入是"**先导 points，再按 points 位置装轮子**"。
> `.points` 锚点先落地，`WHEEL_*` 枢轴直接取对应锚点的位置，轮子网格挂在枢轴下、
> **不做任何居中**（轮子局部坐标系里 `x = 0` 就是外侧面，正好落在 `POINT_WHEEL_*` 上）。
> 动画（尾翼）也用同一套 `pos_scale`/`pos_factor`，所以微调不会把组装拆开。
>
> **朝向 / 镜像**由**一个根空物体**（`<车名>_ROOT`）承担，车身、轮子、尾翼枢轴、锚点
> 全部挂在它下面，整体转/镜像——不会出现"车身转了轮子没转"。
>
> **轮子为什么需要单独一个参数**：游戏里的轮子网格是**一个 0.60 m 的通用模板**
> （463 台车的模板半径变异系数只有 0.46%），每台车加载时按自己的轮胎直径把它**径向**拉伸
> ——只拉 y/z，宽度不动。`wheel_size` 三档：
>
> - `engine`（默认）复现游戏算的系数，中位前轮 ×1.153、后轮 ×1.196；来源是
>   `suspensionbehaviour` 的轮胎直径（172 台）或 appearance 块的加载半径 ÷0.95（291 台）
> - `ground` 用加载半径，轮胎正好贴地，比 `engine` 小约 5%（车重压下去的那点）
> - `none` 不缩放，所有车都是 0.60 m 的模板
>
> 选中轮子网格看 `N` 面板 → Item → Scale，应该是 `(1.0, k, k)`，**x 恒为 1.0**。
> 完整推导与全库数字见 `docs/轮毂与轮胎缩放.md`。

> **前后轮不一样的车**：全库 463 台里 88 台有独立的 `TYRE_REAR`、149 台有独立的
> `WHEEL_REAR`。有专用网格的用专用网格；只有更宽的后轮辋、没有后轮胎的车（62 台，
> 其中 9 台轮辋比例偏离 1.0 超过 2%）按轮辋宽度比拉宽后轮胎。实测 87 台两种网格
> 都有的车，`TYRE_REAR/TYRE` 与 `WHEEL_REAR/WHEEL` 的中位偏差只有 0.6%，所以这个
> 代理是可靠的（Huayra：0.2336 × 1.230 = 0.2873 vs 轮辋 0.2896）。

> **刹车盘和卡钳**（`brakes`，默认开）：游戏对它们用的**就是轮胎那个径向系数**，
> 所以插件也是同一个 `(1.0, k, k)`、枢轴同样落在 `POINT_WHEEL_*` 上。只有一条差别：
> **卡钳不跟轮子转**。四个卡钳各自建模在自己那个角落、盘的后方
> （`BRAKE_CALIPER_FRONT_LEFT` 的 x 是正的、`_FRONT_RIGHT` 是负的），所以右轮那半圈
> 旋转只作用在轮辋、轮胎和刹车盘上；卡钳对象带 `rr3_brake_fixed = True`。
> 只有 **LOD A / B** 有这两个网格（全库 398–401 台），LOD C 及以下本来就没有——
> 那不是丢件，是游戏自己就这么省。

> **LOD F 的轮子是预装配的**：全库 463 台车的 `LOD_F` 轮网格都**跨越车身左右**
> （x 从 −0.95 到 +0.95 这种），y 从 0 到一个直径、z 覆盖轴距——就是四个轮子已经按
> 真实尺寸摆好的整车网格。再缩放或再按 points 平移就会做两遍。所以这一级走独立路径：
> 挂在一个位于**世界原点**的 `WHEEL_LODF_ASSEMBLED` 空物体下，`scale` 保持 1、位置保持 0，
> 顶点原样，并且**不做 `wheel_size` 拟合**。对象带 `rr3_pre_assembled = True`。

> **LOD G / H 的轮子**：`_shared.m3g` 里的轮子网格**只到 F 级**（全库 463 台车的 G、H
> 两级轮子网格数都是 0）。游戏的做法是 G 级**复用 F 级那套预装配网格**、H 级**干脆不要轮子**
> （已经是最低质量了）。插件照做：`WHEEL_LOD_FALLBACK = {"G": "F"}`、`NO_WHEEL_LODS = ("H",)`。
> 所以导入 LOD G 会看到一个 `LOD_F_WHEEL_mm_wheel`，导入 LOD H 没有轮子，这两件事都不是丢件。

> **相机壳和发光片**（`separate_camera`，默认开）：`_shared.m3g` 里除了轮子还有
> `LOD_A_BONNETCAM_BODY/HOOD_*`（车头视角用的第二个车身，和引擎盖完全重合、会 z-fighting）
> 和 `LOD_A_LIT_*_GLOW`（面向相机的发光片）。它们进 `<车名>_LOD<X>_camera` 子集合，
> 对象带 `rr3_camera = True`。注意车身文件里 375/463 台也有 `BONNETCAM`，但那些都是
> `BONNETCAM_HOOD_DAMAGE_*`，已经被损伤集合收走了。

> **`shared` / `int_a` / `int_b` 是完整模型，不是 LOD 的附属**：导入面板的 *LOD* 下拉里
> 有 `shared`、`int_a`、`int_b` 三项。选它们时插件**整份导入**（不装轮子、不装空力、
> 不报"缺 shared/缺 wing"），集合名分别是 `<车名>_shared`、`<车名>_int_a`、`<车名>_int_b`。
> `int_a`/`int_b` 是第一人称车内视角模型（各 43–44 个网格），`shared` 是车头视角壳
> （43 个网格，含轮子）。想单独看内饰/相机壳就用这三个入口。

> `textures` 打开时，插件会把 `.dxt.dds.z` 解到 `%TEMP%\rr3_dds\v2\` 再加载。
> 一个车目录有 12 张左右，第一次导入会慢几秒。

## 3. 任务 B：换车身模型（改完还能进游戏）

**用时**：10 分钟建模 + 2 分钟导出。**产出**：一个能替换原版 `<车>_a.m3g` 的文件。

### 3.1 建模要求（不满足引擎会拒或显示错乱）

- 一个网格 = 一个零件。零件名必须**就是 liveries 槽位表里的名字**，
  形如 `LOD_A_BODY_mm_ext`（完整 1869 个名单见参考手册）。
  名字不对 → 该零件拿不到材质，显示成纯黑高光。
- UV 必须展开。插件按 `UV_TILES = 4` 平铺，V 轴默认翻转。
- 顶点色可选；有的话按 0–4096 或 0–255 归一化。
- 硬边靠**顶点分裂**保留（插件会按 corner 算法重算法线）。
- 不要做蒙皮、不要一个网格塞多个材质 —— 不支持。

> **想合并顶点（按距离合并）时别用 Blender 自带的**：RR3 的硬边就是「同一位置两个顶点」，
> 一合就抹平，而且之后按角度标锐边也标不回来。用 `N` 面板 → Car ▸ **Weld, keep hard edges**
> （`rr3.weld_and_mark_sharp`）：它先记住每个角原本的法向，合并，再把「两侧法向原本不同」的边
> 标成锐边。Chiron 车身壳实测：普通合并平均偏 17.5°、51% 的面角偏差超过 5°；
> 这个 operator 平均 0.36°、1.1%。细节见插件 README。

### 3.2 导出步骤

1. 选中你要导出的网格（或者留空，导出全部网格）。
2. *File ▸ Export ▸ Real Racing 3 ▸ Export RR3 Model (.m3g)*
3. **`Template .m3g` 一定要填**：指向这台车的原版 `_a.m3g`。
   插件从里面抄三样东西：每个零件 81 字节的引擎私有块、材质列表、author 串。
   不填也能导出，但生成的块结构和引擎期望的不同，容易出怪问题。
4. `Position scale` 留 **0**（用模板值，原厂是 `0.0021973606199026108`）。
5. 导出。

> **绝对不要把 `Position scale` 设成 1.0。** 文件是合法的，但引擎会走慢速顶点路径
> —— 扫描线卡顿、高光全丢。如果你看到 `positionScale 1.0000000000`，
> 说明你手填了 1.0，重导一次。

### 3.3 验证

导出报告会写 `wrote N part(s), M bytes, positionScale 0.0021973606`。
`N` 应该等于你选中的网格数。如果 `N` 比预期小，说明有些对象不是 MESH。

进游戏前还可以用 *Reference ▸ File report* 把新文件和原版对一遍。

## 4. 任务 C：做一套会动的尾翼

**用时**：30 分钟。**产出**：`<车>_wing.banim` + `<车>_animations.xml`，以及 spec 里的行为开关。

这是整个流程里最容易搞错的一环，先记住三件事：

```
.banim        决定「能不能动」        —— 零件每帧在哪、转多少
_animations.xml 决定「动哪一段」      —— 片段名 → 帧范围
spec 行为串    决定「什么时候动」     —— 刹车时？到某个速度时？
```

**三者互相独立。** 实测 53 台有尾翼动画的车里，**34 台根本没写行为串**，
照样动得好好的；反过来 40 台 NASCAR 写了 `NascarAirBrake` 却没有 `_wing.banim`。

### 4.1 步骤

1. *Import ▸ Whole car*，选车目录，确认 `animate` 是开的。
   场景里会出现 `AERO_<轨道号>_<零件名>` 空物体，例如
   `AERO_1_WING_REAR_mm_ext`（`LOD_A_` 前缀被去掉了）。
2. 选中那个 `AERO_*` 空物体。**注意它的 location / rotation_euler 就是引擎值**
   —— 动画基和 Blender 基是同一个，不需要换算。
3. 摆姿势插关键帧：
   - 帧 1：收起姿态（尾翼平放）
   - 帧 31：展开姿态（尾翼抬起 45° 左右）
   - 只在 `AERO_*` 上插帧，不要动下面的网格
4. *File ▸ Export ▸ Real Racing 3 ▸ Export RR3 Part Animation (.banim)*
   - `Tracks from` 选 `AERO`
   - 存成 `<车目录名>_wing.banim`，放进车目录
5. *Export ▸ Animation Clips (.xml)*
   - `Preset` 选 `WING`，会生成 `wing_initial` + `wing_up` + `wing_down` 三段
   - `Start frame` / `End frame` 填你插帧的范围（上面例子是 1 和 31）
   - 存成 `<车目录名>_animations.xml`，放进车目录
6. 打开行为开关（**只有需要"自动展开"时才做**）：
   - 用插件：*Car ▸ Build a new car* 时勾 `aero`
   - 或手工：把 spec 里 `generic_race` 前的那个空 token（`00 00 00 00 0c 00 00 00`）
     **原地替换**成 `DeployWhenBraking`。
     **不能插入字节** —— 插入会让后面字段全部错位，引擎在 `+0x18` 空指针崩溃。

### 4.2 片段怎么选

| 你的车是 | 建议片段 |
| --- | --- |
| 普通跑车，尾翼整体抬起 | `wing_initial` + `wing_up` + `wing_down` |
| 尾翼有独立活动片（Huayra 那种） | 再加 `pivot_up` + `pivot_down` |
| 要做完整的四状态机 | 加 `neutral_to_speed` / `speed_to_neutral` / `speed_to_brake` / `brake_to_speed` / `neutral_to_brake` / `brake_to_neutral` |

`wing_initial` **必须有**，其余都能省。全库实测最小组合就是
`wing_initial` + `wing_up` + `wing_down`（2 台车这么干）；
甚至只做 `pivot_up` / `pivot_down` 的也有 14 台。

### 4.3 帧范围参考（原厂实测）

| 车 | 片段 | 帧 |
| --- | --- | --- |
| Aston Martin One-77 | `wing_up` | 0→30 |
| Lamborghini Reventon | `wing_up` / `wing_down` | 0→45 / 45→0 |
| Jaguar CX-75 | `wing_up` | 0→75 |
| Porsche 918 Spyder | `wing_up` | 0→90 |
| Bugatti Veyron SS | `wing_up` / `wing_down` | 150→330 / 330→150 |
| Mercedes SLR 722 | `neutral_to_speed` / `speed_to_brake` | 0→10 / 10→30 |

注意 Veyron 那种 `150→330` 的写法：帧号不是从 0 开始，是**全局时间轴上的位置**。
照抄原厂值最安全。

## 5. 任务 D：加一台全新的车（端到端）

**用时**：1 小时（含部署验证）。**产出**：游戏里多出一台可以选、可以开、可以改漆的车。

### 5.1 准备

你需要两个路径：

| 路径 | 是什么 | 例 |
| --- | --- | --- |
| `depot` | 原版解包出的 `.depot` 目录 | `E:\...\files\.depot` |
| `pkg` | 解包出的 `files` 目录（`.depot` 的父级） | `E:\...\files` |

`depot` 里要有 `vehicles/data/`（六张表 + 540 个 spec）和 `vehicles/`（车目录）。

### 5.2 选 donor

donor 就是"抄哪台车"。规则只有一条：

> **必须选一个有 appearance 记录的车。**

540 个 spec 里 63 个没有 appearance 记录（F1 系列、NASCAR 涂装车、少数概念车），
它们的车目录也不存在 —— 选了会在 `build_spec` 阶段报
`appearance_id == 0` 失败。

安全的选择：`2012_lexus_lfa`、`2013_ferrari_laferrari`、`2017_ford_gt` 这类
主流量产车。测试脚本默认用 `2012_lexus_lfa`。

### 5.3 跑插件

*Car ▸ Build a new car*，填：

| 字段 | 填什么 |
| --- | --- |
| `Depot folder` | 上面那个 `depot` |
| `Package folder` | 上面那个 `pkg` |
| `Output folder` | 空目录，会生成 `files/` 镜像 |
| `Donor car` | 例如 `2012_lexus_lfa` |
| `New name` | `<年份>_<厂牌>_<型号>`，例 `2026_my_brand_gt` |
| `New car id` | 留 0 = 自动取下一个空闲 id |
| `Body .m3g` | 想用自己做的车身就填（可选） |
| `Active aero` | 要不要自动空力 |
| `Donor aliases` | **保持勾选** |

点 OK，日志会写进 Text 编辑器里的 `rr3_build_car`：

```
  shared      : livery string table + default livery copied
  spec        : 611_2026_my_brand_gt.bin.nct (appearance 564, aero on)
  cardesc     : 541 entries
  suspension  : 541 x 140 bytes
  damage      : 541 x 116 bytes
  appearances : 541 records, id 564
  liveries    : 6 schemes, wing->body on 5
  folder      : 55 files, 6 aliases
  registry    : ...
  data list   : ...
```

### 5.4 它写了什么（10 个产物）

输出目录是**游戏 `files/` 的镜像**，可以直接推：

```
<out>/.depot/vehicles/data/611_2026_my_brand_gt.bin.nct    ← spec
<out>/.depot/vehicles/data/cardesc.list.nct                ← +1 行
<out>/.depot/vehicles/data/suspensionbehaviour...nct       ← +1 条 140B
<out>/.depot/vehicles/data/cardamagethresholds...nct       ← +1 条 116B
<out>/.depot/vehicles/data/carappearances...nct            ← +1 条外观块
<out>/.depot/vehicles/data/liveries/2026_my_brand_gt.liveries.bin.nct
<out>/.depot/vehicles/2026_my_brand_gt/                    ← 整个车目录
<out>/.depot/asset_list_base.txtCache.txt                  ← 注册表
<out>/apk/res/asset_list_vehicle_2026_my_brand_gt.txt      ← 车辆清单
<out>/apk/res/asset_list_vehicle_data.txt                  ← 数据清单
```

### 5.5 三条必须知道的坑

**坑 1：donor 命名别名副本不能省。**
贴图名是烘进 `.m3g` 里的。只把文件重命名成新名字，m3g 里写的还是
`2012_lexus_lfa_ext.dxt.dds.z`，引擎找不到 → **全车洋红**。
所以每个含新名字的文件都要在**同一目录**再放一份 donor 原名的副本。
`livery/` 子目录里的 `_ext_*.dxt.dds.z` 特别容易漏（旧版就漏了，
导致 6 个别名只生成了 6 个而不是 12 个）。

**坑 2：空力开关必须原地替换。**
见 [4.1 第 6 步](#41-步骤)。

**坑 3：尾翼材质是 donor 克隆唯一继承不到的东西。**
donor 没有尾翼零件，它的 livery 表里就没有 `LOD_A_WING_REAR_mm_ext` 这一行。
不补的话引擎退回 `car_flat`（纯黑高光）→ 尾翼发暗。
插件自动把 `745`（尾翼）指向和 `30`（车身）相同的材质，跟随每个涂装的车漆。

### 5.6 推到设备上

镜像做好后推到模拟器/真机。目标路径：

```
/storage/emulated/0/Android/data/com.ea.games.r3_rra/files
```

要推的东西（12 个文件 + 1 个目录）：

| 本地 | 设备 | 权限 |
| --- | --- | --- |
| `data/611_<name>.bin.nct` | `.depot/vehicles/data/` | 644 |
| `data/cardesc.list.nct` | `.depot/vehicles/data/` | 644 |
| `data/suspensionbehaviour.suspensiondata.nct` | 同上 | 644 |
| `data/cardamagethresholds.damage.nct` | 同上 | 644 |
| `data/carappearances.appearances.nct` | 同上 | 644 |
| `data/liveries/<name>.liveries.bin.nct` | `.depot/vehicles/data/liveries/` | 644 |

| `asset_list_vehicle_data.txt` | `apk/res/` | **444 只读** |
| `apk_res/asset_list_base.txt` | `apk/res/` | **444 只读** |

- 先 `adb root`，再 `chown 10041:1078`（`10041` 是 app uid，`1078` 是 `ext_data_rw` 组）。

- 六张原版表推之前先备份。还原时要把属主改回 `0:1078`、权限 `770`。
- 参考实现：`analysis/newcar_deploy.py`，四个命令 `push` / `boot` / `check` / `restore`。

## 6. 任务 E：改某个零件的材质

**用时**：1 分钟。**产出**：改好的 `<车>.liveries.bin.nct`。

### 6.1 最常用：让尾翼跟随车漆

*Car ▸ Set part material*：

| 字段 | 填 |
| --- | --- |
| `Depot folder` | depot 路径 |
| `Car` | 车目录名，例 `2012_lexus_lfa` |
| `Part` | `LOD_A_WING_REAR_mm_ext` |
| `Copy the body paint instead` | **勾上** |

勾了 `Copy the body paint` 就不用填材质名 —— 插件会逐涂装地把尾翼设成
和车身一样的材质。

### 6.2 指定材质

不勾 `Copy the body paint`，`Material` 填材质名，例 `car_paint_matte`。
完整名单用 *Reference ▸ Material / part catalog* 查（297 个材质，
其中车漆类 41 个）。

> 车漆类里 `car_paint_*` 有 36 个，另外 5 个（`car_body_plastic` / `car_gloss` /
> `car_matte` / `car_matte_doublesided` / `car_rotor_low`）的 application 也是
> `appCarPaint`，所以"41"不等于"36 种漆"。

### 6.3 查现在用的是什么

*Car ▸ Audit part materials*。它会读场景里所有名字带 `_mm_` 的网格，
逐个报出**最终材质**和**来源层级**：

```
=== 2012_lexus_lfa ===
  LOD_A_BODY_mm_ext          slot    30  -> car_paint_metallic_white      paint
  LOD_A_WING_REAR_mm_ext     slot   745  -> car_paint_metallic_white      paint
  LOD_A_TYRE_mm_tyre         slot   639  -> tyrewall                       default
  LOD_A_NOT_REAL_mm_ext      slot     -  -> car_flat                      no-slot
```

| 层级 | 含义 | 好坏 |
| --- | --- | --- |
| `paint` | 涂装级覆盖，跟随每个涂装 | **最好** |
| `car` | 本车表②，全车固定 | 可接受 |
| `default` | `default.liveries.bin.nct` 兜底 | 通用光泽漆，不跟车漆 |
| `none` | 该车没有这条涂装 | — |
| `no-slot` | 部件名在槽位表里查不到 | **永远无法上漆** |

三级回退顺序就是从上往下。只落到 `default` 时尾翼是"通用光泽漆"，
不跟随车漆 —— 这就是历史上"尾翼发暗"的根因。

### 6.4 上不了漆的 8 个名字

`LOD_A_INT_GLASS_CRACKED_FRONT_01` / `_02` / `_03` / `_04`、
`LOD_A_INT_HAND_GEAR`、`LOD_A_INT_HAND_STEER`、`add`、`projected_lights`。

它们没有 `_mm_` 标签，在 `liveryStringTable` 里查不到槽位。别白费力气。

### 6.5 换涂装：把游戏材质整套导进来

上面的 `Set part material` 是**改数据**（写回 `.liveries.bin.nct`，进游戏才生效）。
如果只是想在 Blender 里**看到**每套涂装长什么样，用这条：

1. *Import ▸ Whole car (folder)*，把 `materials` 从 `simple` 改成 **`Game materials`**；
   想默认显示某一套涂装就填 `paint`（0 起，`-1` = 第一套）；
2. 导入后选中车身网格，*Car ▸ **Switch paint scheme***，`Paint scheme` 填预设号（0 起）。

它会做三件事：

- 走游戏的链路 `网格名 → 涂装表部件槽 → 材质槽 → materials.bin 着色器`；
- **每个网格仍然只有一个材质槽**（和游戏一致），槽里的材质内部按涂装分
  **预设**：每个预设一套 `Principled BSDF`（`bsdf_0`、`bsdf_1`…）+ 该涂装的
  贴图节点（`atlas_0`…）+ 两条色带节点，**只有当前预设的 BSDF 连到
  Material Output**。切涂装只是换一根连线，不会增加材质槽；
- Base Color 用该涂装的 `<车名>_ext_<颜色>` 贴图，Roughness / Metallic / Coat
  由游戏的双镜面叶瓣和 fresnel 色带换算，**Specular Tint = 游戏值 ÷ 255**
  （游戏存 0–255 字节，直接写会让高光放大 255 倍、整车像镀铬）。

**不是每个部件都有多预设**：只有涂装表真的覆盖到的部件才需要切换。轮胎、轮毂、
刹车盘、底盘这些槽在任何涂装下都不变（P1 的 `LOD_A_TYRE` / `LOD_A_WHEEL` 的
`overridden_by` 是空的），所以只给 1 套预设，`rr3_paint_slots = 1`，
对它们按 *Switch paint scheme* 是空操作。实测 P1 83 个网格里 20 个有 6 套、63 个只有 1 套；
Huayra 103 个里 18 / 85。

**但 `_mm_cab` 内饰面板有时也跟着涂装变**。全库 379 台多涂装车、1903 个 `_mm_cab` 网格里，
有 49 个在不同涂装下解析出不同贴图（机制是涂装表的 **texture override**，不是材质覆盖）。
典型是 `2013_bugatti_veyron_gsv`：`LOD_A_BODY_mm_cab` 的 6 套预设分别用
`cab.png` / `cab_chrome.png` / `cab_orange.png`。这些网格会照常拿到多预设。

**窗户 / 轮胎 / 刹车盘 / 底盘的贴图来自 `vehicles/common`**：车自己的涂装表里往往
没有那一行（全库 540 台车里 `ext_tyre` 缺 153 台、`ext_rotor` 155、`ext_windows` 90、
`ext_chassis` 540 全部），只有 `default.liveries.bin.nct` 才有。取贴图按
**涂装覆盖 → 车表 → default 表**三级回退，所以这些部件现在也有图了。

| 车的例子 | 涂装数 | 车身网格的槽 / 预设 |
| --- | --- | --- |
| `2014_mclaren_p1` | 6（黄/黑/蓝/橙/银/白） | 1 槽 / 6 预设，材质 `car_paint_gloss` 与 `car_paint_metallic_cool` 混用 |
| `2012_lexus_lfa` | 6 | 1 槽 / 6 预设 |
| `2011_pagani_huayra` | 6 | 1 槽 / 6 预设（银是金属漆，带清漆层） |
| `2013_bugatti_veyron_gsv` | 6 | 1 槽 / 6 预设，`_mm_cab` 内饰面板也跟着变 |

> 注意：同一台车的不同涂装可以用**不同的材质模板**——P1 的蓝色涂装是
> `car_paint_metallic_cool`（Roughness 0.447、带清漆层），黄色是 `car_paint_gloss`
> （Roughness 0.045、无清漆层）。所以换涂装不只是换贴图。
>
> 两条色带（`ramp_fresnel` / `ramp_specular`）以**未连线**的贴图节点留在预设里，
> 想自己接就接。细节和全部实测数字见 `docs/游戏材质与涂装.md`。

### 6.6 损伤件单独成组

车身文件里每个板件都同时有**完好版和撞毁版**：`DOOR_LEFT` 与 `DOOR_LEFT_DAMAGE`，
玻璃和灯罩另有 `*_BROKEN_*`（`GLASS_BROKEN_REAR`、`HEADLIGHT_LENS_BROKEN_A_LEFT`…）。
两者位置完全重合，一起显示就会看着像穿模。

导入时 `separate_damage`（默认开）会把撞毁的那些放进
`<车名>_LOD<X>_damaged` 子集合，完好件留在主集合，对象带 `rr3_damaged = True`。
实测 `2014_mclaren_p1` 的损伤集合 24 个对象、`2013_bugatti_veyron_gsv` 29 个、
`2012_lexus_lfa` 22 个。想看撞毁状态就把主集合里的同名件隐藏、只留损伤集合。
判定只看基名里有没有 `DAMAGE` / `BROKEN`（`_mm_` 之前的部分）。

### 6.7 贴图：导出、加载、为什么会"看不见"

游戏里的贴图不是普通图片，是几种私有容器：

| 后缀 | 是什么 | 数量 |
| --- | --- | --- |
| `.dxt.dds.z` | zlib 压的 DDS，车辆贴图主力 | 21,446 |
| `.dxt.dds.z.bin` | 多帧阴影图（每帧一段 zlib DDS） | 924 |
| `.dxt.dds.bin` | 多帧阴影图，不压缩 | 2 |
| `.rgb.pvr.z` | zlib 压的 PVR（9 台车的 badges/wheel/misc 只有这个） | 3,229 |

**导成普通图片**：*3D 视图 ▸ N ▸ RR3 ▸ Textures ▸ **Export textures***，
`Source` 选车目录、`Write to` 选输出目录、`Format` 选 `PNG`。
结果会写进 Text Editor 里的 `rr3_textures` 文本块（`N written, N skipped, N failed`）。

**导出的 PNG 会垂直翻转**。游戏把每张图都存成 bottom-up（文件第 0 行是画面最下面一行），
MonkeyTool 的解码器在解压后无条件翻一次，再告诉模型读取器**不要**翻 V
（`loadM3g(..., flipV = false)`）。所以"翻图、不翻 UV"才是配套的；我们的 UV 保持文件原样，
只翻图片。代码里是 `texport.FLIP_V = True`，想拿原始行序传 `flip_v=False`。

**直接灌进 Blender**：*Textures ▸ **Load car textures***，选车目录，
把该车所有图集 + 12 条着色器色带都加载成 Blender 图像（色带自动设成 `Non-Color`）。
它会**递归**扫车目录，所以 `<车>/livery/` 里的涂装图集也会进来（平铺 `listdir` 会正好
漏掉换涂装最需要的那几张）；加载前还会**清掉上一版解码**（产物按
`<临时目录>/rr3_dds/v2/` 分版本存），否则同一张图会同时存在正反两份。

**选具体的文件**：*Textures ▸ **Load textures (pick files)***（`rr3.load_texture_files`）
可以一次选一个或多个 `.z/.dds/.pvr/.etc/.atc/.ptc` 文件直接加载，不用管它属于哪台车。
特殊车辆在游戏里用的是专属轮胎贴图、或者图集没写进涂装表时，整台车扫描找不到那些图，
就用这个入口手选。勾 *Treat as data (non-colour)* 会把图像设成 `Non-Color`（给色带用）。

> **为什么以前"贴图没进去"**：导入器其实一直把 DDS 解码成功了（1024×1024、
> 首像素就是涂装色），但 ①每个涂装占一个材质槽，Blender 按 polygon 选槽，
> 你看到的多半是别的槽 ②解码出来的文件放在临时目录，重启 Blender 就变成粉色
> ③`Load car textures` 只扫了车目录根、漏了 `livery/` 子目录 ④旧解码不清理，
> Blender 按路径命中已加载的图像、不重新读盘 —— 看起来就像"从没导入过贴图"。
> 现在改成单槽多预设、递归扫描、按版本清缓存，并且加载后**打包进 .blend**
> （`img.pack()`），重启也在。

> **`materials = Game materials` 找不到材质表**：材质表在 depot 根
> （`materials/materials.bin`、`vehicles/data/liveries/`），插件从车目录向上找 8 层。
> 把车目录单独拷出 depot 后就找不到了，导入会报
> `game materials: cannot find the depot's materials/materials.bin above …`。
> 把导入面板的 **Depot** 参数指到 `.depot` 文件夹即可。
> （早期版本这里静默退回占位材质，看起来像"材质完全没导入"。）

### 6.8 导入驾驶员

驾驶员不在车目录里，在 `<depot>/driver/`：`driver_lod_a.m3g`（15 个部件）、`driver_lod_b.m3g`
（同姿势低模）、`driver_lod_c/d.m3g`（各 1 个网格，腿已在座位里），外加 12 台车的定制版。
动画是 `driver.banim`（通用坐姿）或 `driver_<车>.banim`（36 个按车定制）。

*File ▸ Import ▸ **Real Racing 3 Driver***（`import_scene.rr3_driver`）：

| 参数 | 说明 |
| --- | --- |
| `Depot` | `.depot` 文件夹，留空则从当前 .blend 位置向上找 |
| `Car` | 车目录名（`2013_caterham_seven_620r`）。填了会用它自己的 `driver_lod_c_<车>` 变体，并自动查出该车的 `.bin.nct` 记录 |
| `Car data (.bin.nct)` | **推荐**。该车的 `vehicles/data/<id>_<车>.bin.nct`，里面直接写着这台车用哪个 `driver_<x>.banim`（游戏自己的答案，不用猜名字） |
| `Animation (.banim)` | 手选一个 `.banim`，优先级最高（想给任何车换任何姿势时用） |
| `Driver LOD` | `A` 15 部件（默认）/ `B` 同姿势低模 / `C`·`D` 只有腿 |
| `Skin` | `alesi`、`alonso`、`ferrari`、`raikkonen`… 留空用默认 `driver.dxt.dds.z` |
| `Placement` | `NODE`（默认，每个部件绕自己的关节转，游戏就是这么做的）/ `BONE` / `JOINT` |
| `FPS` | 默认 **90**。源 `.banim` 的键间隔是 11/10/12 ms 循环（约 91 键/秒），按 30 采样会丢掉三分之二，导出回去的动作比游戏的粗 |
| `Mirror the figure` | 默认**关**。它会把每个部件各自镜像（连带换手、把旋转共轭），一般不要用 |
| `Parent to a root empty` | 默认开。建 `<车名>_DRIVER_ROOT`，所有部件挂上去，移动它就能整体搬动 |

**朝向**：根空物体**不做任何旋转**。`.banim` 里的人偶本身就是朝 +Y 的（就是车头方向），
早期版本给根空物体绕 Z 转 180° 想"对齐车头"，结果把人偶转反了 —— 那个开关已经删掉。
根空物体保留，因为它就是用来整体搬动/摆放驾驶员的。

**装配顺序**：先按 `.banim` 在它自己的空间里摆好每个部件 → 把部件挂到 `<车名>_DRIVER_ROOT`。
这样部件保留游戏原始变换，只有根负责整体位置。

**专属 LOD**：`driver_lod_c_<x>.m3g` / `driver_lod_d_<x>.m3g` 只对 12 个有专属动画的车型存在
（`919_lmp1`、`alfa_romeo_155`、`apollo_ie`、`dezirconcept`、`f1412t2`、`f1_mp44`、
`f1_toro_rosso`、`f1f14t`、`ferrari_500_trc`、`lotus_t125`、`mclaren_mp4x`、`porsche_909`）。
导入时**先定动画、再按动画名找网格**，所以引用 `driver_919_lmp1.banim` 的 16 台 LMP1
都会自动拿到 `driver_lod_c_919_lmp1.m3g`，而不是通用模型。

**动画怎么选**（优先级从高到低）：

1. `Animation (.banim)` 手选的；
2. `Car data (.bin.nct)` 里写着的（540 条记录里 **224 条**有这个字段，引用 34 个不同的 `.banim`）；
3. 用车名去猜（`driver_<x>.banim` 的 `<x>` 出现在车名里，最长者胜）；
4. `driver.banim`。

> 猜名字经常猜错，所以才要读记录：`2014_toyota_ts040` → `driver_919_lmp1.banim`、
> `2014_ferrari_f1_f14t` → `driver_laferrari.banim`、
> `2015_ferrari_fxx-k` / `2017_lamborghini_centenario` / `2019_mclaren_senna` →
> `driver_renault_dezirconcept.banim`。这些靠车名一个都猜不到。

导入结果是**一个集合 + 一个根空物体 + 15 个带 action 的部件**（LOD C/D 是 1 个网格、不摆姿态）。
贴图从 `vehicles/common/` 取（`materials.bin` 里没有 `driver` 这个材质，是特判的）。

> **人偶是灰的、没有贴图？** 这是旧版本的 bug，已修。原因是 `.m3g` 的材质表里那 15 个部件的
> 材质就叫 `driver`，导入器先建了一个同名、按名字哈希出假色、没有贴图的材质；旧代码拿到这个
> 已存在的材质就直接复用，贴图节点即使建出来也没连到 `Base Color`。现在 `_driver_material()`
> 会检查"贴图节点存在 + 图片正确 + `Color` 连到了某个 Principled BSDF 的 `Base Color`"，
> 不满足就整棵树重建；材质槽 `link` 强制 `DATA`、polygon 索引归 0。
> 重跑一次导入即可，不需要清场景。

**怎么确认摆对了**：选中 `<车名>_DRIVER_ROOT` 移动，应该整体跟着走；
把驾驶员摆到 `ANCHOR_POINT_DRIVER` 上，左右手应该落在方向盘轮缘附近
（实测 F375 轮缘 0.201 m、左手 0.164 / 右手 0.175 m；Caterham 轮缘 0.125、双手 0.103/0.126）。

> **位置单位**：所有 `.banim`（含 `driver.banim`）都是 **1/65536 米**，不是 1/32768。
> 早期版本把驾驶员按 1/32768 算，人会大一倍（1.69 m 高、0.98 m 宽）。

### 6.9 通用模型：进出都不需要车辆上下文

**导入任意 `.m3g`**：*File ▸ Import ▸ **Real Racing 3 Generic Model***（`import_scene.rr3_m3g_raw`）。
不带锚点、不猜图集、不套车辆模板，只有网格 + 游戏材质名。用来：
自己拿游戏原始的轮胎模型进来量尺寸、跟插件自动缩放的结果对照排错；或者看赛道模型。

| 参数 | 说明 |
| --- | --- |
| `Scale` | 顶点乘数，默认 1.0（`.m3g` 里已经是米，除非那个文件的 `positionScale` 不是 1） |
| `Convert axes` | 默认开，转成 Blender 的 Z-up。**关掉就是文件原始坐标**（游戏自己的数值），比对数值时用这个 |
| `Report sizes` | 默认开，导入后逐个网格打印 `名字 x 宽 y 高 z 深 radius`，半径取 `max(y,z)/2` |

实测 `2012_lexus_lfa_shared.m3g` 的 `LOD_A_TYRE_mm_tyre` 是 `x 0.2247 / y 0.5985 / z 0.5952`，
半径 **0.2992 m**；全库 463 台统计的轮胎网格半径中位是 0.2991（变异系数 0.5%）——
也就是说**模板轮胎的半径在所有车上几乎一样，宽度才是逐车建模的**（宽度中位 0.2493，
变异系数 20%）。这解释了为什么插件的轮子缩放只拉 y/z 不拉 x。

**导出任意 `.m3g`**：*File ▸ Export ▸ **Real Racing 3 Generic Model***（`export_scene.rr3_m3g_raw`）。
不要求模板，`Scale mode` 三档：

| 档 | `positionScale` | 什么时候用 |
| --- | --- | --- |
| `AUTO` | 拟合到 ±1024 raw（约 0.0022） | 车身/零件，和车辆导出器一个做法 |
| `METRES` | **1.0** | 驾驶员、赛道模型 —— 游戏里这两类文件本来就是 1.0 |
| `FIXED` | `0.0021973606199026108` | 替换车零件时想跟出厂值完全一致 |

实测：`driver_lod_a.m3g` / `driver_lod_c.m3g` / `Tracks/Bathurst/processed/high/bathurst.m3g`
的 `positionScale` 都是 **1.0**；`2012_lexus_lfa_a.m3g` 是 **0.00219736062**；
`bathurst_minimap.m3g` 是 0.971518。

> **为什么不能一律用 1.0 导出车零件**：引擎会走慢速顶点路径（卡顿 + 丢高光）。
> 车辆零件必须用 `AUTO` 或 `FIXED`。

**导出驾驶员的 `.banim`**：*File ▸ Export ▸ **Real Racing 3 .banim***，
`Tracks from` 选 **`Tagged parts (drivers, characters)`**。它按每个网格的 `rr3_track`
数字标签排轨道（不是按名字），因为游戏是按索引绑动画的，`00_helmet` 必须留在轨道 0。
实测 `driver_lod_c.m3g` 的 15 个部件导出后是 15 轨、16,110 键、1,978 ms
（源 `driver.banim` 是 16,290 键、1,980 ms）。

## 7. 任务 F：做静态铰链（车门 / 引擎盖）

**用时**：20 分钟。**产出**：改好的 `.points`。

主动空力走 `.banim`，**静态铰链走 `.points`**，两者不共存 ——
实测有 `HINGE_WING_REAR_LEFT/RIGHT` 的 17 台车全是 NASCAR 且全都没有 `_wing.banim`；
有 `_wing.banim` 的 53 台车全部 0 条 WING 铰链。

### 7.1 步骤

1. *Import ▸ Anchors (.points)*，选车目录里的 `<车>.points`。
2. 找到 `HINGE_*` 空物体（例如 `HINGE_DOOR_LEFT`）。
   它们的自定义属性：
   - `rr3_point_type` = 2（hinge）
   - `rr3_orientation` = 9 个 float 的旋转矩阵
3. 改位置 / 旋转。**注意锚点基不是 Blender 基**：导入时做了 `Rot180Z`，
   导出时会再乘一次 `Rot180Z` 转回去。你不用管，插件自动处理。
4. *Export ▸ Anchors (.points)*，`Only tagged` 保持勾选。
5. 导出前会跑校验，问题逐条报 WARNING。

> **工程里存了两份锚点怎么办**：一个 .blend 里同时放着两台车的 `.points` 空物体
> （或者同一台车的原始版和改过的版本）时，**全导出会把它们混成一个文件**。
> 这时候用 *Export ▸ **Selected anchors (.points)*** —— 它和上面那个是同一个 operator，
> 只是把 `Selected empties only` 预先勾上了；选中你要的那一组再点它即可。
> 这个开关本来就在文件浏览器的侧栏里（`Selected empties only`），只是很容易漏看，
> 所以面板上单独给了一个按钮。
>
> 选了但选中的不是空物体（比如只选了车身网格）时，导出会**直接报错停下**，
> 不会退回"导出整个场景"——那是这个开关存在的唯一原因，悄悄退回等于毁掉另一份锚点。

### 7.2 引擎认识的锚点名

79 个硬点名（37 个 `POINT_` + 42 个 `HINGE_`），存在
`re/lib/libRealRacing3.so` 的 `0x01EEB458..0x01EEB6C8` 连续 79×8 字节槽里，
**槽索引就是引擎内部 id**（例：6 = `POINT_STEERING_WHEEL`，
57 = `HINGE_STEERING_WHEEL`）。

名字必须是这 79 个之一，否则引擎不认。完整表见参考手册第 5 章。

前缀匹配规则：`POINT_HEADLIGHT_LEFT_01..09` 都会映射到 `POINT_HEADLIGHT_LEFT`
（去掉尾部数字和下划线后匹配）。

## 8. 排查表：出问题先看这里

| 症状 | 原因 | 解决 |
| --- | --- | --- |
| 菜单里看不到"导入模型/整车" | 旧版只注册了 6 个类 | 升级到 2.0；或自检 `classes` 元组有 16 项 |
| 全车洋红 | 贴图名烘在 m3g 里，找不到 | 补 donor 命名别名副本（见 5.5 坑 1） |
| 尾翼发暗 / 纯黑 | livery 表缺该零件行，退回 `car_flat` | 用 *Set part material* 勾 `Copy the body paint` |
| 零件纯黑但车身正常 | 零件名不在槽位表里 | 改用参考手册里的合法部件名 |
| 导出后扫描线卡顿、高光没了 | `Position scale` 是 1.0 | 重导，填 0（用模板值） |
| 游戏启动崩在 `+0x18` | spec 里插入了 token 而不是原地替换 | 只做原地替换，不插字节 |
| 游戏里没有这台车 | 注册表 / 数据清单没更新 | 重跑 *Build a new car*，确认 10 个产物都在 |
| 资源清单报 `ASSET DOWNLOAD ERROR` | `asset_list_*` 格式错或权限不对 | 检查 `chmod 444`，检查清单行数 |
| 关键帧导出来全是同一个数 | 直接读了对象当前姿态而不是逐帧求值 | 插件已修（`_pose_at` 会 `frame_set`）；自己写脚本要注意 |
| 尾翼角度差 90° | 用了网格基做共轭 | 必须用动画基：`rot_bl = anim @ rot @ anim.transposed()` |
| `Action` 没有 `fcurves` 属性 | Blender 4.4+ 改成 slotted action | 插件已兼容；自己写脚本要走 `layers[*].strips[*].channelbags[*].fcurves` |
| 读 `gametext.txt` 是乱码 | 它是另一套密钥的密文 | 用 `nct.crypt(data, KEY_GAMETEXT, 211)`，不是默认的 `nct.read` |
| `appearance_id` 读出来是 0 | 该车确实没有 appearance 记录（63 台） | 换 donor；这不是 bug |
| 改完 spec 后其他字段乱了 | 硬编码了 token 索引 | 索引在 84..112 之间浮动，必须按字节形状定位（插件已做） |

### 9.3 三种轮子半径（别混用）

| 定义 | 来源 | 中位值 |
| --- | --- | --- |
| 自由半径 | `suspensiondata` 浮点 21/22 ÷ 2 | 0.345 / 0.360 m |
| 加载半径 | `carappearances` 外观块 f1/f5 | 0.328 / 0.336 m |
| 轮心高度 | `.points` 的 `POINT_WHEEL_*` y | 0.323 m |
| **模板网格半径** | `_shared.m3g` 的 `LOD_A_TYRE_mm_tyre` | **0.2993 m（几乎恒定）** |

加载半径 = 自由半径 × 0.9498（低 5.0%）。
110 台车的轮心高都是占位值 0.31903 m。

最后一行的"模板半径"是轮子为什么看起来都一样大的原因：463 台车全部共用一个 0.60 m 的
模板网格，游戏加载时按前三种半径之一把它径向拉伸。详见 `docs/轮毂与轮胎缩放.md`。
