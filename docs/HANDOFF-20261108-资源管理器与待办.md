### 2.3 关键格式事实（这些是逆向出来的，别重复劳动）

- **`.m3g` 里零贴图引用**：贴图全靠涂装表 + 文件名约定在运行时解析。
- **部件名不含年份/品牌/车名**（0 / 162,840），同一套 1869 个名字被 540 台共用。
- **轮子只有左侧**：右侧靠绕竖轴 180°（`x=-x, z=-z`），不是镜像。
- **轮胎半径全库几乎恒定**（CV 0.5%）⇒ **引擎按 nct 里的直径自己缩放**，不要把
  目标尺寸烘进顶点。
- **尾翼轨道↔部件按名字序绑定**，文件里没有轨道号字段（穷举过）。面板可对调。
- **aero 行为 4 种**：`DeployWhenBraking`(35) / `DeployAtSpeed`(11) /
  `BrakeAndSpeedCombo`(7) / `NascarAirBrake`(42)。
- **`_animations.xml` 的帧号不能反推**；33 ms/帧是确定的。
- **PVRTC 页是 gamma 编码的**（γ=2.2），DXT/ETC/ATC 是线性。
- **ETC 块要转置读**（`x = i >> 2, y = i & 3`），否则误差从 2.37 涨到 6.71。
- **`custom.paints.nct` 末尾有 102 字节 `Author:` trailer**，必须原样带回去。
- **清单里每张贴图有 4 个 GPU 家族行，磁盘只解包一套**，缺三行是正常的。
- **`suspensionbehaviour.suspensiondata.nct` 头是 `u32 1` + `u32 540`**，不是
  `u32 count` 开头；每条 140 B = id + 34 float，**float 21/22 是前后轮胎直径**。
- **spec 前 35 个 token 布局在 540 个文件里完全一致**（class=6、weight=9、
  top_speed=10/11、accel=14/15、braking=16/17、grip=18/19、drivetrain=20、
  声浪=21/22/23）；**引擎块与 PR 必须按字节偏移读写**，MonkeyTool 的 token 走法
  只命中 75/540 且读错字段。

更细的格式笔记在 `docs/` 里 40 篇文档中，按需查：
`FORMATS.md`（72 KB，总纲）、`m3g自定义参数.md`、`points-格式.md`、
`appearances-格式.md`、`materials-格式.md`、`livery槽位表与材质名.md`、
`部件名清单.md`（1869 名）、`锚点名清单.md`（142 个锚点）、`UV平铺与贴图.md`。

### 3.4 工作副本从来没镜像过 `vehicles/data` 和 `vehicles/common`（tests 623 → 648）

### 3.5 生涯编辑器：加/删阶段、单改一场比赛（tests 650 → 672）

改一个系列以前只有一条路：`set_events()` 把整个 tier 列表扔掉重建。那会把
**所有 tier id 换新**，而存档或解锁规则可能正指着某个 tier id。所以新增三个函数，
全部**就地改游戏已经在读的那条记录**：

| 函数 | 做什么 | 关键约束 |
| --- | --- | --- |
| `series.add_tier(c, sid)` | 复制**最后一个** tier（继承奖励曲线、banners、flags），index 取 `max+1`，id 取 `max_tier_id()+1` | 其它 tier 的 id 与 index 一个不动 |
| `series.remove_tier(c, sid, tid)` | 删一个 tier，后面的 index 各减 1 保持 0..n-1 | 只剩一个时抛错——**没有 tier 的系列在游戏里是打不开的空菜单** |
| `series.set_event(c, sid, eid, ...)` | 原地改 track / type / laps / fame / reward | `-1` 与空 track = 不动，所以表单只回传用户真的改过的字段 |

- `add_tier` 的 `events` 为空时**连最后一个 tier 的赛事一起复制**（"再来一个一样的"
  通常就是这个意思）。
- `remove_tier` 的"后续 index 减一"是安全的：**全库 1602 个系列的 tier index 都是
  0..n-1 连续，0 例外**。
- 生涯数据规模：**21767 tier / 1602 series / 50374 event**；每个 tier 都有事件，
  每 tier 最多 3 个事件（`{1: 6877, 2: 1173, 3: 13717}`）；`fame` 0–51500、
  `reward` 0–248100。

UI 侧是三个按钮 `Add a tier` / `Remove a tier` / `Change event...` 加表格双击，
`EventDialog` 只回传改动过的字段。

**踩坑**：`EventDialog` 里那条记录**不能存成 `self.event`** —— `QDialog.event()`
是 Qt 的虚函数，用 dict 覆盖它会抛
`TypeError: Error calling Python override of QDialog::event(): 'dict' object is not callable`，
而且报在建窗口标题那一行，看不出真正原因。改叫 `self.source`。

**另一个坑**：`set_event` 是就地改对象，所以测试里想比较"改前改后"必须在调用
**之前**把旧值读出来，否则 `event.laps` 已经被改掉了（我第一次就栽在这儿）。

### 3.6 工作区：撤销不再把整个程序弄瘫（tests 672 → 693）

用户报的一串症状看起来是四五个 bug，其实是**一个 bug 加三个连带缺陷**，全部
源自 `rrmod/workspace.py` 的 `clear()`：

| 症状 | 真正原因 |
| --- | --- |
| 撤销后车辆详情页还留着改了一半的内容 | `app._staged_changed()` 只刷新 Deploy 页，不刷新详情页 |
| 涂装/部件列表被清空、重启也不恢复 | `clear()` 把 `vehicles/data` 删成空目录，`_data_done` 仍是 `True`，下一次 `ensure_car` 直接跳过镜像 |
| Deploy 页"准备"读不到工作区 | `mirrored()` 只判 `os.path.isdir`，空目录也算"已镜像"，于是所有页面都指向这个空工作区 |
| 只有手动删工作区才能恢复 | 删掉目录后 `exists()` 变 False，`ensure()` 才从头重建 |
| 推送过的文件一直在待推列表里 | 没有任何地方记录"这个文件已经上过设备" |

修法：

- **`_has_files(path)`**（模块级新函数）：`os.walk` 找到任意一个文件才返回 True。
  空目录比没有目录更糟——读侧会把它当成"真实但空"的安装。
- **`clear()`** 现在：① 把 `_data_done` / `_common_done` 清成 False ② 用
  `os.walk(topdown=False)` 连**空目录一起 `os.rmdir`**（保留 workspace 根与两个
  manifest 目录）。docstring 里写清了整条 bug 链。
- **`mirrored()`** 改用 `_has_files()`，并且在发现目录空时**顺手把标志也清掉**，
  这样即使标志是脏的也能自愈。
- **`ensure_car()` / `ensure_data()` / `ensure_common()`** 的"已经做过"判断都加
  了 `_has_files()` 兜底，空目录会被重新填满。
- **`_staged_changed()` / `_staged_cleared()` 拆成两个**：前者（每次暂存编辑后）
  只刷 Deploy；后者（撤销/丢弃后）额外调 `cars.refresh_detail()`。**这个区分是必要的**
  ——如果每次暂存都重载详情页，用户正在另一个窗格里填了一半的值会被冲掉。
- **`Workspace.mark_pushed(rels)`** + `pending()` 过滤：推送成功后记下
  `pushed`(md5) / `pushed_bytes` / `pushed_mtime`，`pending()` 跳过"内容仍等于上次
  推送"的行。用 **size + mtime 先做廉价判断**，只有两者都不符才真去算 md5
  （否则每次刷新都要把几个 MB 的 LOD 全哈希一遍，实测 8 ms → 0.7 ms）。文件被
  改动（哪怕只是 touch）就自动回到列表。

**adb 连不上**不是程序的问题：`adb devices` 显示 `emulator-5554  offline`，
`adb kill-server` + `start-server` 就好了。以后先试这个。

#### 3.6.2 尾翼"消失"的真正原因：banim 少了尾块（tests 724 → 729）

用户报：「重新导出 m3g 和 banim，在管理器里构建车辆并配置好 xml，推送，进游戏后尾翼消失。
推送时只看到 4 个文件。」

**推送本身是对的**：4 个文件都在设备上，三本账（注册表 / `asset_list_vehicle_data.txt` /
per-car 清单）的 md5 全部对得上，livery 目录权限也正常。**几何、材质、索引、UV 全部合法。**

真因是 **`.banim` 少了末尾的尾块（trailer）**：

| | 字节数 | 轨道 | 尾块 word |
| --- | --- | --- | --- |
| 推上去的 | 19,520 | 3 | **`[]`** |
| 之前成功的 | 19,536 | 3 | `0xad45c13f, 0x89cef5e4, 0x57529dc8` |

两者**前缀逐字节相同**，差的就是那 16 字节。**全库 53 个 `_wing.banim` 无一例外**
都有 `len(trailer_words) == num_tracks`。引擎读到没有尾块的 clip 会**加载成功然后永不套用**，
部件就停在建模原点——而尾翼是从车身拆出来、原点在翼上的，所以看起来就是"消失"。

**尾块 word 是部件常量，不是哈希。** 我扫了 crc32 / crc32c / adler32 / fnv1 / fnv1a /
djb2 / sdbm / elf / oaat / java / murmur3 / xxh32，对名字的 10 种拼法（带不带 `LOD_A_`、
`AERO_`、`_mm_ext`，ascii 与 utf-16）**命中 0 次**。成立的是这条：轨道数与部件数相等的
**52 台车**里，尾块 word 的**多重集**与下面六个常量的多重集**每次都相等**。

| 部件 | word | 出现车数 |
| --- | --- | --- |
| `WING` | `0x6C8C2CFD` | 10 |
| `WING_REAR` | `0xAD45C13F` | 39 |
| `WING_REAR_LEFT` | `0x4202CB14` | 3 |
| `WING_REAR_RIGHT` | `0x344991DE` | 3 |
| `WING_STRUT` | `0x89CEF5E4` | 13 |
| `WING_STRUT_REAR` | `0x57529DC8` | 16 |

（顺序不保证：有 5 台车的 word 顺序与字母序不同，所以只保证多重集。）

**改法**：`rr3_export.TRAILER_WORDS` + `trailer_words_for(bases)` 按部件名写尾块，
`_synthesize_container()` 补魔数 `0x7F7F7F00` 与普通 variant，**donor 从必填变成可选**。
实测：带 donor 与不带 donor 导出的 LFA 尾翼 banim **逐字节相同**（19,536 B，
md5 `38176db29b51b9da…`）。管理器侧 `anim.read()` 在暂存的 banim 没有尾块时报警，
文案说的是玩家会看到什么（"the wing will look as if it is missing"）而不是字段名。

**顺带排除的一个假线索**：m3g 的 aero 标志（`gap81[17]`）**不是原因**，也不需要。
用户之前确认"完美运行"的那份 `lfa_new.m3g` 四个尾翼网格的标志全是 0。而且它也不是通则：
1,347 个出厂网格有 morph 表但标志为 0，另有 6 台有尾翼 banim 的车 `_mm_ext` 一个标志都没有。
反过来成立的是——**标志为 1 的 83 个网格，尾块一定存在**，所以将来真要写这个标志，
至少要写 `count = 0` 而不是什么都不写。

#### 3.6.3 第 0 期：asset list 归属索引，与"加品牌触发下载"的三个 bug（tests 729 → 749）

用户报：「我尝试添加品牌时游戏触发下载了。然后就是 logo 我不知道为什么添加 png 后管理器仍不显示。
我想删掉新加的品牌，但没有按钮，撤销更改后它把 lfa 的更改也撤销掉了。」

引擎就"磁盘上有这个文件、但没有任何清单提到它"，于是判定资源不完整、去云端要。
logo 不显示是另一条：`rrmod/atlas.py` 的模块级 `_INDEX`/`_PIXELS` 缓存不失效，
且 `BrandsPage._logo_for()` 读的是安装而不是工作副本。撤销把 LFA 一起清掉，是因为
`app.undo_last()` 调的是 `ws.clear()`——整份工作副本。

**归属是函数，不是启发式。** `rr3lib/manifest.py` 新增 `AssetIndex` / `build_asset_index()` /
`owner_of(pkg, path)`：扫 1,236 本账、114,307 条路径耗时 **0.25 s**，**0 条路径出现在两本账里**
（映射唯一）。所以不必落盘缓存，每次启动建一次就够。

**排序规则一条复现 1,227 / 1,233 本账**：四个 GPU 家族
（`.atc.dds.z` / `.dxt.dds.z` / `.etc.dds.z` / `.ptc.pvr.z`）各自成连续块，块内按路径升序，
非纹理行在最前。两个坑：`family_of()` 必须用 `suffix in path` 而不是 `endswith`
（`..._ext_shadows_high.dxt.dds.z.bin` 以 `.bin` 结尾，判错会把 468 本账算成无序）；
插入位置要取同家族的**第一段**（`same[0]`）再 `bisect`，取最后一段会变成 8 本不复现。
剩下 6 本不复现的都是"事后追加"留下的痕迹，内部本身升序，不值得为它们加特例。

**改法**（全部落盘）：

| 位置 | 改动 |
| --- | --- |
| `rr3lib/manifest.py` | `AssetIndex` / `owner_of()` / `list_for()`（按最近父文件夹投票） |
| `rrmod/edit.py` | `_sync_other_list()` 认领新账本；账本不在工作副本时**从安装补种**；车自己目录短路（否则撞 `ManifestError: ... is already listed in`）；`_backup()` 支持 `.absent` 标记 |
| `rrmod/workspace.py` | `ensure_lists()` 镜像全部账本；`capture()` 覆盖 `gui_assets/`；`undo_step()` 按步撤销 |
| `rrmod/deploy.py` | `_other_lists()` 推送时合并任意账本；`following_manifests(root=)` 列出它们 |
| `rrmod/ui/brandsui.py` | `_read_depot()` 读工作副本；`_write()` 逐个文件 `sync_file`；`remove_brand()` |
| `rrmod/ui/app.py` | `undo_last()` 按步撤销，`discard_staged()` 才是清空全部 |

**`.absent` 标记**：编辑前文件不存在时写一个空标记 `<rel>.absent`，撤销时据此删除文件。
没有它，"加一个 banim 再撤销"会把新建的 banim 留在原地——半撤销比不撤销更难查。

**两个实测撞到的硬错误**（已修，别再犯）：`sync_file` 对车自己目录重复 insert 会抛
`ManifestError: /vehicles/<car>/<car>_wing.banim is already listed in asset_list_vehicle_<car>.txt`；
新车目录无人认领会抛 `EditError: no asset list claims ... and none of its folders are listed either`。
同一条短路（`rel_path.startswith(f"/vehicles/{name}/")`）同时解决两个。

**一个更隐蔽的坑**：同一步里同一文件被改多次时，旧 `_backup()` 会用自己的产物覆盖自己的备份，
撤销就把编辑"恢复"了。实测症状是撤销 logo 后 `apk/res/asset_list_gui_assets_core.txt`
仍然暂存着。改成**首次拷贝优先**（`if os.path.isfile(dst) ...: return dst`）后通过。

#### 3.6.4 真机上那三本账是怎么被弄脏的，以及怎么擦干净

第 0 期改完代码之后顺手体检了设备，发现 `Plymouth` 那次加品牌留下的痕迹**还在设备上**：
三个尺寸的 `manufacturer_logos/sprites.android.atlas` 被改过，多出
`sprites_3` / `sprites_1` / `sprites_1` 三张页，而 `asset_list_gui_assets_core.txt`
**一行都没记**（老代码不写这本账），注册表里那三行也还在。于是游戏一边看到三张没登记的页、
一边看到三行指向已删文件的记录。

**修法**（都是只动设备，E 盘一个字节没写）：

| 文件 | 处理 |
| --- | --- |
| 三个 `sprites.android.atlas` | 从安装推回去（安装里的 md5 与 core 账一致） |
| 三张 `sprites_N.rgb.pvr.z` | `rm`，安装里没有它们 |
| `asset_list_gui_assets_core.txt` | 直接用安装那份（365,312 B），**已与设备逐字节相同** |
| `asset_list_base.txtCache.txt` | 以设备原副本为底，删掉那三行、把 14 行 logo 行的 md5 全对齐安装 ⇒ 47,092 行 |

**结果**：`core` 账 3,292 行与安装**完全一致**；注册表 47,092 行 = 安装 47,090 + LFA 的
`_wing.banim` 与 `_animations.xml` 两行（这两个是 mod 自己加的，本来就该在）；
14 行 logo 行的 md5 与安装**全部相等**；`asset_list_vehicle_data.txt` 1,137 行与注册表
逐行一致。启动后 logcat 里 **57 条 `Asset download skipped - all files up to date!`**、
0 条 `Incorrect Asset cache`、0 条 `SIGSEGV`。

**教训**：改 `gui_assets/` 之前一定要先确认 `asset_list_gui_assets_core.txt` 里有没有那行。
`sprites_N.rgb.pvr.z` 的编号是 `max(ids)+1`，删页时**不能**把编号往回缩——atlas 里的
`<pos id="N">` 是绝对引用，缩号会让别的 logo 指到错的页。

#### 3.6.5 第 1 期第一步：历史面板（tests 749 → 776）

第 0 期之前，撤销只有"撤最新那一步"一个动作，而且**看不见**：`_rrmod_backup/`
下的文件夹叫 `20261111-174042-2`，二十步之后没人知道自己站在哪。这一节把那份
已经存在的数据变成能用的东西。

**新模块 `rrmod/history.py`**（纯 Python，不 import Qt，测试因此能无头跑）：

| 函数 | 做什么 |
| --- | --- |
| `dir_for(root)` | 步目录在哪：默认 `<工作副本>/_rrmod_backup`；用户选了别的盘则再拼 `md5(abspath(root))[:10]`，两个安装不会混 |
| `begin(root, title, stamp=)` | 开一步：建目录 + 写 sidecar；同一个 stamp 重复调用是幂等的 |
| `note(root, stamp, rel, size=)` | 记"这一步动了哪个文件" |
| `steps(root)` / `stamps(root)` | 新→旧列出；**没有 sidecar 的老步也能列出**（`files` 为空时从目录扫） |
| `pin(root, stamp, on)` | 钉住 |
| `prune(root, keep=20)` | 超上限丢最旧的，**钉住的跳过**，但仍计入上限 |
| `restore(root, stamps_)` | 按**新→旧**遍历，所以最后写回的是最旧那一步的字节 |
| `drop(root, stamps_)` | 主动忘掉某几步 |

**两个设计决定**：

1. **sidecar 放在步目录旁边**（`<base>/<stamp>.json`），不是里面。`restore_backup()`
   会把步目录里每个文件都拷回工作副本，元数据放里面会被当成杂散文件"恢复"到车上。
2. **`edit._begin()` 只生成名字，不建目录**。`_begin()` 在每个编辑函数开头被调用，
   那时还不知道是哪个工作副本（`root` 是后面才传进来的）——目录与 sidecar 在
   `_backup()` 里建，那是第一个既知道 stamp 又知道 root 的地方。

**`rrmod/edit.py`**：`_backup()` / `backup_before_write()` 改走 `historylib.dir_for()`，
每拷一个文件就 `historylib.note(...)`；`restore_backup(root, stamp, *, base="")` 新增
`base` 参数（历史在别的盘时用）；12 个编辑函数都拿到了标题（"Build 2012_lexus_lfa"、
"Change the paint finish of ..."），`install_pack` 的暂存目录改成 `historylib.scratch(root)`
——**暂存不跟着历史搬家**，它不是历史。

**`rrmod/workspace.py`**：`undo_step()` 变成 `undo_steps(stamps_)` 的薄包装（取最新一步），
新的 `undo_steps` 走 `historylib.restore` + 每个 rel 重算暂存状态 + `historylib.drop`。

**`rrmod/ui/historyui.py`**：`HistoryDock(QDockWidget)`，`setAllowedAreas(Left|Right|Bottom)`，
可以拖出去浮在旁边（实测 `setFloating(True)` → `setFloating(False)` 能来回）。
四列表格（勾选 / 时间 / 做了什么 / 文件数），钉住的步骤整行淡黄；按钮 *Undo these (N)* /
*Pin* / *Forget* / *Tick all* / *Folder...*；底部一行写"副本存在哪、还剩多少空间"，
历史在别的盘时追加一句"每步都是真拷贝"。

**`rrmod/ui/app.py`**：`MainWindow.__init__` 建 dock 并 `hide()`（不打扰）；
`_scanned()` 里 `self.history.attach(self.editor)`；`_staged_changed()` 里 `refresh()`；
File 菜单新增 *History panel*（Ctrl+H，可勾选）与 *Where undo copies are kept...*；
`undo_last()` 改成调新的 `undo_steps([newest])`。

**`rrmod/ui/settings.py`**：新增 `history_dir()` / `set_history_dir()` / `history_keep()` /
`set_history_keep()`。

**测试组 62（+27 条）**：命名步读回、sidecar 位置、钉住不被上限吃掉但仍计数、

#### 3.6.7 第 2 期：共享页的四行账、槽位表追加、推送可撤回（tests 804 → 862）

三件事一起做完了，因为它们是同一个问题的三面：**游戏里"一个资源"往往不是"一个文件"**。

**① `vehicles/common` 的一页 = 四行账 + 一个依赖**

`asset_list_vehicle_common.txt` 是 1,192 行 / 298 个 stem，但按家族分成四段连续块：

```
family 1 (atc.dds)  行 0   .. 298
family 2 (dxt.dds)  行 298 .. 596     ← 磁盘上只有这一族
family 3 (etc.dds)  行 596 .. 894
family 4 (ptc.pvr)  行 894 .. 1192
```

同一个 stem 的四行 **md5 全不相同**（298/298，一个都不共享），所以不能拿 dxt 的哈希填另外三行。
加一页 = 四行各插进自己家族的段里；`edit._sync_common_page()` 就是这么写的，实测 1192 → 1196 行、
四段边界变成 `(1,0,299)(2,299,598)(3,598,897)(4,897,1196)`、+328 B、第二次调用不再写。

**② 依赖项要分清"谁现在用它"和"谁把它带来的"**

- **谁现在用它**：实时扫 540 个 livery 表的 `textures` 与 `Paint.overrides`，0.30–0.38 s，不缓存 ⇒ 永不陈旧。
  实测 6,995 个不同页面，其中 249 个在 `common/`，最忙的是 `common/car_windows_02`（342 台车）。
- **谁带来的**：`deps.json`，加页时记。因为磁盘上没有任何东西记录这件事。

键是**去掉 GPU 后缀的 stem**（`common/car_windows_04` 覆盖四族），因为四行描述一个资源。
`shipped`（是不是游戏自带的）问的是**安装**，靠工作副本的 `pending.json` 找到安装目录——
问工作副本会把一分钟前刚加的页说成"游戏自带"。

只有"非游戏自带 + 没人点名"的页才允许删；仍在用的会按名字拒绝，`force` 留给用户自己判断。

**③ 手工做的网格名要占一个槽位**

引擎查的是**完整网格名**在 `liveryStringTable.bin.nct` 里的位置；没有槽位就没有材质。
槽位是位置，所以唯一安全的改法是**追加**：`SlotTable.append()` / `append_all()`，2,068 → 2,069，+26 B。
实测 `serialize_slot_table(load_slot_table()) == nct.read(path)` 逐字节一致。

**④ 推送前按文件备份，撤回来是后进先出**

整盘 10.43 GB / 48,678 文件，而一台车的 mod 通常 < 30 MB，所以只备份**这次要覆盖的那些文件**——
清单现成（`_plan` + `following_manifests()`），连 asset list 一起存，因为
"文件放回去了但账本还指着它"会让车留在菜单里指向不存在的东西。

`_backup/<id>/` 存字节 + `_before.json`（每个文件的 md5、大小，或 `absent` 表示这次是新建），
`_state.json` 存一个**栈**。两个 mod 改同一个文件时必须倒序卸载，否则中间态谁也认不出来；
顺序不对会拒绝而不是做一半。

| 文件 | 作用 |
|------|------|
| `rrmod/deps.py` | `stem_of` / `scan` / `shipped` / `status` / `orphans` / `report` / `record` / `release` / `drop` |

| `rrmod/ui/deployui.py` | `_refresh_backup` / `undo_push` / `_undone`，Push 时在 worker 线程里 `backup.take` |

**测试组 64 / 65 / 66**（+22 / +8 / +22 条）。踩到的坑：

- 测试里 `root` 在第 63 组已被改成 `editor.for_car(CAR)` 返回的**车目录**，不是安装根；
  第 64 组要用 `MINI` 与 `editor.root`，写错就得到
  `FileNotFoundError: ...\.depot\workspace\87a6240516\.depot\workspace\e54a423db3\apk\res\asset_list_vehicle_common.txt`。

#### 3.6.8 第 2 期的界面：贴图槽换成现成页面、依赖项页（tests 862 → 903）

**换胎/换盘/换内饰不用复制任何文件。** 一个槽位指向的是 `vehicles/common` 里的
一张页面，而那一页本来就在设备上。所以 `edit.set_texture_slot_page(root, name,
slot, page)` 只改 livery 表的一行，不拷图、不重新编码，推送时只推那张表。界面在
Materials → Textures 的第三个按钮 **Use another shipped page...**。

清单按 kind 过滤，因为 298 张页一次性列出来没法用：轮胎槽只给轮胎，内饰槽只给
同一个 `_matNN` 织物。`_kind_of()` 的两条规则是——先看有没有 `_mat` + 两位数字
（内饰八个槽各自成组），否则按首段分 `tyre` / `rotor` / `windows` /
`windows_cracked` / `windows_shattered` / `banner` / `chassis` / `scratch` /
`headlight` / `cloak` / `driver` / `arms`。`banner` 必须在 `windows` 之前判，否则
`car_windows_banner_nascar` 会被当成车窗（41 张而不是 10 张）。

#### 3.6.9 第 3 期：两个程序、`.rr3mod` 包、发布页（tests 903 → 942）

**为什么拆两个程序而不是两个 exe。** 差别只是"哪些标签页可见"。编译两份等于
多占 110 MB，而且每个修复都要改两遍。所以 `rrmod/profile.py` 把十一个页面按
"谁拥有真相"分成两组：

| 程序 | 显示 | 不显示 |
| --- | --- | --- |
| Mod studio | Cars, Career, Brands, Materials, Dependencies, Publish, About | Music, Graphics, Deploy |
| Mod manager | Cars, Music, Graphics, Materials, Dependencies, Deploy, About | Career, Brands, Publish |
| both（默认） | 全部十个 | — |

划分依据：制作台不做设备推送，管理器不改生涯与品牌。`QTabWidget.setTabVisible`
**只是隐藏，不销毁**（Qt 6.11.1 实测支持），所以切档不会打断正在干活的页面，
也不会有页面被建两次。窗口标题跟着换（`RR3 Mod Studio` / `RR3 Mod Manager`），
选择记在 `settings.ini` 的 `profile` 键；命令行 `--studio` / `--manager` /
`--all` 覆盖它（双击快捷方式的人要的是那个程序，不是上次的选择）。

**`.rr3mod` 是 `share.py` 的 zip 加一份会说话的清单。** `rrmod/pack.py`：

```json
{"format": 2, "kind": "car", "name": "2012_lexus_lfa",
 "requires": [{"kind": "driver", "name": "driver_laferrari.banim"}],
 "provides": {"cars": ["2012_lexus_lfa"], "pages": ["vehicles/common/..."]},
 "files": ["vehicles/2012_lexus_lfa/2012_lexus_lfa_a.m3g", "..."]}
```

六种 `kind`：`car` / `pages` / `driver` / `brand` / `career` / `track`。
`check()` 给三个状态：`ready`（已安装且依赖齐全）、`missing`（已安装但缺东西）、
`absent`（还没装）。**旧的 format 1 share 自动当 car 包读**，`base` 变成
`requires`，所以老文件不作废。

**依赖清单是这件事的全部意义。** 一台车缺驾驶员姿势，文件本身不会说，游戏里
只表现为"车里没人"。所以包里写清楚，打开时就能看见缺什么，而不是装完才发现。

**游戏自带的页是依赖，不是文件。** 298 张共享页在每台机器上都有，打进包里只是
让接收方多下几 MB。只有"不是游戏自带"的页才随包走。

**装包是独立的一次点击。** 读包应该免费，装包要改文件，所以它有自己的按钮和
自己的一次撤销步。同一个包装两次写出的字节完全相同（有断言守着）。

**生涯包是合并，不是替换。** 十四个文件被游戏里所有系列共用，替换会把接收方
自己加的系列删掉。包的 note 里明写这一点。

**发布页**（第 8 个标签）是表单不是向导：种类、哪一个、存哪、叫什么、一句话说明，
一屏看完。下半张表是反方向——打开别人发来的包，先看它要什么，再决定装不装。
六种包都实测过（真安装）：

| 种类 | 实测结果 |
| --- | --- |
| car | `1951_ferrari_f1_f375` → 33 文件 3.4 MB，`state=ready`，依赖 car + driver 两条 |
| pages | 两张页 → 2 文件 92 KB，四行账本一起改 |
| driver | `919_lmp1` → 3 文件 73 KB（姿势 + lod_c + lod_d）；`f1_1951` 只有姿势，note 里写明没低模 |
| career | 14 文件 55 MB |
| brand | Ferrari → 3 文件 9 KB（三个尺寸的页） |
| track | 只发自制地图图；游戏自带图直接拒绝 |

**踩过的两个坑**（都在 `publish.py`）：①`_materials_of` 把**槽位 id** 当材质名
写进 `requires`，于是 `1951_ferrari_f1_f375` 报"需要 material 28/35/297"——
livery 表里存的是槽位，要过一遍 `liveryStringTable` 才知道名字 ②驾驶员低模的
文件名是 `driver_lod_c_<x>.m3g`，`<x>` 前面**没有第二个 `driver_`**，而姿势是
`driver_<x>.banim`，两种拼法都要试。另外 `pack.upgrade()` 忘了把 `format` 抬到 2，
导致升级后的包每次读都被当成 format 1 重新升级（依赖清单被覆盖）。

**`Task` 的信号名是 `fail` 不是 `failed`，`parent` 必须写关键字**（
`Task(fn, parent=self)`），否则父对象被当成位置参数传给 `*args`。


#### 3.6.10 第 4 期：自制材质，复制一个块而不是改一个字段（tests 942 → 970）

`materials.bin` 的结构早就知道（`u32 key + u32 len + payload`，5,887 条记录），
但一直没敢写，因为它**没有长度前缀**：错一个字节，后面每一条记录都错位，而游戏
不会报错，只会加载一张"看起来合理"的错表。这一期找到的写法是**只在表尾追加整块**：

```
记录 0..7        默认行（instance/template/application/cull/blend/primitive/stencil/rgba）
记录 8..4386     材质表，297 个块（第一个记录是 K_TWOSIDED，296 个有名字）
记录 4386..      着色器表，186 个块（第一条是 K_SHADER 'flat_colour'）
```

- **切块判据**：每个块的第一条记录都是 `K_TWOSIDED`（297/297），所以
  `starts = [j for j,(k,_v) in enumerate(recs) if k == K_TWOSIDED]`。
- **块长只有两种**：14 条记录 68 个 / 15 条 228 个（第 15 条是 `K_FLAGS`），
  外加一个 6 条的无名块（记录 4380..4386，是着色器表的默认行，不是材质）。
- **克隆**：`clone_block()` 逐条复制整个块，只换 `K_INSTANCE`（名字），可选换
  `K_TEMPLATE`（换着色器绑定）、换 `K_RGBA` / `K_FLAGS`。**application / cull /
  blend / stencil / flags 必须一起复制**，否则新名字不是那个 template 的实例，
  `shader_for()` 查不到东西。
- **追加**：`insert_block()` 把新块接在材质表末尾（`spans[-1][1]` 处），所有既有
  偏移不动，着色器表位置不动。实测 `car_paint_matte` 的副本 **292 字节**，
  135,065 → 135,357 B，`load()` 后 297 材质 / 186 shader 全部可读、副本与原版

  车的 livery 行都指不到它。`add_material()` 末尾自动 `add_slot_names()`，

#### 3.6.11 驾驶员姿势：字段在数据记录里，不在 spec 里（tests 970 → 993）

一个车用哪个驾驶员姿势，不在 spec 里，而在**车的数据记录**
（`vehicles/data/<id>_<car>.bin.nct`）里——就是那份同时存着 `CAR_NAME_`、
别名、展示名的记录。`rr3lib/driver.py` 原来靠"扫全文件找 `driver*.banim`"能
读到 224/540，但**读不全也没法写**。

**定位规则：`CAR_NAME_` 字符串之后第 13 个 token。**
记录是自描述 token 流（`u32 长度前缀 + 内容` 或裸 `u32`），所以：

- 从 `raw.find(b"CAR_NAME_")` 找到键，读它前面的长度前缀，从字符串末尾开始走
  **12 个 token**，第 13 个的长度前缀就是该字段。
- **必须逐 token 走，不能按固定字节偏移**：中间夹的东西形状不固定
  （`nnnnnnnnnnnn` 108 条 / `ssnnnnnnnnnn` 52 / `snnnnnnnnnnn` 51 / `nnnnnnnnnn` 1）。
- 33 条记录的 `CAR_NAME_` 本身不是可识别 token（长度前缀被读成数字），所以
  用 `raw.find()` 而不是 tokenizer 定位。
- 9 条记录（如 `322_2018_bm​w_m6_gt3.bin.nct`）的字段被朴素 tokenizer 折进一个
  "数字"里，逐 token 走仍然正确。

**540/540 全部命中，与旧扫描法 0 分歧**：命名 224 / 空 316 / 读不出 0。
**空字段不是故障**：它表示这车没有专属姿势、游戏回落 `driver.banim`。
所以 `field_in_record()` 返回三态：字符串 = 有、`""` = 确实没有、`None` = 读不了。

**依赖问题（这就是用户 m24405 说过的那个）**：记录里点名的 33 个姿势中只有
**12 个**有配套低模 `driver_lod_c_<x>.m3g`，另外 24 个用通用
`driver_lod_c.m3g` 演一个"没人给它建模"的姿势。游戏能跑，只是从外面看不对劲，
所以**界面必须说出来**而不是拒绝：`set_driver_pose()` 返回 `low_poly`（有就是
那个路径，没有就是 `""`），动画页分两段文案。

**写**：`rr3lib/driver.set_field(path, name)` —— `""` 清空；拒非 `.banim` 后缀、
拒非 ASCII；**保留原加密状态**（`nctlib.looks_encrypted()` → 写回时用同一个
`encrypt`）；拼接是 `plain[:at] + pack("<I", len) + raw + plain[at+4+old_len:]`，
记录是自描述流所以移位安全。LFA 副本改完再清空，**874 字节逐字节还原**。

**`driver/` 不镜像**：64 文件 / 3.2 MB，没有任何车编辑会写它，所以
`edit._driver_dir(root)` 优先工作副本、否则回落到安装，**返回 depot 根**（因为
`rr3lib.driver` 的所有读取函数都接 depot 再拼 `driver`）。

**界面**：动画页 `Aero` 段下面新增「Driver pose」段——一个下拉（第一项固定
`The generic driver.banim` 对应空值，后面 35 个姿势）、一行"Pose: xxx"、一行低模
说明。改完必须 `self._collect()`（否则文件不进暂存列表）。

**测试组 72（23 条）**：安装有 36 个姿势、工作副本借用安装的 `driver/` 且没复制、
LFA 没有专属姿势、下拉首项是通用项、记录能找到、能写能读回、没低模的姿势如实说、
重复写不变、有低模的姿势给出路径、三种坏输入被拒、清空后**记录逐字节还原**、
暂存里有那份记录、面板显示当前姿势且 36 项、首项是空值、文案含姿势名、真安装
540 条记录**全部有该字段且 0 条读不出**、命名数 > 200。

`libRealRacing3.so` 里，是一张**按事件类型编号索引的数组**：

```
文件偏移 0xae038，每条 24 字节：{pointer, 0x403, name_pointer}
索引即事件类型号
```

按顺序读出来是：

```
 0 Elimination   1 Head 2 Head    2 Cup          3 Unknown Type
 4 Endurance     5 Unknown Type   6 Unknown Type 7 Speed Record
 8 Unknown Type  9 Autocross     10 Speedsnap   11 Drag Race
12 Hunter       13 Time Trial    14 Fuel        15 NASCAR
16 Speed Gate
```

**所以 3、5、6、8 是游戏自己枚举里的空档，不是我们没找到的名字** ——
`type_name()` 现在对这四个返回 "the game leaves this one unnamed"。

三条独立佐证（不是只靠这一张表）：

| 类型 | 佐证 |
|---|---|
| 13 Time Trial | 标题含 "Time Trial" 的 434 个系列，里面**只有** type 13 |
| 14 Fuel | 37 个事件的参数块**全部**以 `Fuel:<n>;forceManual` 开头 |
| 9 Autocross | 全生涯唯一一个点名自己模式的 tier：`%S Autocross Throwdown`，3 个 type 9，别无其它 |

MonkeyTool 的 `kRsTypes[] = {2,1,0,4,7,10,11,13}` 与这张表**八条全对**，
这才是"读法安全"而不是"看着像"的依据。旧结论里 8 = Speed snap、3 = Drag race
是错的（3 和 8 在本 depot 里 0 次出现，旧表把 10 的名字安在了 8 上）。

**测试组 75（13 条）**：表里恰好 13 个名字、13 条名字逐条与游戏表一致、四个空档
都写明"游戏没名字"、17 这类没提过的仍回落到 `Type 17`、type 3/5/16/17 的事件
打开即确定**返回 `{}`**（一个字段都不改）、只改圈数只返回 `{'laps': 7}`。

#### 3.6.14 贴花记录也能改了：D2（tests 1043 → 1069）

D1 只读浏览之后，把"改一条记录"接上。能改的是**文件里真有东西的那几个字段**：

| 能改 | 怎么做 |
|---|---|
| 名字键 | `set_decal(root, id, name=b"...")`，只改 `gametext.txt` 查得到的那一段 |
| 分类 | 同一函数，`category=`；对话框里是**可编辑下拉**，可以直接敲一个新键 |
| 画什么 | 字形 ↔ 图片互斥，给一个就清另一个（文件本身就是这么写的：187 条字形、42 条图片，中间没有第三种） |
| 列表位置 | `move_decal(root, id, position)`，顺序就是编辑器里的顺序 |

**不能加形状**：加一个形状要往 `r3_decals.ttf` 里画字形，而"记录在、字形不在"正是这一页
存在的理由。所以新增记录只能复用字体里**已有的**码位，或者指向游戏**已自带**的图片。

三个实现细节值得记住：

1. **码位的两种写法都要保留原样**。148 条写 `0x0029`、81 条写 `)`，都不是规范形式。
   `set_record(..., code_point=...)` 在值没变时**不重写拼写**，否则改个名字会顺带改动
   调用方没要求的字节。
2. **`gametext.txt` 不在工作副本里**（它在 `.depot` 根，没有车编辑会写它，所以没镜像）。
   于是 `rrmod/decals.py` 新增 `_texts(depot, texts=None)`：读不到文本表就返回 `None`，
   行名回落成 `Glyph U+2605` / 图片文件名。**这是本轮抓到的一个真 bug** —— 页面对着
   已有车的工作副本会直接抛 `TextError: no gametext.txt or text_<lang>.txt was given`。
3. **`rows()` 多了一个 `position` 字段**，对话框的"位置"框靠它判断有没有动过。

**测试组 76（26 条）**：改名后**再改回名字，整个文件逐字节还原**；加一条字形记录再删掉，
同样还原；加一条图片记录再删掉，同样还原；移到第 0 位后顺序真的变了、移回去还原；
四种坏输入（两个都空 / 两个都给 / 图片不在 `vehicles/decals/` 下 / 没有分类）全部被拒；
页面读到 229 行、没选行时只有"添加"可用、选中后三个按钮都亮、对话框打开即确定返回 `{}`、
只改名字只报 `['name']`、页面读的是工作副本不是安装。

#### 3.6.15 画一个新形状：D3（tests 1069 → 1107）

"记录在、字形不在"是这一页存在的理由，所以加形状这件事必须**两个文件一起写**，而且要
一次写完。`edit.add_decal_shape()` 因此把字体和记录放进**同一个撤销步**，并且**先写字
体**——记录写失败时字体只多一个空字形，无害；反过来则是"记录指向一个没画出来的码位"，
正是要报的错。

新模块 `rr3lib/ttf.py`（约 600 行）。`r3_decals.ttf` 实测 **312,380 B / 11 张表 /
`unitsPerEm 2048` / 232 个字形（186 有轮廓、46 空）/ 237 个码位 / cmap 两个 encoding
共享同一个 format 4**。三条设计决定：

1. **没改过的字体原样返回**（`if not font.dirty and font.raw: return font.raw`）。
   编码器自己选 flag 编码方式，重建会产出**不同但等价**的文件，而"等价"不是拿游戏资源去
   赌的东西。
2. **重建时整字体重排、所有 checksum 重算**（`glyf`/`loca`/`hmtx`/`hhea`/`maxp`/`cmap`/
   `head` 七张表都变），因为加一个字形牵动六张表，就地改字节迟早错一处。
3. **`head` 的 checksum 要在 adjustment 字段清零后算**，
   `checkSumAdjustment = 0xB1B0AFBA - 整文件和`，然后再单独更新目录里 head 那一项。

**两个实测抓到的真 bug**（都已修）：

| bug | 症状 | 原因 |
|---|---|---|
| 表头 `shift` 用 `bit_length()-1` | `struct.error: 'H' format requires 0 <= number <= 65535` | 溢出成 16 位；正确写法是 `while entry*2 <= count: entry *= 2; shift += 1` |
| `_build_format4` 的 `idRangeOffset` | U+00A0–U+00B6 等 **23 个码位读成错误字形**（`0xA1` 从 96 变成 161） | `arrays[i] == 0` 与"偏移算出来真是 0"混为一谈；改成 `None` 表示用 delta、整数表示数组位置，偏移用 `range_at + seg_x2 - here + 2*arrays[i]` |

**`hhea.numberOfHMetrics` 必须跟着字形数改**（`struct.pack_into(">H", hhea, 34, len(glyphs))`）
——不改的话新字形的 advance 会被读成上一个字形的 side bearing。修后 **237/237 码位、
0 个轮廓变化、0 个 advance 变化**。

**画图对话框 `rrmod/ui/shapedlg.py`**：`EM = 2048`，七个预设（Square / Circle /
Triangle / Diamond / Star / Arrow / Cross）、`ShapeCanvas`（点一下加点、拖已有点、
双击删点、双击空白新起一个轮廓、y 轴在 `to_screen`/`to_font` 里翻一次）、`fit_contours`
（按最长边缩放并居中）。对话框校验三件事：画得出（每个轮廓 ≥3 点）、码位是数且在
1..0xFFFF、**码位不在字体已用的 237 个里**（写了就覆盖别人正在用的图形）。

**测试组 77（19 条）**：未改动往返**逐字节一致**；加一个字形后**每个码位都在、每个轮廓
不变、每个 advance 不变**；新字形读回且 advance 是给的 1000；加形状后字体变大、记录码位
一致、记录画字形不画图片；删掉后贴花表逐字节还原、码位消失、字形数不变、其余码位画得一
样；空形状与超 BMP 的码位被拒。
**另外 24 条**覆盖对话框本身（预设形状、缩放、居中、对话框校验与 `result_info`）。

#### 3.6.16 把 ETC 与 ATC 也写成编码器（tests 1107 → 1127）

四族贴图里原来只有 DXT 能写，其余三族只能读。可这一台机器的 depot 恰好解包的是 DXT，换一台
Mali 或老 Adreno 的机器就只解 `.etc` 或 `.atc`，那台机器上换一张贴图就没法写了。所以补上
两个块编码器：

| 族 | 块大小 | 编码器 | 对 DXT 副本的平均差 |
|---|---|---|---|
| DXT1/DXT5 | 8/16 B | `rr3lib/ddsencode.py` | 0.84 |
| ETC1 | 8 B | `rr3lib/blockencode.py` | **1.89** |
| ATC RGB | 8 B | `rr3lib/blockencode.py` | **1.04** |
| PVRTC 4bpp | 8 B | 无 | — |

数字是 `gui_assets/960x640/splash/loading/sprites_0` 从自己的 DXT 副本编码再解回来的逐通道
平均绝对差，也就是编码器自己的误差，不是两张不同图的比较。

**PVRTC 不是"还没写编码器"，是另一个问题**：它的块不为自己那 4×4 区域带两个端点，端点是
**跨块双线性插值**出来的，所以改一个块会改到邻居的像素。逐块编码器写出来的文件能解码、能显示、
但样子是错的——那比拒绝更糟。所以 `.ptc.pvr.z` 仍然只读，`build_texture` 会说清理由。

**两个格式细节都是测出来的，不是读出来的**：

1. **ETC 的块内像素序是转置的**：解码器按 `x = i >> 2, y = i & 3` 走，不是通常的
   `x = i & 3, y = i >> 2`。写反了照样解码、只是图躺倒。
2. **ATC 的不是转置的**：它按 `x = i & 3, y = i >> 2` 走。两个格式在这件事上不一致，而两种
   写法都能解出图，所以只有逐像素比对才能抓到。

ETC1 与 ATC 都没有 alpha 通道，游戏的这两族页面也都是纯 RGB，所以 alpha 页**拒绝**而不是
丢掉通道写出去——该镂空的贴花会变成实心。

**测试组 78（20 条）**：两种族的文件头是 DDS、fourcc 是 `ETC `/`ATC `、块体长度对、解回来
尺寸对、逐像素差在上限内、纯色块解回来几乎不变、PVRTC 仍被拒且理由里有 "interpolate"、两种
族都拒绝 alpha 页、管理器认为 `.etc`/`.atc` 可写而 `.ptc` 不可写。

#### 3.6.17 两个 common 文件夹、贴图随包走 PNG、安装时选编码（tests 1127 → 1190）

这一批是用户 m29933 提的七条。核心认识是：**游戏有两个"共享"文件夹，规则一样但内容完全不同**。

| 文件夹 | 谁点名它 | 数量 | 账本 |
|---|---|---|---|
| `vehicles/common` | 540 个 livery 表，按 stem | 298 页 | `asset_list_vehicle_common.txt`（1 本） |
| `Tracks/common` | **没有表** —— 画师自己的绝对路径，存在每张赛道 m3g 里 | 2,313 文件 / 1,290 页 | **19 本** `asset_list_track_common_*.txt`，每个顶层目录一本 |

赛道侧只有靠**正则扫字节**才现实：把 30 个赛道 m3g 当 m3g 解析要 **18.1 s**，在同一批字节里
找 `Tracks/common/...` 只要 **0.52 s**。`track_report` 整体 **0.59 s**。

**赛道页的账本归属不能猜**：`_track_list_for()` 先查归属索引，再向上走父目录投票，都没有就抛
错。一个新子目录会归到它顶层目录那本（`mat/metal/新页` → `asset_list_track_common_mat.txt`）；
连顶层目录都没被任何账本点名的路径**直接拒绝**，因为猜错了游戏就是找不到它。

**贴图随包走 PNG，不带走成品页**。一页在磁盘上是某一族的成品文件，把那个文件发出去等于把
本机的编码塞给别人——Mali 机器上只有 ETC 副本，收到 DXT 会解成噪点。所以：

1. 编辑一页时 `textures.replace()` 顺手把源图拷进 `<工作副本>/_rrmod_source/<页名>.png`；
2. 打包时这张图进 zip 的 `pictures/`，manifest 里列在 `pictures` 下；
3. 安装时按用户选的那一族编码：`auto`（默认，"本安装本来用哪族就用哪族"）、`dxt`、`etc`、`atc`，
   选择记进 `settings.ini` 的 `texture_family`；
4. 没人编辑过的页没有源图，就按原文件走，包会说明哪几页是这种情况。

**缺一页不再拒绝安装**。原来缺任何 requirement 都拦，结果一个被裁过的安装连整台车都装不上，
而那一页往往包本身也不带。现在 `kind == "page"` 只进 `warnings`，其它 kind 仍然拦——一个没有
驾驶员的姿势不是"画得不对"，是坏东西。

**测试组 79/80/81（19 + 18 + 25 条）**：赛道账本四段 runs 与归属；两个 common 的标签页互不
越界；贴图页切 LOD 会跟着换（`car_pages(model=...)`）；`_mm_windows001` 回落到 `ext_windows`
而 `mat00`..`mat07` 保持八张不同的页；包带 PNG 时成品页不进去；按 `etc` 安装出来的文件是真
DDS + `ETC ` fourcc + 解回尺寸对 + 颜色误差 ≤16；缺页只警告且仍可安装。

#### 3.6.18 一张车表，和安装前问一句（tests 1190 → 1200）

第 ⑤ 条有两半，都做完了。

**一半：不再分"原厂车"和"我的 mod"。** 车辆列表原来是三张表（游戏自带 / 我的 / 未管理），
现在是**一张**。理由不是好看：那个区分唯一的用处是"游戏自带的车不许删"，而它靠
`rr3mods.json` 里一份名单判断——名单错了按钮就错了，名单本身又没有任何东西能校验。而删掉一台
原厂车的代价其实很低：文件先拷进 `_rrmod_backup`，重装数据包就能拿回来。所以现在**任何一台车
都能删**，来源只剩详情页里的一个词，以及 *Show* 下拉的三个筛选项（`Cars the game shipped` /
`Cars this program installed` / `Cars it has not decided about`）。

`rr3mods.json` 的 `vanilla` 名单还在（`depotlib` 用它算 `status` 和"被改过"的指纹），但**不再

**另一半：安装前问要不要留副本。** `publish.install()` 新增 `keep=True` 参数，Publish 页在装

选留副本时每个被覆盖的文件先走 `editlib._backup()`，落进历史面板那一步里，于是 **`Undo these`
就能退回去**；选不留时直接写，历史里那一步还在但**空的**——空步比假步好：面板不会给一个退不

## 4. 续做前必须知道的三条设计决定

这三条是用户明确拍板过的，**不要推翻重来**：

1. **文件系统当真相，`car.json` 当建议。** 插件导出时**文件名即槽位**
   （`LOD_A.m3g` / `SHARED.m3g` / `INT_A.m3g` / `wing.banim` / `wing.xml` /
   `car.points` / `car.dashplanes`）；管理器按文件名猜槽位并显示在 17 行表里让
   用户改；`car.json` 只用来补文件名推不出来的 `identity`（年份/品牌/型号/显示
   名），删掉也能用。用户原话：「car.json我不知道它存在的意义何在，尽量让管理器来弄吧」。
   **一个 `.m3g` 只能装一个 LOD 级**，所以导出器现在按网格所在集合
   （`<car>_LOD<X>` / `<car>_shared` / `<car>_int_a`）自己决定文件名
   （`LOD_A.m3g`、`SHARED.m3g`、`INT_A.m3g`、`FRONTEND.m3g`），并**拒绝**一次
   导出跨两个级别的选择（会报 "those meshes span LOD levels B, A"）。导出框里的
   `File name` 下拉可切回"用我打的名字"。`_lod_of` / `_lod_filename` /
   `_lod_mixture` 在 `rr3_blender_addon/__init__.py`。
2. **一切编辑先落工作副本。** `rrmod/workspace.py` 的 `capture()` 用 md5 比对
   工作区与安装，任何差异都 stage 进 `pending.json`；Deploy 页的 Prepare 读它。
   理由：安装只读，且用户要求「推送界面中决定是否要覆盖」。
3. **逆向类的东西先留占位符，不硬啃。** 用户 m16827：「有关逆向的你就先别着急弄
   （很费时间且需要大量测试），留着占位符然后待办清单中保留事项」。

## 6. 常见坑（我踩过的，别再踩）

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| `Failed to start embedded python interpreter!` | 旧构建被 `rmtree` 半删（运行中的程序锁目录但不锁文件） | 只 `os.rename`，见 `tools/build_exe.py` |
| `PermissionError: [WinError 5]` 写 `_rrmod_backup` | 往只读安装里写 | 用 `workspace` / `editor.for_car()`，别写 `inv.root` |
| `TypeError: model_for() got an unexpected keyword` | 插件用的是自带旧 `rr3lib` | 先 `python tools\sync_rr3lib.py` |
| `SpecError: suspension: id 89 already present` | 往迷你安装里加第二张 spec | 别加；测试里改用原厂车 |
| `AttributeError: 'CompletedProcess' object has no attribute 'strip'` | `Device.sh()/su()` 返回 `CompletedProcess` | 取 `.stdout` |
| `AttributeError: 'str' object has no attribute 'decode'` | `mesh data["name"]` 是 `str` 不是 `bytes` | 直接用 |
| `AttributeError: 'Curve' object has no attribute 'keys'` | `banim.Curve` 没有 `.keys` | 键在 `bn.keys[c.start_key]` |
| `AttributeError: 'GfxFile' object has no attribute 'items'` | `GfxFile` 只有 `.values` | 用 `.values` |
| `TypeError: object of type 'int' has no len()` | `series.write()` 返回的 `bytes` 是**整数** | 直接比大小 |
| `UnboundLocalError: animlib` | 函数内又 `from rrmod import anim as animlib` | 删掉函数内 import |
| `dlg.Accepted` → `AttributeError` | PySide6 枚举只在类上 | `QDialog.Accepted` |
| 测试里 `inv.depot` 写到了 E: 盘 | 前面某组把 `inv` 重指向只读真实安装 | 重新 `depotlib.scan(root)` 取 `.depot` |
| 清单推上去车消失 | 用本地旧表覆盖了设备新表 | `deploy.check_table` / `check_career` 守着；表只能从设备拉 |
| `QThread: Destroyed while thread is still running` | 关窗时后台任务还在跑 | `worker.shutdown()` + `wait_all()`，见 `app.closeEvent` |
| i18n 里出现带车名的字符串 | 文案里 f-string 拼了车名 | 改成静态文案（`_fill_paints` / `_fill_clips` 已改） |
| `TypeError: 'NoneType' ... os.path.join` in `pack._driver_exists` | `driver_dir()` 在文件夹不存在时返回 `None` 而不是抛错 | 加 `if not folder: return False` |
| `NameError: editing is not defined` | 测试里用的是 `from rrmod.ui import editing as editinglib` | 用 `editinglib` |
