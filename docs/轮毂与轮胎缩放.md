# 轮毂与轮胎是怎么缩放的

一句话：**游戏里的轮子网格是一个 0.60 m 的通用模板，每台车加载时按自己的数据把它径向拉伸。**
所以你在 Blender 里直接看 `_shared.m3g`，会觉得"所有车的轮子都一样大"——它们确实一样大，
不一样的是引擎在加载时乘上去的那个系数。

这份文档记录系数的来源、实测分布，以及插件怎么复现它。

> ## ⚠️ 2026-11-16 游戏内实测：第 1、3.1 节的结论被推翻
>
> 本文最初是照着 **MonkeyTool 的预览算法**写的（`attachSharedCorners()`），
> 并假定游戏也走同一条路。**实测证明游戏不走。** 详见下面的 §0。
> 第 1 节保留是为了记录"预览器是怎么算的"，**不要拿它当游戏规则**。

---

## 0. 游戏内实测（2026-11-16，Tourbillon mod，已定案）

### 0.1 两次对照实验

只改一个文件、只动一台车（id 611 / 外观记录 564），其余全部不变，进游戏看：

| 实验 | 改动 | 结果 |
|---|---|---|
| A | `suspensionbehaviour` 的 `+4+21*4` / `+4+22*4`：前 0.740→**1.480**、后 0.780→**0.390** | **毫无变化** |
| B | `carappearances` 564 号记录的 `f1`→**0.600**、`f5`→**0.150** | 前轮变巨型轮、后轮变备胎 |

结论：

* **`suspensionbehaviour` 的轮胎直径不是可视缩放旋钮**（它可能只喂物理；
  也可能是引擎根本不读这张表）。以后不要拿它调轮子大小。
* **`carappearances` 记录开头那 8 个 f32 才是。** 引擎绘制的轮胎半径 **就是 `f1`/`f5`**，
  实测 1:1（填 0.600 画出来就是 0.600 m 半径）。

### 0.2 8 个 f32 的真实语义（已定案）

```
+0  f0   前轮  ?            +16  f4   后轮  ?
+4  f1   前轮  轮胎半径 ★   +20  f5   后轮  轮胎半径 ★
+8  f2   前轮  轮辋半径 ★   +24  f6   后轮  轮辋半径 ★
+12 f3   前轮  ?（疑胎宽）  +28  f7   后轮  ?
```

★ = 游戏内改过、看到变化的。

`f2/f6` 的独立验证（166 台有 `_shared.m3g` 的原厂车）：

| 比值 | 中位 | CV |
|---|---|---|
| `f2 / 网格轮辋半径` | **1.0096** | **0.053** |
| `f1 / 网格轮胎半径` | 1.0857 | 0.067 |

CV 只有 5%，说明原厂的共享网格就是照着 `f2` 画的：**引擎把轮辋网格径向拉到 `f2`**。
所以 `f2` 是"轮辋自己的旋钮"，和轮胎半径 `f1` 相互独立。

### 0.3 "轮辋太小 / 轮胎太厚"的真正原因

轮辋和轮胎是**两个独立缩放**，所以两者之间会出现缝隙：

```
轮胎内孔实画半径 = 网格内孔 × (f1 / 网格轮胎半径)
缝隙 = f2 − 轮胎内孔实画半径
```

Tourbillon 修复前后（网格：轮胎 0.3501 / 内孔 0.2780 / 轮辋 0.2843）：

| | f1 胎 | f2 辋 | 内孔实画 | 缝隙 | 观感 |
|---|---|---|---|---|---|
| 抄 Chiron 的块 | 0.3410 | 0.2400 | 0.2708 | **−31 mm** | 轮辋比内孔还小，一圈空隙 → "轮辋小、胎厚" |
| `--fit` 之后 | 0.3595 | 0.2919 | 0.2854 | +6.5 mm | 轮辋贴住胎唇，正常 |

**这就是全部原因**：跟 UV 无关、跟 mesh 无关、跟 `suspensionbehaviour` 无关。
抄别人的外观记录时，`f1` 只差 5% 看不出来，`f2` 却差 16% —— 于是"轮子偏小"的锅一直挂在 UV 上。

### 0.4 正确做法：一条命令

```bash
python work/cars/tourbillon/wheelsize_set.py --fit
```

`--fit` 做两件事：

1. `f1`/`f5` = **`POINT_WHEEL_*` 的 z ÷ 32**（轮心离地高，见 `docs/points-格式.md`）；
2. `f2`/`f6` = **网格轮辋半径 × (f1 / 网格轮胎半径)** —— 保持模型自己的辋/胎比例，
   这样轮辋正好压住胎唇，不会出现空隙也不会穿出胎壁。

`report()` 会为每条轴打印 **辋 − 内孔**，负数就是警告。手工微调用 `--rim F R`（写 f2/f6）、
`--appearance F R`（写 f1/f5）。

### 0.5 两条附带发现

* **刹车盘不跟着缩放**：实验 B 里后轮缩到 ×0.43，刹车盘仍是原尺寸，反而比轮胎还大。
  正常尺寸下（0.2199 < 轮辋 0.2919）看不出来，但极端值下会暴露。盘和卡钳的半径来源**未定**。
* **引擎把轮胎"坐"在地面上**：f1 从 0.341 改成 0.6，轮子变大了但仍然贴地，
  没有出现悬空。所以 `f1` 只是视觉半径，不用管落地。

## 1. MonkeyTool 预览器的做法（**不是**游戏规则）

依据是 MonkeyTool 源码 `src/nfsnl_rr3.cpp` 的 `attachSharedCorners()`（:2581）和
`rr3TyreDiameters()`（:2778）。核心就三行：

```cpp
float radius = rear ? tyreRadiusRear : tyreRadius;   // 模板网格自身的半径
float want   = tyreDiameter ? tyreDiameter[rear ? 1 : 0] : 0.0f;
scale = 0.5f * want / radius;                        // 半径 = 直径 / 2
```

也就是 **`缩放系数 = 这台车轮胎半径 ÷ 模板网格半径`**。

⚠️ 这段是**预览器**的算法：`tyreDiameter` 来自 `suspensionbehaviour`，而 §0.1 的实验
证明游戏不吃那两行——所以预览器算出来的轮子大小和游戏里不一致。留着它是因为
它的**第三条分支**（`scale = 轮心高 / 网格半径`）恰好和 `--fit` 的思路一致，
而且它按角色分配部件、只缩 y/z 的处理方式与游戏一致（§0.5 的刹车盘除外）。

### 优先级（引擎实际的判定顺序）

| 顺序 | 依据 | 条件 | 结果 |
|---|---|---|---|
| 1 | `suspensionbehaviour.suspensiondata` 的轮胎直径 | `0.2 < 直径 < 2.0` | `k = 直径/2 / 网格半径` ← **172 台走这条** |
| 2 | 轮拱贴合 `archRadius()` | 轮拱半径在 `网格半径×0.8 .. ×1.8` | `k = (轮拱半径 − 0.035) / 网格半径` |
| 3 | `POINT_WHEEL_*` 的 y（轮心离地高） | 该值在 `0.5 .. 2.0` 倍的合理范围 | `k = 轮心高 / 网格半径` |
| 4 | 都没有 | — | `k = 1.0`（原样，车会显得轮子偏小） |

源码注释写得很直白：

> the tyre's radius against the point's height above the ground is the scale —
> **1.0 when the shared file was made for this car.**

以及关于"为什么只放大直径"：

> **Only the diameter grows — the width stays as modelled**, so the tyre does not
> push into the suspension.

### 只缩放径向，宽度不动

```cpp
float y = copy.positions[i + 1] * scale;   // 半径方向
float z = copy.positions[i + 2] * scale;
// x（轮宽方向）原样保留
if (rotate) { x = -x; z = -z; }            // 右侧是绕竖轴转 180°，不是镜像
if (scale != 1.0f) {                       // 法线按倒数修正
    copy.normals[i+1] /= scale;
    copy.normals[i+2] /= scale;
}
```

轮子的局部坐标系里，**x 从 0 到 +宽度（x=0 是外侧面/辐条面，+x 朝内朝刹车盘），
y/z 才是那个圆**。所以"径向"= 缩放 y 和 z，x 保持 1.0。

这也解释了为什么不能均匀缩放：均匀放大 1.2 倍会让胎宽也变成 1.2 倍，胎就会顶进悬挂。

## 2. 模板到底有多标准

463 台车有 `_shared.m3g`，全部实测：

| 量 | min | p05 | 中位 | p95 | max | 变异系数 |
|---|---|---|---|---|---|---|
| `LOD_A_TYRE_mm_tyre` 半径 | 0.2940 | 0.2975 | **0.2993** | 0.3009 | 0.3024 | **0.46%** |
| `LOD_A_WHEEL_mm_wheel` 半径 | 0.1590 | — | 0.2292 | — | 0.2594 | 16%（轮辋不标准） |
| 胎宽 | 0.1593 | — | 0.2409 | — | 0.3384 | 26% |

**轮胎半径的变异系数只有 0.46%**——这就是"所有车轮子都一样大"的直接证据：直径固定 0.5986 m。

补充两条反直觉的实测：

- **不是字节级同一个网格**：按几何哈希，TYRE 有 **263 种**不同几何、WHEEL 有 **418 种**。
  也就是说模型确实各画各的，但**尺寸被钉死在 0.60 m**。
- **网格尺寸与真实轮胎尺寸无关**：`corr(网格轮胎半径, 悬挂自由半径) = −0.025`，
  `corr(网格轮辋半径, appearance f0) = +0.041`。确认是模板。

全局轮辋库 `vehicles\wheel.m3g`（7,462 B）也是同一套路：5 个网格
`01_wheel_high` / `02_wheel_low` / `03_brake` / `04_wheel_high_menu` / `05_brake_high`，
直径全为 0.5988，`positionScale = 9.145894182438497e-06`。

## 3. 系数从哪来：两份数据

### 3.1 `suspensionbehaviour.suspensiondata.nct`（172 台有记录，**但游戏不用它画轮子**）

140 字节一条记录，**偏移 4 + 21×4 和 4 + 22×4 两个 f32 = 前/后轮胎直径**（0 基索引 21/22）。

| | 范围 | 中位 | 换算半径 |
|---|---|---|---|
| 前轮直径 | 0.5430 .. 0.7700 | **0.6900** | 0.345 |
| 后轮直径 | 0.5930 .. 0.8000 | **0.7200** | 0.360 |

这是**自由（未加载）半径**，也就是车吊起来时的半径。

### 3.2 appearance 块的前 8 个 float（291 台靠这个）

`carappearances.appearances.nct` 的每条记录，块开头就是 8 个 f32：f0..f3 前轮、f4..f7 后轮。
**12 种块长（234/238/266/268/271/284/301/306/311/316/321/327）里，这 8 个 float 永远在偏移 0。**

实测语义：

| 字段 | 含义 | 证据 |
|---|---|---|
| **f1 / f5** | **引擎绘制的轮胎半径**（1:1） | §0.1 实验 B：填 0.600 画出来就是 0.600；`f1 / 悬挂自由半径` 中位 0.9498、`corr +0.753` |
| f0 / f4 | 未定（**不是**轮辋半径，噪声大） | `f0 / 网格轮辋半径` 中位 1.196；47 台 `f0 > f1` |
| **f2 / f6** | **引擎绘制的轮辋半径**（1:1） | §0.2：`f2 / 网格轮辋半径` 中位 **1.0096**、CV **0.053**（166 台）；游戏内改大 21.6% 轮辋随之变大 |
| f3 / f7 | 未定，疑似胎宽 | `f3 × 2` 换算英寸中位 14.96 |

配对情况：`f1==f5` 229/463、`f2==f6` 353/463、`f3==f7` 154/463、`f0==f4` 128/463。

> ⚠️ **`docs/appearances-格式.md` 有一处旧结论是错的**：那里写"这 8 个量与
> suspensionbehaviour 的轮胎直径无关（相关系数 0.07/0.06）"。实际 f1 与自由半径的
> 相关系数是 **+0.753**，比值中位 0.9498。当年是拿 f1 直接比自由半径（差了 5% 下沉量）
> 且 f0 噪声大才得出无关的结论。该文档把 f0 判为轮辋半径、f1 判为轮胎外半径是对的。

### 3.3 已知脏数据

- **`f0 > f1` 的 47 台**（轮辋比轮胎还大，物理上不可能）：其中 32 台是块长 284 的 F1 车，
  f0 固定 0.36 占位。所以不要用 f0 算半径。
- **`POINT_WHEEL_*` 的 y 有 110/463（24%）是占位值 0.31903**，全是老车
  （1951 Ferrari F1 F375、1959 Porsche 718、1966 Cobra 427、1967 Camaro SS、
  1995 Ferrari F1 412T2、1995 McLaren F1、2002 Enzo…）。用轮心高当半径时必须跳过这个值。
- **`corr(轮心高, 网格轮胎半径) = +0.008`**——轮心高和模板尺寸完全无关，
  它反映的是车本身的大小（`corr(轮心高, 悬挂自由半径) = +0.520`）。

## 4. 插件怎么用它

`rr3lib/wheelsize.py`（纯 Python，不需要 Blender）负责算系数，导入器负责施加。

### 三种模式（`wheel_size` 参数）

| 模式 | 含义 | 系数来源 | 用途 |
|---|---|---|---|
| `engine`（默认） | **和游戏一致** | 悬挂直径 → appearance f1 `/0.95` → 轮心高 → 1.0 | 想让 Blender 里的车和游戏里一模一样 |
| `ground` | **轮胎正好落地** | 轮心高 → appearance f1 → 悬挂 `×0.95` → 1.0 | 做静态渲染/展示图，不要那 5% 陷进地面 |
| `none` | **保持模板** | 1.0 | 想自己手调，或对比"没缩放是什么样" |

`wheel_scale` 是**在 `wheel_size` 之上再乘的手动倍数**（默认 1.0）。

### 两种模式的差别

`engine` 用的是**自由半径**（车吊起来时的半径），车放下来会下沉约 5%，
所以在 Blender 里看会显得"轮子略微陷进地面一点点"。`ground` 用加载半径，轮子正好贴地。

实测三台车两种模式的差：

| 车 | `engine` 前/后 | `ground` 前/后 | 差 |
|---|---|---|---|
| `2012_lexus_lfa` | ×1.190 / ×1.188 | ×1.123 | −5.6% |
| `2018_bugatti_chiron_sport` | ×1.230 / ×1.296 | ×1.133 | −7.8% |
| `2013_caterham_seven_620r` | ×0.908 / ×1.058 | ×0.951 | **+4.7%** |

Caterham 是反的，因为它的轮心高（0.35 m）比自己的自由半径还大——正是 MonkeyTool 注释里
说的 Zenvo 那种情形。所以 `ground` 不保证一定比 `engine` 小，插件里只做合理性夹取
（`0.5 .. 2.0`），不强行排序。

### 全库分布

463 台全部有答案，没有一台落到 1.0：

- 来源：`suspensionbehaviour` **172 台** / `appearance（加载半径 ÷ 0.95）` **291 台**
- 前轮 k：min 0.908 / p05 1.054 / **中位 1.153** / p95 1.234 / max 1.290
- 后轮 k：min 0.924 / p05 1.070 / **中位 1.196** / p95 1.263 / max 1.331

也就是说：**共享网格普遍比真车小 15%–20%**，后轮比前轮再大一点点。
以前手动填 `wheel_scale = 1.10~1.20` 的直觉是对的，只是每台车不一样。

单车轮值样例：

| 车 | 系数（前/后） | 实际直径（前/后） |
|---|---|---|
| Lexus LFA | ×1.190 / ×1.188 | 0.712 / 0.711 m |
| Bugatti Chiron Sport | ×1.230 / ×1.296 | 0.740 / 0.780 m |
| McLaren P1 | ×1.115 / ×1.140 | 0.665 / 0.680 m |
| Ferrari F1 F375 (1951) | ×1.244 / ×1.331 | 0.748 / 0.800 m |
| Caterham 620R | ×0.908 / ×1.058 | 0.543 / 0.633 m |

### 后轮胎的宽度（`rear_tyre_width`）

上面说的系数只管**径向**（y/z）。宽度方向另有问题：有些车后轮比前轮宽，但
`_shared.m3g` 里不一定给了独立的后轮胎网格。

全库 463 台（都有 `_shared.m3g`）的统计：

| 网格 | 数量 |
|---|---|
| `LOD_A_TYRE` | 464 |
| `LOD_A_TYRE_REAR` | **88** |
| `LOD_A_WHEEL` | 463 |
| `LOD_A_WHEEL_REAR` | **149** |
| 同时有 `WHEEL_REAR` + `TYRE_REAR` | **87** |
| 有 `WHEEL_REAR` 但**没有** `TYRE_REAR` | **62** |

有独立 `TYRE_REAR` 的 88 台直接用专用网格（`partslib.wheel_set()` 的
`rear_tyre_own`）。剩下 62 台只有更宽的后轮辋：

- 其中 **53 台**轮辋宽度比 ≈ 1.000，前后一样宽，什么都不用做；
- 只有 **9 台**偏离 1.0 超过 2%：`2021_lamborghini_scv12`(1.262)、
  `2011_pagani_huayra`(1.230)、`2021_pagani_huayra_r`(1.141)、
  `2020_porsche_911_rsr`(0.858)、`2023_porsche_mission_r`(0.952)、
  `2018_porsche_919_hybrid_evo`(0.967)、`2018_mazda_dpi`(0.973)、
  `2023_mclaren_solus_gt`(0.974)、`2006_mercedes_slr_mclaren_722`(0.978)。

对这 9 台按**轮辋宽度比**拉宽后轮胎（只拉 x，与径向 `(1.0,k,k)` 正交）。
这个代理的可靠性有实测支撑：87 台两种网格都有的车，
`|TYRE_REAR/TYRE − WHEEL_REAR/WHEEL|` **中位 0.0060、p90 0.0295**。

Huayra 就是最典型的例子：后轮辋宽 0.2896 m、前轮胎宽只有 0.2336 m，
不处理的话后胎比轮辋**窄 23%**（正是用户报的那个 bug）。
按比例拉宽后 `0.2336 × 1.230 = 0.2873 m` vs 轮辋 0.2896 m，差 0.8 mm。

> **拉宽和右侧转向都会经过 `_build_mesh_object` 的 matrix 分支**，那条分支曾经
> 因为 `tuple(...).normalized()` 抛 `AttributeError` 又被 `except: pass` 吞掉，
> 导致这些网格丢失自定义法线（2026-10-28 修的 Huayra 后胎"法向丢失"）。
> 现在失败会打印 `warning: <网格名>: custom normals dropped (...)`，
> `tools/smoke_wheels.py` 也有两条断言盯着它。

### 刹车盘和卡钳（`brakes`）

引擎对刹车盘和卡钳用的**就是轮胎那个系数**，`attachSharedCorners()` 里同一个
`scale` 变量套在每一类部件上，而且同样只乘 `y`/`z`：

```cpp
case SR_ROTOR:      if (rear && lv.rotorRear) continue; break;   // 会转
case SR_CAL_FL:     if (rear || right) continue; turn = false; break;  // 不转
```

所以插件也是 `(1.0, k, k)`、枢轴同样落在 `POINT_WHEEL_*` 上。唯一区别是**卡钳不跟
轮子转**：四个卡钳各自建模在自己那个角落、盘的后方（`BRAKE_CALIPER_FRONT_LEFT` 的
`x` 是正的、`_FRONT_RIGHT` 是负的），右轮那半圈旋转只作用在轮辋、轮胎和刹车盘上。
卡钳对象带 `rr3_brake_fixed = True`。

**只有 LOD A 和 LOD B 有卡钳和刹车盘**（全库 398–401 台 / 399–401 台），
LOD C 及以下一律为 0。低 LOD 只有轮辋+轮胎是游戏自己的取舍，不是导入漏了。

### 一个例外：LOD F 的轮子是预装配的

全库 463 台车的 `LOD_F` 轮网格都**跨越车身左右两侧**（`x` 从 −0.95 到 +0.95 这种），
`y` 从 0 到一个直径、`z` 覆盖轴距 —— 这是四个轮子已经按真实尺寸摆好的整车网格：

| 车 | LOD F 前/后轮半径 | `.points` 轮心 y | `wheel_size` 拟合半径 |
|---|---|---|---|
| `2012_lexus_lfa` | 0.2982 / 0.2983 | 0.3361 / 0.3416 | 0.3361 / 0.3416 |
| `2011_pagani_huayra` | 0.3340 / 0.3748 | 0.3190 / 0.3190 | 0.3190 / 0.3190 |
| `2018_bugatti_chiron_sport` | 0.3305 / 0.3438 | 0.3410 / 0.3502 | 0.3410 / 0.3502 |
| `2013_caterham_seven_620r` | 0.2847 / 0.3065 | 0.2843 / 0.2810 | 0.2843 / 0.2810 |
| `1962_ferrari_250_gto` | 0.3143 / 0.3143 | 0.3112 / 0.3176 | 0.3112 / 0.3176 |

再缩放或再按 points 平移就是把装配做两遍。所以这一级**完全跳过 `wheel_size`**：
网格挂在一个位于世界原点的 `WHEEL_LODF_ASSEMBLED` 空物体下，`scale` 保持 1、
位置保持 0，对象带 `rr3_pre_assembled = True`，没有 `rr3_wheel_scale`。
（判定条件是"轮网格的 x 跨过 0"：`min(x) < -0.05 && max(x) > 0.05`。）

## 5. 在 Blender 里怎么检查

导入整车后：

1. 选中 `WHEEL_FL` 下面的 `FL_LOD_A_TYRE_mm_tyre`。
2. 看 `N` 面板 → Item → Scale：应该是 `(1.0, k, k)`，**x 恒为 1.0**（除非它是被
   按轮辋比拉宽的后胎，那种情况 x 也会不是 1.0，见上面"后轮胎的宽度"）。
3. 看自定义属性 `rr3_wheel_scale` = 那个 k；后胎被拉宽时还有 `rr3_tyre_widen`。
4. 看 `Dimensions`：y 和 z 应该等于 `0.5986 × k`。
5. 看 `WHEEL_FL` 这个空物体本身：它应该**正好落在 `ANCHOR_POINT_WHEEL_FL` 上**
   （两者位置一致到 0.001 mm）。这就是"先导 points 再装轮子"的验证点。
6. 刹车盘和卡钳（LOD A / B）用**同一个 k**，属性里 `rr3_wheel_scale` 相同；
   卡钳另有 `rr3_brake_fixed = True`，且它的 `Rotation` 应该全是 0
   —— 右轮的半圈旋转不作用在卡钳上。
7. LOD F 是例外：它的轮网格是四个轮子已经装好的整车网格，导入后挂在
   `WHEEL_LODF_ASSEMBLED`（世界原点）下，`Scale` 应为 `(1,1,1)`、`Location` 应为 0，
   属性 `rr3_pre_assembled = True`，而且**没有** `rr3_wheel_scale`。

如果想让某台车单独再大一点，改 `Wheel scale`（它会乘在自动系数上），
不要直接改对象 scale——那会连宽度一起改。

## 7. 还没弄清楚的

- **f3 / f7 的确切含义**：与胎宽、辋宽的相关性都只有 0.12 / 0.19；`f3×2` 换算英寸
  落在 14–16 寸之间但换算不精确。像是轮辋直径，但换算系数对不上。
- **为什么 `f0` 噪声那么大**（p05 0.941、p95 1.658 倍网格轮辋半径）：47 台物理上不可能的值
  说明至少有一批车的块语义和别的不一样（已知 32 台 F1）。块长 284 那一组需要单独建模。
- **`archRadius()` 没实现**：MonkeyTool 用它做"填满轮拱"的兜底，需要车漆顶点的空间搜索。
  我们的 463 台全部能从数据拿到系数，用不上它；但如果哪天遇到数据缺失的车，
  这是唯一剩下的办法。
