# HANDOFF 2026-10-25：导出器改成原厂定点顶点格式

承接 `docs/HANDOFF-20261024.md` 与桌面上的 v36/v37 实验记录。
上一轮已经证明了一件事：**`positionScale = 1.0` 是「扫描线卡顿 + 丢高光」的唯一差异**，
但是用 `analysis/to_fixed_point.py` 事后转换出来的 v37 文件。这一轮把这条规则**内建进导出器**，
以后从 Blender 直接导出就是原厂格式。

## 1. 改了什么

| 文件 | 改动 |
| --- | --- |
| `rr3lib/m3gwrite.py` | 新增 `FACTORY_POSITION_SCALE = 0.0021973606199026108`、`RAW_UNIT_RANGE = 1024.0`、`auto_position_scale(parts)`；`build_file(..., position_scale=None)` 现在把米制坐标换成 `raw = 米 / scale` 再写顶点数组，VB 里写这个 scale。`None` ⇒ 自动 `峰值/1024`。 |
| `rr3_blender_addon/m3gexport.py` | `DEFAULT_POS_SCALE` 改成原厂常量（仅兜底）；`collect_parts(...)` 保持在米制、把系数记进 `part.extra["position_scale"]`；新增 `template_position_scale(per_part)`（取模板里出现最多的非 1.0 系数）；`build` / `build_from_objects` 透传 `position_scale`；顺带删掉一段没用的顶点级解码（原来每个网格算两遍）。 |
| `rr3_blender_addon/__init__.py` | 导出算子 `export_scene.rr3_m3g` 新增 `Position scale`（默认 0 = 自动，`soft_max` 0.01）。 |

| `analysis/build_pkg.py` | 新增正式打包脚本：先把顶层 `rr3lib` 同步进插件目录，再打 `rr3_blender_addon.zip`（14 条目）。 |
| `analysis/_probe_rawextent.py`、`analysis/_probe_va_roles.py` | 新增探针：逐网格 raw 峰值、顶点数组角色统计。 |
| 文档 | `README.md`、`rr3_blender_addon/README.md`（新增「导出 .m3g」一节）、`docs/m3g自定义参数.md`、`docs/自制部件并入车辆-流程.md`、`analysis/to_fixed_point.py`（标注为存量工具）。 |

## 2. 原厂系数（实测，逐 VertexBuffer 读取）

| 车 | `positionScale` | 峰值坐标 | 峰值 raw |
| --- | --- | --- | --- |
| 2012_lexus_lfa | 0.0021973606199026108 | 2.2479 m | 1023 |
| 2007_lamborghini_reventon | 0.0022958945482969284 | 2.3487 m | 1023 |
| 2014_mclaren_p1 | 0.0023481915704905987 | 2.4022 m | 1023 |
| 1951_ferrari_f1_f375 | 0.0019114369060844183 | 1.9554 m | 1023 |

`scale ≈ 峰值/1024`（误差 0.1% 以内），同一台车所有网格共用一个值 —— 所以模板导出直接继承模板的系数，
无模板时才按几何自己算。**永远不写 1.0。**

## 3. 验证结果

`blender -b --factory-startup -P analysis\test_fixedpos_export.py`（4.5.10 LTS 与 5.0.1 都跑过，12/12 通过）：

- 模板导出：Reventón 模板 ⇒ 文件里 `positionScale = 0.0022958945482969284`，世界坐标误差 6.9e-08；
- 无模板：cube ⇒ `scale = 1.9/1024`，raw 峰值 1024.0，坐标误差 5.1e-08；
- LFA 轮转：68 个部件名一致、全部网格 `scale = 0.0021973606199026108`、
  **逐网格 raw 峰值与原厂完全一致（最差 0.00%）**、bbox 最差 1.3e-07、三角数 23 145 一致。

`analysis\test_pkg_fixedpos.py`（隔离 profile 装 zip 再跑算子）：14 条目、装好即用、
算子写出的文件 `scale = 0.0021973606199026108`、材质表只剩被引用的
`Vehicle Exterior_mm_ext`（多写一项引擎会崩）。

## 4. 还剩下的差异

- **顶点不焊接**：LFA 轮转 69 435 顶点 / 2 110 435 B，原厂 17 942 / 728 986 B（三角数相同）。
  上一轮的二分假设是「若扫描线仍卡 ⇒ 顶点数问题」。用户尚未回报 v37 实机结果，
  所以焊接先没做（要做的话是在 `collect_parts` 里按 `(位置, 法向, UV, 颜色)` 去重并重排索引）。
- **原厂每个网格还多一个没有被任何 VB 引用、全 0 的 2×2 顶点数组**（对象表里共 68 个，
  疑似第二套 UV / 光照贴图占位）。我们不写，实测无影响，但没在实机上专门验证过。
- **尾翼发暗**依旧未定位（见 `docs/HANDOFF-20261024.md` 的剩余嫌疑：81 字节块 `byte17` / `byte26`、
  空力件独有的 130/144 字节尾块）。定点格式这条假设本轮已被排除或证实，取决于 v37 的实机结果。

## 5. 下次接手先看

1. 问用户 v37（现已是导出器默认行为）实机两个现象：扫描线还卡不卡、尾翼还暗不暗。
   - 不卡 ⇒ 顶点格式收工，把「焊接」降级为可选项，转去攻尾翼发暗的字节块；
   - 还卡 ⇒ 做焊接（目标 17 942 顶点），再对比文件大小与实机表现。
2. 重新打包只需 `python analysis\build_pkg.py`（会自动同步 `rr3lib`，杜绝插件里跑旧库）。
3. 设备推送仍走 `analysis/push_m3g.py test <file.m3g>`，之后注意属主/权限与热重载。
