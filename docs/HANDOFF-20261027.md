## 1. 本次的核心发现：liveries 文件有 4 张表，之前只解了第 1 张

来源：MonkeyTool `docs/FORMATS.md` §"A liveries list"（即用户提供的 `docs/FORMATS.md`，
md5 `6211FECE3DA3E0C99B79B5A9F2DF5858`），并逐字节实测对上。

```
str  车名
u32  n1, n1 × (u32 slot, str path)          # ① 贴图表
u32  n2, n2 × (u32 meshSlot, u32 matSlot)   # ② 网格 → 材质表          ★ 之前全漏
u32  n3, n3 × (u32, u32, u32)               # ③ 第三张表
u32  n4                                      # ④ 涂装列表
n4 × {
    str 文件名, str 显示名, 8B, str swatch, str logo,
    u8 flag, str arms, str driver, 4B, 3B RGB,
    u32 m, m × (u32 slot, str path)          #    贴图覆盖
    u32 k, k × (u32 meshSlot, u32 matSlot)   #    材质覆盖              ★ 之前全漏
}
```

所有 id 都是 `vehicles/data/liveries/liveryStringTable.bin.nct`（70,134 B，2068 条）的下标。

**表②和"材质覆盖"就是官方的「零件 → 材质」映射**，它决定每个 part 的材质集，
材质集决定引擎绑哪张 LUT（`set=2,binding=2` vs `binding=4`）——这就解释了
`docs/尾翼发暗-着色器取证.md` 里"同一像素着色器、不同 LUT"的现象。

### 1.1 原厂怎么写尾翼材质

- 全库 541 个 liveries 文件里，**只有 10 台车**在表②（全局网格→材质）写了 WING：
  Reventon / Veyron GSV / P1(STRUT) / Regera(STRUT) / F12tdf / ID.R / 911 Turbo S(STRUT) /
  Huayra R / CC850 / Nevera。多数给的是 `car_paint_matte` / `car_matte`。
- **绝大多数车是在每个涂装的「材质覆盖」里按零件覆盖**：全库 25 台车、59 个涂装出现
  `745 LOD_A_WING_REAR_mm_ext`。
- **`745` 的目标材质永远等于同一涂装里 `30 LOD_A_BODY_mm_ext` 的目标**（16 组配对无例外）。
  ⇒ 尾翼漆 = 车身漆是**表里显式写出来的**，不是引擎自动继承。
- **`747 LOD_A_WING_REAR_mm_misc` 全库 0 命中** ⇒ 原厂从不给尾翼的 `_mm_misc` 部分做覆盖
  （那部分本来就是黑塑料/内饰件）。
- 其它尾翼槽：`738/742` = `WING_REAR_LEFT/RIGHT_mm_ext`（21 台车）、`750` =
  `WING_STRUT_REAR_mm_ext`、`753` = `WING_STRUT_mm_ext`、`757` = `WING_mm_ext`。

### 1.2 我们的车为什么发暗

`611` 的 liveries 是从 LFA 原样克隆的；**LFA 原厂车身根本没有 WING 网格**，所以表里
一条 745/747 都没有。我们往 `_a.m3g` 里加了 `LOD_A_WING_REAR_mm_ext` / `_mm_misc` 两个网格，
引擎在 livery 表里查不到 → 退回默认 `car_flat`。

## 6. 同日下午的补充工作：`.points` 全面收官（2026-10-27 11:50）

尾翼问题结案后继续把 `.points` 锚点格式彻底做完，产出新文档 **`docs/points-格式.md`**。
要点（细节全在那份文档里）：

### 6.1 引擎侧 79 条硬点名表找到了

`re/lib/libRealRacing3.so` 的 **`0x01EEB458 .. 0x01EEB6C8`** 是连续 79 个 8 字节槽，
索引就是引擎内部 id（索引 6 = `POINT_STEERING_WHEEL`、57 = `HINGE_STEERING_WHEEL`，
与 FORMATS.md §1372 的 "37 POINT_ + 42 HINGE_" 完全吻合）。

**方法论（之前一直踩的坑）**：`.so` 是 PIE，`.data.rel.ro` 里的字符串指针在文件中是 0，
真值在 `.rela.dyn` 的 `R_AARCH64_RELATIVE` **addend** 里 ⇒ 朴素指针扫描必然 0 命中。
必须用 `analysis/reloc_scan.py`（解析 `.rela.dyn`，151,591 条，取 `info & 0xFFFFFFFF == 1027`）。
这也是当初找 `liveryStringTable.bin.nct`、`car_paint_gloss` 全部失败的原因。

### 6.2 修了解析器的两个真 bug

* **type 1 spline**：`u16 splineCount` + 每条 `(u16 pointCount + pointCount × 3f32)`，
  **没有 flags 字段**。旧代码把第二个 u16 当点数，在"多 spline 且点数不等"的 68 条记录上必然错位。
* **type 3 transform**：`16 × f32` 行主序 4×4，最后一列是平移且 w=1，上 3×3 是纯旋转。
  旧代码当成未知类型。

修完复验：**927 文件（463 个 `.points` + 464 个 `_int.points`）、12,719 条记录、
0 warning、0 trailing bytes、types {0:8334, 1:328, 2:4038, 3:19}**。

### 6.3 尾翼铰链的两条互斥路径（重要）

* 有 `HINGE_WING_REAR_LEFT/RIGHT` 的**正好 17 台，全是 NASCAR，且全部没有 `_wing.banim`**。
* 有 `_wing.banim` 的 **53 台车全部 0 条 WING 铰链**。
* `HINGE_WING_REAR`（无左右）**全库 0 命中**。

⇒ 主动空力走 banim 动画，静态尾翼走 `.points` 铰链。**611 的自定义尾翼不需要任何 `.points` 记录是对的。**

### 6.4 修正了一条旧结论：suspensiondata 的索引偏移 1

旧文档（`docs/进度-车辆外观与轮子尺寸.md`）和 FORMATS.md 都说"轮胎直径在 +22/+23"。
实测 172 台：**0 基索引 21/22 才是前/后轮胎直径**，22/23 会取出 0.017..0.058 这种荒谬值。
按 21/22 取则与 FORMATS.md 自己给的样例逐字吻合
（GT3 RS 0.710/0.720、Megane Trophy R 0.670、Reventón 0.685/0.735、Chiron 0.740/0.780）。
⇒ FORMATS.md 那段是 1.2.10 版本的，14.0.1 上偏移了 1。

### 6.5 轮子"半径"有三个，别混用

| 定义 | 来源 | 中位 |
|---|---|---|
| 自由半径 | suspensiondata floats 21/22 ÷ 2 | 0.349 / 0.363 |
| 加载半径 | `carappearances` 外观块 f1 / f5 | 0.328 / 0.336 |
| 轮心高度 | `.points` 的 `POINT_WHEEL_*` z | 0.319（占位组）/ 随加载半径 |

**加载半径 = 自由半径 − 0.0165..0.0180 m（4.8~5.0%），188 台全部为正** ⇒ 这是轮胎受载下沉，不是噪声。

⚠ 另发现 **107 台车的四轮 z 是完全相同的占位值 0.31903 m**（年份中位 2012，全集 2018）。
`rr3lib/parts.py` 的 `height_offset = 四轮 z 均值` 对这 107 台恰好正确，
对其余 356 台有 6~13 mm 偏差；更准的做法是取外观块 f1/f5（**尚未改代码**，见 §7）。
