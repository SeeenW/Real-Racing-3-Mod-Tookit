## 2. P0：应先修的确定缺陷与安全问题

### 2.1 未知赛事类型在“没有修改”时被改成 type 0

**等级：已复现；优先级最高。**

证据：

- [当前类型表](<D:/rr3/rrmod/series.py#L41-L52>)只列 0–9。
- [EventDialog 初始化](<D:/rr3/rrmod/ui/seriesui.py#L875-L879>)找不到原始类型时执行 `setCurrentIndex(index if index >= 0 else 0)`。
- [result_info](<D:/rr3/rrmod/ui/seriesui.py#L919-L932>)把控件值与原值比较，产生 `{'type': 0}`。
- [编辑事件调用链](<D:/rr3/rrmod/ui/seriesui.py#L650-L683>)会把这个差异传给 `set_event`。

只读 fixture 中，type **10、11、12、13、14、15、99** 打开后直接确定，都返回了错误的类型修改；只修改圈数时也会夹带 type 0。原类型 0、9 不出现该问题。

**修改方向**

1. 遇到表中不存在的数值，动态加入 `未知类型（ID 99，保留原值）`，其 `userData` 必须就是原始整数。
2. 显示标签与实际数值彻底分离，逻辑使用 `currentData()`，不依赖翻译后的文字。
3. 控件初始化后建立正确基线，必要时记录用户是否真正修改过该字段。
4. 只改用户明确修改的字段；不能以“UI 无法表示”作为覆盖原值的理由。
5. 同时检查新增赛事的[类型选择器](<D:/rr3/rrmod/ui/seriesui.py#L1058-L1072>)，不要只修已有赛事弹窗。

**验收**

- 0–15 和未来 ID 99：打开直接确定，`result_info()` 无类型差异；通过实际 UI→逻辑链路保存后，事件原始字节不变。
- 只改圈数，不改变类型、奖励、声望等其他字段。
- 取消不产生修改；中英文切换后仍保留正确数值。
- 新增赛事的默认 type 2 不被破坏；未知项不作为普通“已知玩法”误导用户。

### 2.2 数值控件截断与 uint32 溢出

**等级：合成数据已复现；当前参考包未超这些范围。**

[赛事控件](<D:/rr3/rrmod/ui/seriesui.py#L882-L898>)限制：圈数 0–999、声望 0–1,000,000、奖励 0–5,000,000。底层[赛事格式字段](<D:/rr3/rr3lib/career.py#L227-L272>)为 uint32。

超控件范围的原值会被截断，直接确定即可写回错误数值；奖励 `4294967295` 会产生 `Value 4294967295 exceeds limits of type [signed] "int" (4bytes).` 警告并抛出 `OverflowError`。Qt 的普通 `QSpinBox` 不能因为格式是 uint32 就直接设置上限 `0xFFFFFFFF`。

本参考包实测圈数 0–20、声望 0–51,500、奖励 0–248,100；因此这是**真实格式边界缺陷，而不是声称当前全部赛事已损坏**。

**修改方向**

- 对能用 signed int 表示的原值，初始化前扩展显示范围，不静默截断。
- 对超过 signed int 的合法 uint32，短期显示原始值并只读保留；长期用带严格 uint32 校验的文本输入或专用控件。
- “修改能力有限”与“读入保真”分开：不支持编辑的值也必须原样保存。
- 对其他编辑对话框做相同边界审计，但不要未经验证一次性替换所有控件。

**验收**：普通值、超业务范围值、`2147483647`、`2147483648`、`4294967295` 均能打开；未修改时无差异、不崩溃；非法输入不能提交。

### 2.3 只读扫描会间接尝试写原安装；状态路径可能跨安装共用

**等级：代码确认／结构性风险；不是已证实 E 盘遭到修改。**

- [scan](<D:/rr3/rrmod/depot.py#L583-L593>)默认调用 `load_mods`。
- [状态目录候选及写探针](<D:/rr3/rrmod/depot.py#L279-L340>)首先把原 depot 放进候选目录，`_writable_dir()` 会创建目录、写 `.write_probe` 再删除。
- 部分 APPDATA／用户目录／portable 状态候选没有按安装身份区分；不同安装可能共用一份 `rr3mods.json`。
- [工作区根目录](<D:/rr3/rrmod/workspace.py#L89-L99>)又依赖状态位置，因此不要只修 UI 的某一个调用点。

**修改方向**

1. 分离“只读加载已有状态”和“为持久化选择可写目录”。扫描不应写探针，不应创建状态或工作区。
2. 状态与缓存只能存入应用管理的可写位置；原游戏目录不作为自动写入候选。
3. 按规范化安装路径或明确安装 ID 分区保存状态。迁移旧状态时验证所属安装，不把同名文件直接认作当前安装状态。
4. 没有可写位置时返回明确错误，不回退到原 depot。
5. 测试允许临时指定 state/settings 目录，避免依赖真实 APPDATA。

**验收**

- 在只读安装上扫描、切换页面、浏览赛事／贴花不触发任何创建、写探针或原文件修改。
- 两个不同安装的 Mod 状态互不串用；重启仍能找到各自的工作区。
- 通过拦截文件写操作验证“读路径没有写调用”，不要只检查最终 MD5（写探针创建后删除也属违规）。

## 4. P1：工作区、清单、撤销和界面一致性

### 4.1 根目录字体不在默认镜像／capture 闭包内

[ensure_data](<D:/rr3/rrmod/workspace.py#L353-L393>)会镜像 `custom.*` 数据表，但不会复制 depot 根字体。[默认 capture](<D:/rr3/rrmod/workspace.py#L623-L710>)扫描车辆、data/common、graphics、gui_assets、materials，遗漏根字体。

可复用已有[ensure_rel](<D:/rr3/rrmod/workspace.py#L584-L599>)、[capture_paths](<D:/rr3/rrmod/workspace.py#L783-L798>)及[Editor 包装](<D:/rr3/rrmod/ui/editing.py#L148-L159>)，补 `for_decals()` 或等价的明确资源集合。

注意两套路径语义：workspace 相对路径是 `.depot/r3_decals.ttf`，游戏清单资源路径是 `/r3_decals.ttf`；不能混用。

**推荐**：功能级显式资源闭包，不要用全 depot 遍历兜底。浏览时逐文件优先工作副本、缺失则只读原安装；修改时才镜像必需资源。

### 4.2 generic owner 能同步，不代表撤销／丢弃全链路完整

- [sync_file](<D:/rr3/rrmod/edit.py#L399-L462>)能更新实际 owner、registry、vehicle_data，值得复用。
- [清单识别／重置](<D:/rr3/rrmod/workspace.py#L1023-L1064>)只覆盖 registry、vehicle_data 和 vehicle 类书，没有把 startup 纳入同一集合。
- [clear](<D:/rr3/rrmod/workspace.py#L954-L1020>)会把未识别为清单的 startup 书当普通文件清掉；后续可能重新 seed，所以不是“永远无法恢复”，但流程不完整。
- [设备 other-lists 合并](<D:/rr3/rrmod/deploy.py#L895-L962>)已经按实际 owner 处理 startup 等清单，且能识别一般 `asset_list*.txt`。**不要为新功能另写一套整书覆盖部署。**

**修改方向**

统一清单识别、seed/reset、clear 和事务备份的覆盖范围；基于实际 owner 判断，不把字体塞进 vehicle_data。验收包括首次编辑、undo、discard、clear 后再编辑、重新 seed、导出／部署及设备保留其他 Mod 行。

### 4.3 多文件修改的备份必须覆盖数据与所有清单

[undo helper](<D:/rr3/rrmod/edit.py#L59-L145>)提供会话和修改前备份；但 [sync_file 的 registry／data 保存](<D:/rr3/rrmod/edit.py#L439-L459>)没有替新功能保证完整事务备份。

新增“字形＋记录”操作应：

1. 在内存中计算全部候选字节并解析验证。
2. 开启一个 undo 步骤，备份**当前工作副本状态**及所有可能修改的清单。
3. 再写数据文件、同步清单、capture。
4. 任一环节失败，整组回滚，避免字体成功而数据表失败，或数据恢复而清单没恢复。

不要用事后从原安装补备份替代修改前工作副本备份，否则会丢失同一文件较早的未部署编辑。新增文件还需要记录“原先不存在”的撤销语义。

### 4.4 丢弃／撤销后的共享页面与字体缓存刷新

[当前 staged clear 回调](<D:/rr3/rrmod/ui/app.py#L511-L522>)主要刷新汽车详情。新增贴花页面需刷新记录、字体和预览缓存；同时针对材料、依赖、赛事等共享页检查实际刷新路径，避免内存仍显示已撤回状态。

字体缓存按内容 hash 或可靠修订号索引；切换安装、undo、discard、重载后失效。不要以文件名或 font family 名作为唯一缓存键。

### 4.5 pending 的秒级时间／大小缓存

**等级：结构性风险，尚未专门复现完整 GUI 场景。**

[mark_pushed](<D:/rr3/rrmod/workspace.py#L872-L874>)记录整数秒 mtime；[pending](<D:/rr3/rrmod/workspace.py#L1098-L1100>)在大小和整数 mtime 相同的情况下跳过 MD5。相同秒、相同大小的再次修改存在漏报风险。

建议显式 capture 时使摘要缓存失效，或使用可靠版本号／高精度 mtime 配合 hash，不以秒级时间作为编辑保真的唯一依据。回归用例固定相同 mtime、相同长度但不同内容，必须列为 pending。

另外，[summary 的 seeded_from_device](<D:/rr3/rrmod/workspace.py#L1113>)表达式始终为 False，应在状态确有可靠来源信息后修复；这是低优先级状态显示问题。

## 5. P1：中文界面和测试闭环

### 5.1 profile 菜单用显示文字判身份

[菜单创建／选中逻辑](<D:/rr3/rrmod/ui/app.py#L275-L309>)用 `action.text() == profilelib.label(name)` 判勾选。翻译后前者是中文，后者是英文，选中状态可能丢失。

改为 action 的稳定 `data` 存储 `studio / manager / both`，勾选比较数据，不比较可翻译字符串。验收英文→中文→切换 profile→再切英文，始终恰好选中当前 profile。

### 5.2 翻译 inventory 的“完整”目前不能证明实时覆盖

- [gen_i18n](<D:/rr3/tools/gen_i18n.py#L43-L84>)实例化 SeriesDialog，但没有 EventDialog；默认真实安装扫描还会触及状态探针路径。
- [strings walker](<D:/rr3/rrmod/ui/translate.py#L224-L259>)没有收集树表头，虽然 apply 支持翻译它。
- [i18n 测试](<D:/rr3/tools/test_rrmod.py#L1100-L1217>)主要检查已保存 inventory、翻译缺项及数量；旧 inventory 即使遗漏新弹窗也可能全绿。
- combo 被全局跳过有历史原因：部分代码把 `currentText()` 当数据。不能为了中文化直接全局翻译所有 combo。

**修改方向**

1. 增加 EventDialog、树表头及新页面的实时字符串采集。
2. 采集工具在最小 fixture／无安装环境运行，不扫描真实安装来“生成词条”。

### 6.6 阶段 C：用户确认输入格式与依赖后，追加新轮廓

**推荐输入**：显式闭合轮廓 JSON，包含版本、units／坐标系、fill rule、contours、每点 `x/y/onCurve`，可选 advanceWidth。限制点数、轮廓数、坐标、闭合、退化与空洞方向。可配简单多边形绘制 UI。

**首版不做**：PNG 自动转轮廓、任意 SVG、整字体替换、外部 TTF、non-BMP、通用复合字形／hint 编辑。

SVG 如后续需要，先做明确的 `M/L/Q/Z` 子集；transform 必须解释，拒绝 stroke/text/filter/image/external URL 等未支持元素。C/A 曲线需有误差受控转换，不能静默忽略。

依赖方案：

- **允许新增依赖**：长期优先 fontTools（TTFont／TTGlyphPen），降低表结构和校验维护风险。当前本机／work/pylibs 未安装，必须先获用户确认并验证打包。
- **不新增依赖**：只做面向已验证字体结构的 append-only 专用 writer，严格预检，超范围拒绝。不是通用字体库。

字体策略：保持全部旧 glyph ID／cmap／metrics／旧轮廓；新 glyph 从空闲 gid 追加，码点选择未占用 BMP PUA（如 U+E000 只是候选）。**游戏是否识别新 PUA 与 `glyphText=0xE000` 尚未实测。**

**验收**

- 旧映射、glyph ID、轮廓、metrics 不变。
- 两个 cmap encoding 均能找到新 glyph；loca/glyf 边界、post/maxp/hhea 等一致，整字体 checksum 正确。
- Qt 可预览；font／NCT／sync／capture 分别注入失败，整组回滚。
- 字体和主表是一个 undo 步骤；Prepare／导出确实含字体和正确 owner 清单。
- 不能仅凭“TTF 能被 fontTools 打开”就判为游戏可用。

### 6.7 阶段 D：独立的游戏验收

由用户观察：列表名称／分类、形状比例和空洞、选中后涂装、保存重启、购买／解锁、旧贴花是否不变、撤回是否恢复。PUA、新记录、未知门控字段、纹理贴花预览和包 writer 都保留各自的不确定性。

**工具端写入成功 ≠ 游戏确认成功。** 阶段 C 可交“实验功能”，只有通过这一步才升级为稳定功能。

## 7. 贴花格式技术附录：给实施者的可复核起点

### 7.1 主 NCT 的当前样本结构

解密头为小端 `<II>`：version、count。每条正式记录：

```text
<i id>
4 × (u32 byteLength + ASCII bytes)
    categoryKey, nameKey, glyphText, texturePath
<3I>                     第一项与已有包 ID 相符，其他项未知
(u32 byteLength + ASCII bytes)
<2I4B>                   2 个未知 uint32，4 个 byte 标志
```

第五个字符串本样本为：210 条 `'0'`、18 条 `'172'`、1 条 `'143'`，语义未证；4 个 byte 本样本全部为 1。正式记录精确结束于 byte 34,065，后 162 B 原样保留为 opaque_tail。

`glyphText` 解析必须区分：148 条 `0x...` 用十六进制整数；39 条单字符用 `ord()`。不能把单字符 `'A'` 或 `'1'` 一律按 hex 解释。

实际 14 类：SHAPES 62、ALPHABET 29、FLAGS 27、HALLOWEEN 24、CAYMAN 18、CHRISTMAS 14、PORSCHE 13、STPATRICKSDAY 12、NUMBERS 10、SPONSORS 8、BLM 4、LOVE_WINS 4、GRADIENTS 3、SPECIAL 1。

[追加样例](<E:/DXT_480x320+960x640+2048x1536数据包-Build260716/files/.depot/vehicles/data/custom.decals-add.nct>)为 version 11／count 230，追加一条 ID 275 的 LOVE_WINS 纹理记录，且无主表的 162 B 尾巴。这是结构样例，不是游戏成功证明，也不是应默认改写的主资源。

### 7.2 加密判定不能套文本启发式

复用[nct.crypt](<D:/rr3/rr3lib/nct.py#L71>)；当前固定 RC4 key 为 `a535b3b1e843e7cf`，drop 133。

[looks_encrypted](<D:/rr3/rr3lib/nct.py#L85-L104>)按首 512 B 可打印比例判断，对二进制表不可靠。建议原字节与 crypt 后候选分别做 version/count/长度／完整记录边界校验，记录实际输入加密状态；候选不唯一时明确报歧义，不猜。零编辑往返必须保留原加密状态及全部尾部字节。

### 7.3 TTF 追加必须处理的不止 glyf

当前字体：sfnt `0x00010000`；11 表：OS/2、cmap、gasp、glyf、head、hhea、hmtx、loca、maxp、name、post。

```text
unitsPerEm = 2048
numGlyphs = 232
indexToLocFormat = 1（long loca）
loca = 233 offsets / 932 B，终点 308438
hmtx = 928 B，numOfLongHorMetrics = 232
cmap encodings = (platform 0, encoding 3), (3, 1)
两个 encoding 共享 offset 20 的 format 4 子表，37 segments
post = 2.0，OS/2 = 4
head bbox = (29, -102, 13173, 3362)
hhea ascender = 5628, descender = 0, lineGap = 0
整个字体 uint32 大端校验和 = 0xB1B0AFBA
```

已有坐标和度量并不简单局限在 UPM 框内。新形状先参考同类 donor 的 bbox／advance，不要统一缩到 UPM 就假定游戏效果一致。

需要追加／更新：glyf、loca、hmtx、maxp.numGlyphs 与相关 maxima、head bbox、hhea advance/bearing/extents、post 2.0 名称计数、两个编码共享的新 cmap format 4、各表 checksum、table directory／4-byte alignment、head.checkSumAdjustment；评估 OS/2 范围／度量时避免破坏原值。

原 glyph 为 0 composite 仅代表这个样本。遇到其他版本、未知表、复杂 hint／复合场景，专用 writer 应拒绝或只读，不声称兼容任意 TTF。

### 7.4 owner 与 companion

- 主 NCT 属 vehicle_data；根字体属 startup。新增纹理／其他资源用[owner 索引](<D:/rr3/rr3lib/manifest.py#L384-L449>)实查。

## 11. 稳定性与构建：有价值但次于 P0

### 11.1 Task 取消不等于停止工作

[worker](<D:/rr3/rrmod/ui/worker.py#L68-L87>)的 cancel 主要设置标志，不能中断已经执行的函数；[窗口关闭](<D:/rr3/rrmod/ui/app.py#L984-L987>)等待超时后仍退出存在活跃线程销毁风险。未观察到本次实际崩溃，属结构性风险。

建议耗时函数合作检查 cancel，外部进程有明确可终止生命周期；退出等待使用全局期限而非每个任务各等 30 秒，超时明确反馈，不在后台仍使用对象时直接销毁。回归长任务、取消、失败、关闭；不在 worker 内创建 QWidget。

### 11.2 build_exe 参数与状态迁移
