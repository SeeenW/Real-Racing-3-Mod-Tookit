# 游戏材质与涂装：从 `materials.bin` 到 Blender 材质

插件导入整车时加 `materials = "Game materials"`（API 是 `materials="game"`），
就会按游戏自己的数据给每个网格建**每个涂装一套**的材质，选中网格后用
*Car ▸ Switch paint scheme* 填槽号即可换涂装。

这篇文档记录这条路是怎么走通的、每个数字的出处，以及哪些地方是**换算**而非原值。

---

## 1. 为什么不能直接用 `.m3g` 里的材质名

`.m3g` 里确实有 `T_MATERIAL_LIST`（对象 type 24），但里面只有 **15 条笼统的名字**：

```
Vehicle Exterior_mm_ext      Vehicle Exterior_mm_windows
Vehicle Interior_mm_int      Vehicle Exterior_mm_chassis      ...
```

这些是"渲染批次"的名字，不是游戏材质名。真正的材质名在**共享表**里，
必须走下面这条链：

```
网格名  →  liveryStringTable 的部件槽  →  材质槽（三级优先）  →  材质名  →  materials.bin 的着色器
```

链上每一段的规则都是实测出来的，见下。

---

## 2. 链路第一段：网格名 → 部件槽

`liveryStringTable.bin.nct` 里有 2068 条字符串。`_mm_` 后面的 tag 就是查表的键，
**命名规则是 `ext_<tag>` 优先，然后 `int_<tag>`**：

| 网格名 | tag | 查到的槽 |
|---|---|---|
| `LOD_A_BODY_mm_ext` | `ext` | `ext_ext`（P1 上是 1932） |
| `LOD_A_BODY_mm_badges` | `badges` | `ext_badges`（1935） |
| `LOD_A_BODY_mm_misc` | `misc` | `ext_misc`（1934） |
| `LOD_A_WINDOWS_mm_windows` | `windows` | `ext_windows`（3） |

覆盖率（540 台有 liveries 文件的车）：

| tag | 有槽的车 |
|---|---|
| `badges` `cab` `int` `lights` `misc` `sw` `wheel` `wheel_blur` `ext` | **540 / 540** |
| `windows` | 450 |
| `windows_cracked` | 446 |
| `windows_shattered` | 442 |
| `tyre` | 387 |
| `rotor` | 385 |
| `headlight_glow` | 35 |
| `banner` | 30 |
| `scratches` | 7 |
| `cloak` | 1 |
| `chassis` `taillight_glow` `sidelight_glow` `dash` `dashplanes` | **0** |

⇒ `chassis` / `dash` / `dashplanes` / `*_glow` 这些 tag **在涂装表里根本没有槽**，
所以这些网格拿不到贴图，只有材质参数。这不是导入漏了。

共享轮子网格也有槽：`LOD_A_WHEEL_mm_wheel → 729`、`LOD_A_TYRE_mm_tyre → 639`、
`LOD_A_ROTOR_mm_rotor → 559`、`LOD_A_BRAKE_CALIPER_FRONT_LEFT_mm_misc → 88`、
`LOD_A_WHEEL_REAR_mm_wheel → 707`。

## 3. 链路第二段：部件槽 → 材质槽（三级优先）

`<depot>/vehicles/data/liveries/<车名>.liveries.bin.nct` 里四张表：
`textures`（槽 → 贴图路径）、`materials`（网格槽 → 材质槽）、`extra`、`liveries`（每套涂装）。

取材质槽的顺序（`rr3lib/livery.py` 的 `resolve_material`）：

1. **涂装自己的 override**（`level = "paint"`）——只有部分涂装有；
2. 车的 `materials` 表（`level = "car"`）；
3. `default.liveries.bin.nct`（`level = "default"`）；
4. 都没有就 `None`。

P1 实测：`textures 20 / materials 9 / extra 3 / paints 6`。6 套涂装里**只有第 3 套有
materials override**（69 条网格槽 → 1956/1957），第 4 套有 66 条，其余走车表。

## 4. 链路第三段：材质名 → 着色器 + 色带

`<depot>/materials/materials.bin`（135,065 B 明文）是 `[u32 key][u32 len][ascii]`
的扁平记录流，里面有两类块：

- **297 个材质实例**（137 个模板），字段：`application` / `template` / `cull` /
  `blend` / `primitive` / `stencil` / `rgba` / `flags` / `twosided` / `queue` /
  `priority` / `alpha_test`。字段 key 是硬编码的 u32，例如
  `K_INSTANCE=1875587694`、`K_TEMPLATE=1424680013`、`K_APPLICATION=3133585612`。
- **186 条着色器绑定**：`vsh` / `fsh` / `uniform` 实例 / 贴图槽。

**查绑定必须用 template 名，不是 instance 名**：297 个实例里按 template 查能命中 296 个，
按 instance 名查只有 119 个。

贴图槽语义：

| 槽 | 内容 | 引用次数 |
|---|---|---|
| `[1]` | 漫反射/法线类 | 15 |
| `[2]` | 法线 / spec mask | 38 |
| `[3]` | **fresnel 色带** | 110（96 条唯一） |
| `[4]` | **specular 色带** | 96 |
| `[6]` | 自发光（`car_rotor` 的 `car_rotor_glow.pvr`） | 2 |

### 4.1 色带（LUT）文件在哪、长什么样

绑定里写的是 `vehicles/shaders/fresnel_gloss.pvr`，**磁盘上是
`vehicles/shaders/fresnel_gloss.rgb.pvr`**（`.rgb` 是像素布局中缀）。
`resolve_lut()` 会试原路径再试插 `.rgb` 的路径。

`vehicles/shaders/` 共 72 个文件：`fresnel_*.rgb.pvr` 31 个、`spec_*.rgb.pvr` 41 个。
全部是 **1024×1** 的横向渐变。PVR 头 52 字节、偏移 44 处是 `PVR!`、像素自偏移 52 起紧排：

```
u32 headerSize(52)  u32 height  u32 width  u32 mips  u32 flags  u32 dataSize  u32 bpp
```

实测色带（16 点采样，0..255）：

| 文件 | 采样值 |
|---|---|
| `fresnel_gloss` | 20,23,26,30,34,39,46,53,62,74,95,121,149,176,199,215 |
| `fresnel_metallic` | 24,26,27,29,31,35,41,49,61,79,100,123,147,168,187,200 |
| `fresnel_matte` | 31,32,34,36,38,40,43,45,48,52,55,59,65,75,85,93 |
| `fresnel_chrome` | 117,121,126,133,140,148,156,165,173,182,190,198,205,211,217,221 |
| `fresnel_flat` | **全 0**（4 通道） |
| `spec_gloss` | 全 0，最后一像素 255 |
| `spec_metallic_white` | 0×8, 3,13,26,40,55,68,80,255 |
| `spec_matte` | 0×11, 5,15,25,32 |
| `spec_flat` | 18, 0,…,0, 18 |

`fresnel_flat` 全 0 就是**尾翼发暗**的物证：`car_flat` 绑它，反射项整个是 0。

### 4.2 双镜面叶瓣：光漆和金属漆是反的

每个车漆材质有两个 `SpecularPower`：

| 材质 | `power_base` | `power_top` | fresnel | F0 | F90 | 均值 |
|---|---|---|---|---|---|---|
| `car_paint_gloss` | **1000** | **10** | `fresnel_gloss` | 0.078 | 0.843 | 0.326 |
| `car_paint_metallic_white` / `_cool` / `_warm` / `_spec_orange` | **8** | **1000** | `fresnel_metallic` | 0.094 | 0.784 | 0.318 |
| `car_bumper_paint_gloss` | 1000 | 10 | `fresnel_gloss` | 同上 | | |
| `car_matte` | 15 | 100 | `fresnel_matte` | 0.122 | 0.365 | 0.201 |
| `car_flat` | 1 | 1 | `fresnel_flat`（全 0） | 0 | 0 | 0 |
| `car_glass` | 500 | — | `fresnel_glass` | 0.031 | 0.878 | 0.425 |
| `car_wheels_chrome` | 1000 | 40 | `fresnel_wheel_chrome` | 0.353 | 0.843 | 0.598 |
| `car_lights` | 15 | — | `fresnel_gloss` | 0.078 | 0.843 | 0.326 |
| `car_light_housing` | 30 | 40 | `fresnel_light_housing` | 0.608 | 0.906 | 0.670 |
| `car_tail_light` | 30 | — | `fresnel_tail_light` | 0.078 | 0.502 | 0.255 |
| `car_grill` | 15（template = `car_matte`） | 100 | `fresnel_matte` | 0.122 | 0.365 | 0.201 |
| `car_badge_plastic` | 15 | — | `fresnel_gloss` | | | |
| `car_badge_matte` | 15 | — | `fresnel_matte` | | | |
| `car_rotor` | — | — | `fresnel_rotor` | | | + 槽 6 自发光 |

⇒ **光漆 = base 锐利(1000) / top 宽(10)；金属漆 = base 宽(8) / top 锐利(1000)。**
所以"top 叶瓣锐利 ⇒ 视作清漆层"这个映射有物理依据：金属漆的锐叶瓣是清漆，
光漆的锐叶瓣是漆面本身、宽叶瓣才是清漆。

## 5. 换算成 Principled BSDF

Blender 没有 Blinn-Phong 双叶瓣，只能换算：

| 目标 | 来源 | 公式 / 规则 |
|---|---|---|
| **Roughness** | `mu_MaterialSpecularPower_Base` | `roughness = max(0.02, min(1.0, sqrt(2/(n+2))))` |
| **Metallic** | fresnel 色带均值 | `clamp((mean - 0.35) / 0.40, 0, 1)` |
| **Specular Tint** | `mu_MaterialSpecularColour_Base` | **`c / 255`，再夹到 0..1** |
| **Coat Weight / Coat Roughness** | `mu_MaterialSpecularPower_Top` | 仅当 `top >= 200` 时开 Coat，`Coat Roughness = sqrt(2/(top+2))` |
| **Base Color** | 该涂装的贴图 | 见 §6 |

`roughness = sqrt(2/(n+2))` 是 Blinn-Phong 半向量叶瓣的标准差闭式解：
`n=1000 → 0.045`、`n=8 → 0.45`、`n=1 → 0.82`。实测三档正好对应光漆、金属漆、`car_flat`。

`metallic` 的映射依据：介电清漆的 fresnel 均值约 0.28 → 0；铬约 0.66 → 0.8。

> **`Specular Tint` 一定要除以 255。** 游戏存的是 0–255 的字节
> （`255,255,255`、`512,512,512`、`90,160,209`…），Blender 的 `Specular Tint` 是
> 0..1 的颜色。直接把字节写进去等于把高光放大 255 倍——所有车漆都会变成镜面，
> 车身颜色被高光吃掉，看起来"像镀铬、看不见颜色"。全库 296 个材质里有 **139 个**
> 的分量超过 1.0，说明 0–255 是全局约定而不是个别脏数据。

**两条色带本身也导进材质**：作为**未连线**的 `ShaderNodeTexImage`，放在名为
`ramp_fresnel` / `ramp_specular` 的 `NodeFrame` 里。想自己接就接，不想接也不影响观感。

## 6. 贴图：路径要回退，颜色按涂装

### 6.1 路径

涂装表里的路径是 `.ptc.pvr.z`，磁盘上是 `.dxt.dds.z`，而且**有的带 `livery/` 前缀、
有的不带**。正确解析：

```python
stem = internal[:-len(".ptc.pvr.z")]
for base in (os.path.join(VEH, car, stem), os.path.join(VEH, stem)):
    for ext in (".dxt.dds.z", ".dds.z"):
        if os.path.isfile(base + ext):
            return base + ext
```

`VEH = <depot>/vehicles`。**只查车目录会漏 6925/9971 条；加上 `vehicles/` 根回退后
9248/9971 命中，剩 723 条缺失**（`2017_renault_formula_e_*`、`2016_chevrolet_ss_nascar_*`、
`2016_nissan_altima_v8_supercar_*`、`common/car_windows_banner_nascar_2021` 等未随包发布的车）。
`vehicles/common/` 里有 298 个共享贴图（`car_windows_04`、`car_rotor_05`、
`leather_grey_mat01`、`stitching_red_mat02` 等）。

**但路径解析只是第一层，取哪个槽还要三级回退**：`texture_path_for_tag()` 的顺序是
**涂装 override → 车自己的 `textures` 表 → `default.liveries.bin.nct`**。
第三级是必须的，因为窗户 / 轮胎 / 刹车盘 / 底盘根本不是每台车的美术资源，
车表里通常**没有那一行**。全库 540 台有 livery 文件的车里缺自己那行的数量：

| 槽名 | 缺的台数 | default 表指向 |
|---|---|---|
| `ext_tyre` | **153** | `common/car_tyre_tread.ptc.pvr.z` |
| `ext_rotor` | **155** | `common/car_rotor_00.ptc.pvr.z` |
| `ext_windows` | **90** | `common/car_windows.ptc.pvr.z` |
| `ext_chassis` | **540（全部）** | `common/car_chassis.ptc.pvr.z` |
| `ext_windows_cracked` | — | `common/car_windows_cracked_01.ptc.pvr.z` |
| `ext_windows_shattered` | — | `common/car_windows_shattered.ptc.pvr.z` |

`default.liveries.bin.nct` 的 22 条 texture 行就是这批共享图集（`ext_cloak` / `ext_banner` /
`ext_scratches` / `ext_headlight_glow` / `int_windows*` / `int_mat00..mat07` / `int_banner`）。
少了这一级，那 153 台车的轮胎、155 台的刹车盘、90 台的玻璃就完全没有贴图 ——
看起来就是"材质/贴图没导入"。实测改后 4 台车（P1 / Veyron GSV / Huayra / LFA）
**0 个网格缺贴图**。

`_load_car_textures()` 也会把这批 common 图集一起载进 `bpy.data.images`，
但只载 `default` 表真正引用到的那些，不是把 298 个文件全扫一遍。

### 6.2 颜色

车身漆（tag = `ext`）用**该涂装自己的** `<车名>_ext_<颜色>.dxt.dds.z`。
P1 有 6 张：`black` / `blue` / `orange` / `silver` / `white` / `yellow`，88–110 KB。
其余 tag 用对应的图集（`misc` / `lights` / `badges` / `wheel` …）。

贴图格式实测：`<车>_ext_<颜色>` = **DXT1 1024×1024 / 11 级 mip**；
`<车>_misc` = **DXT5 1024×1024 / 11 级**；`<车>_lights` = **DXT1 512×512 / 10 级**。

UV 是 4×4 tile 空间（`UV_SCALE = 0.25`、`UV_FLIP_V = True`）。实测 P1 车身
`raw u[0.12,3.97] v[-2.98,0.97] → Blender u[0.03,0.99] v[0.01,1.00]`，范围正常；
但 `misc` 网格是 `u[-1.04,1.17]`，**超出 0..1**，所以贴图节点必须是 `extension="REPEAT"`。

### 6.3 贴图要垂直翻转（图片翻，UV 不动）

游戏存的图是 **bottom-up**：文件第 0 行是画面的**最下面**一行。MonkeyTool 的做法是
解码时翻一次、然后告诉模型读取器**不要**翻 V：

```cpp
// nfsnl_image.cpp:1100 —— decodeImageAuto() 里无条件
flipImageVertically(out);
// 注释："Real Racing 3's DDS files are bottom-up too ... so everything is
//        turned over here."
// nfsnl.h:530
Model loadM3g(const uint8_t* data, size_t len, bool flipV = false);   // 默认不翻
```

`nfsnl_rr3.cpp:1765-1789` 的 UV 导出也印证了这对搭配——它写的是
"V runs from 0 down to -1 in the file, and the textures are stored bottom-up,
so the export value is 1 + v: that puts the map the right way up against the
flipped texture."

所以正确组合是 **图片翻转 + UV 按文件原样**。我们的 UV 变换
（`v' = (1-v)/4`）本身是对的，缺的只是**把图片翻过来**：

```python
# rr3lib/texport.py
FLIP_V = True

def flip_rows(width, height, channels, pixels) -> bytes:
    stride = width * channels
    out = bytearray(len(pixels))
    for y in range(height):
        src = (height - 1 - y) * stride
        out[y * stride:(y + 1) * stride] = pixels[src:src + stride]
    return bytes(out)
```

`export_png(..., flip_v=None)` 默认按 `FLIP_V` 翻；传 `flip_v=False` 拿原始行序。
导入器 `_image_for_path()` **所有容器统一走 `texport.export` 出 PNG**（包括普通的
`.dds.z`），这样翻转对每种容器都生效，不再依赖 Blender 自己的 DDS 解码。

## 7. 一个材质槽 = 一套涂装预设

导入时（`materials="game"`）：

1. 读这台车的涂装表，拿到 `N` 套涂装（P1 / LFA / Huayra 都是 6 套）；
2. 对每个网格 × 每套涂装解析出材质名、贴图、roughness、metallic、coat；
3. **每个网格只保留一个材质槽**——和游戏一致（游戏里一个网格就是一个材质实例，
   换涂装换的是实例里的参数，不是槽数）。涂装活在这个材质的**预设**里：
   - `preset_<n>`（`NodeFrame`）装着 `bsdf_<n>` + `atlas_<n>` + `ramp_fresnel_<n>` + `ramp_specular_<n>`；
   - **只有当前预设的 BSDF 连到 Material Output**，其余预设静默；
4. 材质名 `<车名>_<游戏材质名>`；各涂装参数不同的加 `_paint` 后缀；
5. 网格对象写 `rr3_paint_slots`（共几套）、`rr3_paint_slot`（当前第几套）、
   `rr3_paint_presets`（名字表）；材质写 `rr3_presets` / `rr3_preset_names` / `rr3_preset_active`。

### 7.0 只有真正会变的部件才有多预设

**涂装表说了算**：一套涂装只有在它的 `materials` override 表里出现了某个网格槽，
那个网格才需要多预设。P1 实测：

```
paint 01   materials 0    texture overrides 2
paint 02   materials 0    texture overrides 2
paint 03   materials 73   texture overrides 2
paint 04   materials 73   texture overrides 2
paint 05   materials 73   texture overrides 2
paint 06   materials 0    texture overrides 2

LOD_A_BODY_mm_ext      part_slot=30   overridden_by=[03, 04, 05]
LOD_A_TYRE_mm_tyre     part_slot=639  overridden_by=[]      ← 轮胎
LOD_A_WHEEL_mm_wheel   part_slot=729  overridden_by=[]      ← 轮毂
```

轮胎、轮毂、刹车盘、底盘这些槽在**任何涂装下都不变**，给它们 6 套一模一样的预设
既浪费又没有意义。实现上按**签名**去重：`GameMaterials._signature(rm)` 把
`(材质名, 贴图, fresnel, specular, roughness, metallic, coat, paint_rgb)` 打包，
其中 `paint_rgb` **只对车漆材质计入**（`car_paint_*` / `car_bumper_paint_*`）——
否则轮胎会因为"车漆颜色不同"被误判成 6 套不同的材质。

实测 P1：**83 个网格里 20 个有 6 套预设、63 个只有 1 套**；Huayra：**103 个里 18 / 85**。
只有 1 套的网格 `rr3_paint_slots = 1`，`Switch paint scheme` 对它是空操作。

换涂装：选中网格 → *Car ▸ Switch paint scheme* → 填预设号（0 起）。
这个 operator 只做一件事：把那个预设的 BSDF 重新连到 Material Output
（`_activate_preset`），**不增加材质槽、不改 `poly.material_index`**。

实测：

| 车 | 网格 | 涂装 | 每个网格的槽数 | 场景内不同材质 |
|---|---|---|---|---|
| `2014_mclaren_p1` | 83 | 6 | **全部 1 槽 / 6 预设** | 22 |
| `2012_lexus_lfa` | 84 | 6 | 全部 1 槽 / 6 预设 | — |
| `2011_pagani_huayra` | 103 | 6 | 全部 1 槽 / 6 预设 | — |

P1 车身 `LOD_A_BODY_mm_ext`（材质 `2014_mclaren_p1_car_paint_gloss_paint`）的六个预设：

| 预设 | 游戏材质 | Roughness | Coat | 贴图 |
|---|---|---|---|---|
| 0 | `car_paint_gloss` | 0.045 | — | `_ext_yellow` |
| 1 | `car_paint_gloss` | 0.045 | — | `_ext_black` |
| 2 | `car_paint_metallic_cool` | 0.447 | 0.045 | `_ext_blue` |
| 3 | `car_paint_metallic_spec_orange` | 0.447 | 0.045 | `_ext_orange` |
| 4 | `car_paint_metallic_white` | 0.447 | 0.045 | `_ext_silver` |
| 5 | `car_paint_gloss` | 0.045 | — | `_ext_white` |

⇒ 同一台车的不同涂装可以用**不同材质模板**（有的光漆、有的金属漆），这就是为什么
不能只换贴图。Huayra 更极端：6 套里只有银色的 `Roughness` 是 0.447 且带清漆层
（`Coat Weight 1.0`），其余 5 套都是 0.045 无清漆。

`LOD_A_WING_REAR_mm_ext` 与车身**同材质同贴图**（尾翼跟着车身漆走），这与
`docs/HANDOFF-20261027.md` 里"尾翼发暗是因为拿到 `car_flat`"的结论一致：
涂装表缺行的时候尾翼才会掉到 `car_flat`。

### 7.0.1 `_mm_cab` 内饰面板也会跟着涂装变

上面说"只有涂装表覆盖到的才有多预设"，`_mm_cab` 就是被覆盖到的一类：
全库 **379 台多涂装车、1903 个 `_mm_cab` 网格里，49 个在不同涂装下解析出不同贴图**。
机制是涂装表的 **texture override**（`Paint.texture_of(slot)`），不是材质覆盖 ——
所以同一个材质名、同一套参数，只有贴图换。

```
2013_bugatti_veyron_gsv   LOD_A_BODY_mm_cab      part_slot=27
   paint1 cab_chrome / paint2 cab_orange / paint3 cab
   paint4 cab_chrome / paint5 cab / paint6 cab_orange
                          LOD_A_INTERIOR_mm_cab  part_slot=275  同上
1999_nissan_skyline_r34_r3
   paint1 _cab / paint2 _cab_blue / paint3 _cab
```

实测 Veyron GSV 的 `LOD_A_BODY_mm_cab` 拿到 **6 套预设**，atlas 分别是
`..._cab.png` / `..._cab_chrome.png` / `..._cab_orange.png`。

### 7.0.2 材质名必须唯一，否则会穿错贴图

`car_flat` / `car_matte` / `car_glass` 这几个材质名一台车会用在**好几个网格**上，
每个网格配的图集还不一样。早期版本用 `<车名>_<游戏材质名>` 当 Blender 材质名，
于是**先建的赢，其余网格全穿错图**。实测冲突数：

| 车 | 网格 | 不同材质名 | 撞名数 |
|---|---|---|---|
| `2014_mclaren_p1` | 67 | 15 | **3** |
| `2013_bugatti_veyron_gsv` | 84 | 14 | **4** |
| `2011_pagani_huayra` | 87 | 16 | **3** |
| `2012_lexus_lfa` | 68 | 14 | **4** |

P1 的 3 处：
```
2014_mclaren_p1_car_flat    2 sigs: tex=_misc  / tex=_cab
2014_mclaren_p1_car_glass   2 sigs: tex=car_windows_04 / car_windows_shattered_04
2014_mclaren_p1_car_matte   3 sigs: tex=_misc / tex=_lights / tex=_ext_yellow
```
改前后果：`LOD_A_DOOR_LEFT_mm_cab` 拿到 `_misc.png`（应该 `_cab.png`）、
`LOD_A_GLASS_FRONT_mm_windows` 拿到 `car_windows_shattered_04.png`（应该 `car_windows_04.png`）。

现在 `GameMaterials._unique_name(stem, tag)` 撞名时加 tag 后缀：
`<车>_car_flat` → `<车>_car_flat_cab`，再撞就 `_2`。实测改后
`2014_mclaren_p1_car_tail_light_rotor`（rotor 与尾灯共用一个材质名）、
`2013_bugatti_veyron_gsv_car_glass_windows`、`2014_mclaren_p1_car_flat_cab` 都对上了。

### 7.0.3 损伤件单独成组

车身文件里每个板件都同时有完好版和撞毁版，位置完全重合：
`DOOR_LEFT` + `DOOR_LEFT_DAMAGE`，玻璃和灯罩另有 `*_BROKEN_*`。
61 台车抽样里 `DAMAGE` 出现 1516 次、`BROKEN` 493 次，共 21 种基名：

```
LOD_A_DOOR_LEFT_DAMAGE 258 / DOOR_RIGHT_DAMAGE 258 / HOOD_DAMAGE 213 /
BONNETCAM_HOOD_DAMAGE 211 / REARBUMPER_DAMAGE 195 / BOOT_DAMAGE 193 /
FRONTBUMPER_DAMAGE 188 / TAILLIGHT_LENS_BROKEN_{A,B}_{LEFT,RIGHT} 57-59 /
HEADLIGHT_LENS_BROKEN_{A,B}_{LEFT,RIGHT} 52 / GLASS_BROKEN_REAR 36 /
TAILLIGHT_LENS_REARBUMPER_BROKEN_* 4 / TAILLIGHT_LENS_BOOT_BROKEN 1
```

`separate_damage`（默认开）把基名里含 `DAMAGE` / `BROKEN` 的网格放进
`<车名>_LOD<X>_damaged` 子集合，对象写 `rr3_damaged = True`；完好件留在主集合。
实测 `2014_mclaren_p1` 24 个、`2013_bugatti_veyron_gsv` 29 个、`2012_lexus_lfa` 22 个。
材质应用要用 `_all_objects(coll)` 递归收集，否则子集合里的网格会保留占位材质。

### 7.1 为什么改成单槽（旧版的问题）

旧版是"一个涂装一个材质槽"，实测有两个后果：

1. **Blender 是按 polygon 选材质的**。6 个槽摆在面板上，但 `poly.material_index`
   只指向其中一个，用户在视口里看到的多半不是默认涂装 —— 观感就是"贴图没进去"；
2. 网格面板上 6 个槽很容易被误改成别的槽，切涂装要手工翻 `material_index`。

改成单槽多预设后，`me.materials` 长度恒为 1，切涂装是一根连线的重接，
用户看到的永远是"当前涂装"那一套。

### 7.2 贴图为什么要 `pack()`

解码出来的 DDS/PNG 落在 `%TEMP%\rr3_dds`。不打包的话重启 Blender 后这些临时文件
被清掉，每张贴图都变粉色 —— 这看起来完全像"贴图从来没导入过"，而实际上是
"导入过但文件没了"。所以 `_image_for_path` / `_ramp_image` 加载后都调 `img.pack()`。

代价是 .blend 变大（一台 6 涂装的车约 15–20 MB 贴图）。要省空间就在导入后
*File ▸ External Data ▸ Unpack*，并把临时目录设成持久路径。

**解码产物按版本分目录**：`<临时目录>/rr3_dds/v2/`（`TEXTURE_CACHE_VERSION = 2`）。
贴图翻转是 2026-10-28 改的，之前解出来的 PNG 行序是反的，但文件名一样；
Blender 又只按路径命中已加载的图像、**不会重新读盘**，所以仅覆盖文件不足以让场景刷新。
分版本目录让旧解码永远不会被误命中，`_purge_stale_textures()` 再把 `v1` 之类的
旧目录、散落的 `.png/.dds`、以及引用它们的 `bpy.data.images` 一并删掉。

**加载要递归**：涂装图集在 `<车>/livery/` 下，不在车目录根。`_car_texture_files()`
用 `os.walk` 收集，平铺 `listdir` 会正好漏掉换涂装最需要的那几张
（P1 实测根目录 18 个文件 + `livery/` 6 个）。

### 7.3 私有贴图容器（`rr3lib/texport.py` + `ddsdecode.py`）

| 后缀 | 布局 | 全库数量 |
|---|---|---|
| `.dxt.dds.z` | `u32 rawSize` + zlib → 完整 DDS | 21,446 |
| `.dxt.dds.z.bin` | `u32 0xFFFFFFFF, version=1, frames, flags` + 每帧 `[u32 comp][u32 rawSize]` + zlib | 924（阴影图，实测 19–43 帧） |
| `.dxt.dds.bin` | 重复的 `[u32 rawSize][raw DDS]`，不压缩 | 2（实测 128 帧 × 32,900） |
| `.rgb.pvr.z` / `.ptc.pvr.z` | `u32 rawSize` + zlib → 完整 PVR | 3,229（车辆里 12 个） |
| `.atc.dds.z` / `.etc.dds.z` | `u32 rawSize` + zlib → DDS，块格式是 `ATC `/`ETC ` | 各 9（只在 gui_assets） |

车辆贴图**只用 DXT1 / DXT5**（7,846 个 `.dds.z`：DXT1 6,248、DXT5 1,598，0 个解码失败），
由 `rr3lib/ddsdecode.py` 自己解（numpy 可用时快 8 倍，两条路径字节级一致；
与 Blender 自带 DDS 解码逐像素对比 0 处差异）。

**9 台车的 badges/wheel/misc 只有 `.rgb.pvr.z`、没有 DDS 兄弟文件**：
`2008_bmw_z4_m`、`2012_audi_a5_touring`、`2016_mclaren_mp4x_uvc`、`2020_ligier_js_p320`、
`2022_bugatti_centodieci`、`2024_f1_haas_vf24`、`2024_hyundai_i20_n_rally1_wrc_11`
（bpp 16 掩码展开、32 直读、8 灰度三种都要支持，`rr3lib/pvr.py` 已覆盖）。

## 8. 怎么在 Blender 里核对

```python
ob = bpy.data.objects["LOD_A_BODY_mm_ext"]
mat = ob.data.materials[0]                     # 永远只有一个
print(len(ob.data.materials), mat.name)        # 1 2014_mclaren_p1_car_paint_gloss_paint
print(mat["rr3_presets"], list(mat["rr3_preset_names"]), mat["rr3_preset_active"])

nt = mat.node_tree
out = next(n for n in nt.nodes if n.type == "OUTPUT_MATERIAL")
print("wired:", [l.from_node.name for l in nt.links if l.to_node == out])   # ['bsdf_0']

for i in range(mat["rr3_presets"]):
    b = nt.nodes[f"bsdf_{i}"]
    t = nt.nodes[f"atlas_{i}"]
    print(i, b.inputs["Roughness"].default_value,
          b.inputs["Coat Weight"].default_value,
          b.inputs["Base Color"].default_value[:3],
          t.image.name if t.image else None)
```

材质上写了这些自定义属性：`rr3_presets`、`rr3_preset_names`、`rr3_preset_active`、
`rr3_material`、`rr3_application`、`rr3_fresnel`、`rr3_specular`；
网格对象上是 `rr3_paint_slots`、`rr3_paint_slot`、`rr3_paint_presets`。

**找不到材质表时**（车被拷出 depot）：`_apply_game_materials` 会抛错，导入把它记成
`game materials: cannot find the depot's materials/materials.bin above <car_dir>`，
并保留 `simple` 的占位材质。把导入面板的 `material_depot` 指到 `.depot` 即可。
判断方法：导入后看 `bpy.data.materials` 里有没有 `*_paint` 后缀的材质，没有就是没读到表。

## 10. 还没弄清楚

1. **`[1]` 槽的 15 条引用是什么**：只在少数材质上出现，还没确认是漫反射还是别的 mask。
2. **`[6]` 槽**只有 2 条（`car_rotor` 的自发光），插件目前没用它。
3. **9 条色带解析不到**：全是 `<texname>_refl.pvr` 这种占位符
   （`glass` / `glass_low` / `glass_night` / `glass_night_low` / `garagemetal` /
   `garagemetalshinny` / `garageconcrete`），是车库/赛道的环境反射占位。
4. **`car_paint_*` 的 `s_cubeMap`** 指向 `s_carReflectionCubeMap`，这是引擎运行时生成的
   立方图，磁盘上没有。所以车漆的反射只能用 Blender 的环境光。
5. **`roughness` / `metallic` 的换算是经验映射**，不是引擎原式。观感接近但不等于游戏内截帧。
