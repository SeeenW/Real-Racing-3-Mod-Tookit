## 1. 环境（本次会话变更）

MuMu 升级后 **adb 路径变了**，旧常量失效：

```
旧  D:\Program Files\Netease\MuMu\nx_device\15.0\shell\adb.exe   ← 目录已不存在
新  D:\Program Files\Netease\MuMu\nx_device\12.0\shell\adb.exe
```

因此新增 `analysis/rr3adb.py`，运行时用 glob 扫 `<MuMu>\nx_device\*\shell\adb.exe`
按版本号倒序取最新，并自动在 `端口 5038/5037 × 序列号 16384/5555/emulator-5554`
的组合里探活。**所有工具的 adb 常量都已改为从它导入**，以后 MuMu 再升级不用改代码。

```python
import rr3adb
ADB, SERIAL, ADB_PORT = rr3adb.ADB, rr3adb.SERIAL, rr3adb.PORT
```

`rr3adb.su(cmd)` 走 `adb shell su -c '<cmd>'`；`rr3adb.adb(*args)` 首参不是 `-s`
时会自动补 `-s SERIAL`（漏了这步会报 `more than one device/emulator`）。

## 2. 地址链（最容易搞错的地方）

`.so` 是 PIE，且**第 2、3 个 PT_LOAD 的文件偏移与虚拟地址差 0x1000**。
把这两件事搞混，读出来的每个值都是错的，而且不会报错。

```
ELF vaddr        ADRP/branch 的目标、.rela.dyn addend 都用这个空间
Ghidra VA        = ELF vaddr + 0x100000        （imageBase = 0x100000）
.so 文件偏移     = ELF vaddr - p_vaddr + p_offset
apk 偏移         = 0x411C000 + .so 文件偏移    （zip 里 .so 是 STORED 未压缩）
运行时地址       = apk_mapping.start + (apk偏移 - apk_mapping.off)
```

段表实测：

| PT_LOAD | p_offset | p_vaddr | filesz | 偏移差 |
|---|---:|---:|---:|---:|
| 1 (.text) | 0x00000000 | 0x00000000 | 0x01E19AE0 | 0 |
| 2 | 0x01E19AE0 | 0x01E1AAE0 | 0x00164DA0 | **0x1000** |
| 3 | 0x01F7E880 | 0x01F80880 | 0x000146A0 | **0x1000** |

> 教训：**ADRP 的 PC 必须用 ELF vaddr，不能用 Ghidra VA**。用 Ghidra VA 会整体偏高
> 0x100000，算出来的 GOT 槽落到别的段里，读到的字节看着"像那么回事"但完全是垃圾。
> 本次就因为这个 bug 白读了一轮 `ff / fd / e0` 的假标志位。

工具：`analysis/addr.py`（反汇编 + vaddr→fileoff + reloc 查询）、`analysis/mem.py`（进程内存读写）。

```powershell
python analysis/addr.py adrp 0x010E87CC        # ADRP + 后续 LDR/ADD → 真实地址
python analysis/addr.py fn   0x010E8DBC 0xC0   # 反汇编一段
python analysis/addr.py str  0x004F7812        # 读 C 字符串
python analysis/addr.py reloc 0x01F6E598       # 查 .rela.dyn
python analysis/mem.py read 0x010E87C4 8       # 读活进程
python analysis/mem.py deref8 0x01F6E598       # 解一层指针再读 1 字节
```

## 3. 补丁表（8 处，全部已验证）

全部作用于 `lib/arm64-v8a/libRealRacing3.so`。地址列是 **Ghidra VA**，
`analysis/patch_debug_menu.py` 内部会转成文件偏移。

| Ghidra VA | 原字节 | 新字节 | 作用 |
|---|---|---|---|
| 0x011E87C4 | FD 7B BF A9 | 20 00 80 52 | `AreCheatsAllowed` → `mov w0,#1` |
| 0x011E87C8 | FD 03 00 91 | C0 03 5F D6 | `AreCheatsAllowed` → `ret` |
| 0x011E8738 | 80 01 00 B4 | 1F 20 03 D5 | `EnterPassword` 跳过空指针失败分支 |
| 0x011E8748 | 08 85 55 39 | 28 00 80 52 | `EnterPassword` 权限字节强制为 1 |
| 0x011E8AA0 | FD 7B BC A9 | 61 98 FF F0 | `StartAcceptingPassword` 构造 "Ironmint" 页地址 |
| 0x011E8AA4 | F8 5F 01 A9 | 21 48 20 91 | 加上页内偏移 0x812 |
| 0x011E8AA8 | F6 57 02 A9 | 14 FF FF 17 | 尾调用 `EnterPassword` |
| 0x011E8DF8 | C0 02 00 B4 | 03 00 00 14 | 角落三击路径跳过权限门 |

`StartAcceptingPassword` 打完补丁后等价于：

```asm
adrp x1, 0x4F7000
add  x1, x1, #0x812      ; "Ironmint" @ VA 0x004F7812
b    EnterPassword
```

即**角落三击 = 自动输入作弊密码 "Ironmint"**，这就是整个调试菜单的钥匙。

## 4. 触发链路（逆向结论）

```
物理屏幕角落连点三次
  → 角落释放处理函数  0x010E8DBC   （vtable 槽 0x1EB9050，无 BL 调用者）
       检查 [obj+0x561] 权限字节
       在 [obj+0x260] 里累计点击数，满 3 次
  → 0x010E8AA0  StartAcceptingPassword
  → 0x010E86F8  EnterPassword("Ironmint")
       成功后往 GOT 0x1F75D20 指向的字节写 1（作弊标志）
  → 0x010E87C4  AreCheatsAllowed 开始返回 true
  → 主菜单出现 Σ 按钮（BTN_DEBUG_RACE，图 button/sigma.png）
  → 点 Σ → DebugRaceSelectScreen
```

相关 GOT 槽（ELF vaddr）：

| GOT 槽 | 指向 | 含义 |
|---|---|---|
| 0x1F75D20 | cheat flag | `EnterPassword` 成功时写 1 |
| 0x1F6E598 | `*PTR_DAT_0206e598` | debug 开关（控制 Σ 按钮可见性） |
| 0x1F6D5D0 | cheat profile | `AreCheatsAllowed` 读 `+0x561` |

`analysis/debug_menu.py status` 会同时校验 APK 内补丁字节和活进程里的运行时字节。

## 6. 配置文件 DebugRaceSelect.2.cfg

路径：`files/doc/DebugRaceSelect.2.cfg`，**49 字节**。

读取：`FUN_00af4c08`（Ghidra 0x00AF4C08，caller `FUN_00af6410` / `FUN_00e986f0`）
写出：`FUN_00af4f58`（Ghidra 0x00AF4F58，caller `FUN_00af6e24` / `FUN_00e98b74`）

两者字段顺序完全一致：

| 偏移 | 大小 | 写入目标 | 当前值 |
|---|---:|---|---:|
| 0x00 | 4 | magic `0x00376765`（"eg7\0"） | — |
| 0x04 | 4 | +0x08 赛道索引 | 51 |
| 0x08 | 4 | +0x0c | 0 |
| 0x0C | 4 | +0x10 | 1 |
| 0x10 | 4 | +0x18 | -1134080 |
| 0x14 | 4 | +0x1c | -1024 |
| 0x18 | 4 | +0x14 | 0 |
| 0x1C | 1 | +0x20 | 1 |
| 0x1D | 1 | +0x21 | 1 |
| 0x1E | 1 | +0x22 | 0 |
| 0x1F | 4 | +0x24 | 0 |
| 0x23 | 1 | +0x28 | 0 |
| 0x24 | 1 | +0x30 | 0 |
| 0x25 | 4 | +0x2c | 0 |
| 0x29 | 4 | +0x38 | 0 |
| 0x2D | 4 | +0x3c | 0 |

读取函数还会扫实时赛道表，找名字等于 `"circuit"` 的条目，把它的索引写进 `+0x08`

**注意**：这个文件只在 **DebugRaceSelectScreen 里按 PLAY** 时才写盘，
拨 `DebugRaceSelector` 开关本身不改它。所以想从文件侧观察选择结果，
必须先真正开一局。

工具：`analysis/debug_cfg.py`

```powershell
python analysis/debug_cfg.py show      # 拉下来并逐字段解码
python analysis/debug_cfg.py pull --watch   # 盯着 mtime 变化自动重拉
```

## 7. 构建与部署

```powershell
# 1) 校验源 apk 里 10 个点的原始字节（8 条新补丁 + 2 条 legacy）
python analysis/patch_debug_menu.py verify

# 2) 从 base_original.apk 重新拷贝并逐点打补丁 → work/sopatch/base_patched.apk
python analysis/patch_debug_menu.py build

# 3) 推上去并重启游戏
python analysis/patch_debug_menu.py push
```

`.so` 在 apk 内是 **STORED（未压缩）**，所以可以原地改字节，**不需要重新签名**。

## 8. 验证手段（当前模型读不了图）

这个环境里 `read_image` 会报 `model does not declare image input`，
所以不能靠看截图确认。可用的替代手段：

| 手段 | 命令 | 能看出什么 |
|---|---|---|
| 补丁字节 | `debug_menu.py status` | APK 内 + 活进程里的字节是否已改 |
| 运行时标志 | `debug_menu.py flags` | 作弊标志/debug 开关的真实值 |
| 像素变化率 | `screen.py` / `debug_menu.py tap3` | 画面是否真的切换了 |
| ASCII 渲染 | `analysis/ascii.py --grab 170` | 粗看布局（亮字/暗底、面板分块） |
| 文件 mtime | `debug_cfg.py pull --watch` | 游戏是否写了配置 |
| logcat | `dev.py logcat` | 游戏基本不打这些日志，参考价值低 |
| uiautomator | `uiautomator dump` | **看不到** ImGui/自绘 UI，只有原生控件 |

> 本次的关键突破其实是**让用户去看一眼屏幕**：所有工具都只能证明"字节改了"，
> 只有人眼能确认"菜单出来了"。
